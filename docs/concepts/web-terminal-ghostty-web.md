# Web/Desktop Terminal on ghostty-web

Applies from 2026-10-28. Earlier xterm.js behaviour is recorded only in the gotchas marked historical.

The terminal panel uses `Terminal` and `FitAddon` from `ghostty-web` (libghostty-vt compiled to wasm, drawn on a canvas 2D), installed from ocode's fork rather than npm (see "Dependency source"). The ~400 KB wasm is embedded in the JS bundle as a `data:` URL, so there is no asset or MIME concern. Pulse reads terminal screens with the headless `GhosttyTerminal` from the same package.

## Dependency source

`web/package.json` pins `ghostty-web` to `file:vendor/ghostty-web-0.4.0-<sha>.tgz`, a tarball built from the `security-fixes` branch of [u007/ghostty-web](https://github.com/u007/ghostty-web), a fork of coder/ghostty-web based on upstream main after the 0.4.0 release (so it also carries upstream's mouse tracking, PR #106, which the npm 0.4.0 package lacked). The fork publishes no npm package and commits no `dist/`, and its wasm build needs Zig plus the ghostty submodule, so pnpm cannot install it from git; the checked-in tarball is what every checkout and CI installs. On top of upstream 0.4.0 the branch carries: pasted control characters replaced with spaces as native Ghostty does (CVE-2026-26982, upstream PR #193), OSC 8 links limited to http(s) plus a `linkHandler` option (PR #194), window titles stripped of control characters and capped at 255 bytes (PR #195), the inlined wasm decoded in memory instead of fetched so a strict CSP works (PR #196), zero-initialized wasm page buffers (PR #142, see the heap trap below), and dependency CVE bumps. To update: commit in the fork checkout, run `bun run build:wasm` there once (needs Zig), then `web/scripts/pack-ghostty-web.sh <fork-dir>`, point `package.json` at the printed tarball, run `pnpm install`, and delete the old tarball.

## Traps of ghostty-web 0.4.0

- **Load the wasm yourself.** `new Terminal` throws unless `options.ghostty` is passed or `init()` ran. ocode never calls `init()`; `ghosttyRuntime.ts` loads `Ghostty` and the panel passes it as `options.ghostty`.
- **Unzeroed wasm heap in upstream 0.4.0 (measured 2026-10-28).** Once any terminal in a `Ghostty` instance had been freed, a later terminal in the same instance read garbage codepoints and stale wide characters from cells it never wrote. On the Pulse parity fixtures one shared instance corrupted 9 of 20 cases and a fresh instance per terminal rendered all 20; it reproduces in plain Node. The stale data is in the terminal's own page memory, so zeroing the viewport export buffer does not help. The vendored fork zero-initializes page buffers (upstream PR #142) and the same probe shows 0 of 20 corrupt with a shared instance, so every panel and every Pulse screen read now shares the one instance `loadGhostty()` caches (a failed load is not cached). The panel calls `Terminal.reset()` only to apply a changed scrollback setting (see Traps) and never for the Reset action, because it frees and recreates the wasm terminal and drops the selection and link state under the panel: a full reset is written as RIS (`ESC c`), and Clear writes `ESC [3J` after `clear()` to drop the scrollback.
- **No OSC handler API.** There is no `parser`. Titles and OSC 9/777/99/52 come from `terminalStream.ts`, which scans the byte stream.
- **Bell on OSC terminators.** `onBell` fires when a written chunk contains `\x07` anywhere, including the BEL ending `ESC ] 0 ; title BEL`. `onTitleChange` only sees OSC 0/1/2 inside one chunk. Neither is used.
- **`write` parses synchronously.** The callback is deferred with `requestAnimationFrame` and never fires in a hidden tab. Never await it. ghostty-web 0.4.0 still ends every `write` with `if (this.viewportY !== 0) this.scrollToBottom();`, so a scrolled-up viewport would bounce to the bottom on each chunk; ocode re-anchors it to the same content via `web/src/components/Terminal/terminalScrollAnchor.ts` (`writePreservingScrollback`), which wraps every pty write and ocode banner. Raw `term.write` remains only for full-buffer operations — the RIS reset, Clear's ED 3, and the scrollback-setting/theme rebuild replays — which intentionally end at the bottom.
- **Built-in mouse reporting, but not the one ocode needs.** The fork's `InputHandler` listens for mousedown/mouseup/mousemove/wheel on the host and sends SGR/X10 reports when the program tracks the mouse. It sends no focus reports (1004), reports shift/alt presses that ocode reserves for selecting text under a mouse-owning program, reports every wheel pixel delta, and only sees releases inside the host. `disableBuiltinMouseReporting` (ghosttyInternals.ts) removes those four listeners after `open()`, and `terminalMouse.ts` is the single sender of SGR and X10 reports and `CSI I`/`CSI O`. The npm 0.4.0 release had no mouse reporting at all; with the fork, leaving both in place sends every release, motion and wheel report twice.
- **Built-in copy-on-select.** The selection manager copies on mouseup and double-click itself. ocode owns copy (dedupe against Cmd+C and Edit > Copy, desktop native clipboard), so `disableBuiltinSelectionCopy` replaces that path.
- **Focus lands on the textarea, never the host.** `Terminal.focus()` focuses the contenteditable host. A phone soft keyboard types into the host, and ghostty-web cancels that host's `beforeinput` instead of forwarding it, so the keyboard shows and nothing reaches the pty. Only the textarea's `beforeinput` is forwarded. Every ocode focus call goes through `focusTerminalInput` (`terminalFocus.ts`), and the press-to-focus path in `terminalMouse.ts` focuses the textarea directly. Hardware keys bubble to the host either way, so they are unaffected.
- **Built-in link providers `window.open` on ctrl/cmd-click.** They are removed (`clearBuiltinLinkProviders`) and ocode registers its own. `registerLinkProvider` returns nothing; providers live until `dispose()`.
- **Custom key handler convention is inverted from xterm.js.** Returning `true` means handled: skip ghostty-web and `preventDefault`. Cmd/Ctrl+V must return `false`, or the browser `paste` event dies.
- **The host element becomes `contenteditable`.** `open()` needs a dedicated inner div (`.terminal-host`), never the panel container that also holds the find bar.
- **Wheel is captured at the host.** `handleWheel` calls `stopPropagation`, so ancestor wheel listeners need `capture: true`.
- **Option changes after `open()`.** Only `cursorBlink`, `cursorStyle`, `fontSize`, `fontFamily`, `cols`, `rows` apply live. `theme` does not. `scrollback` does not either, but the panel applies a changed `scrollbackLines` to an open terminal itself: it serializes the buffer, sets `options.scrollback`, calls `Terminal.reset()` (which rebuilds the wasm terminal from that option) and replays the text, like the mount restore. The pty and socket are untouched. The rebuild drops terminal modes (mouse tracking, alternate screen, bracketed paste) that a running full-screen program had set, plus the selection and link cache; the program is not asked to re-send them, so it keeps running but looks idle to the mouse and redraws only when it next repaints. This is the one deliberate `reset()` call, acceptable because the setting changes rarely.
- **`select(col,row,len)` is wrong when scrollback exists.** Use `setSelectionAbsolute` from `ghosttyInternals.ts`.
- **`buffer.active.viewportY` is always 0.** Use `getViewportY()`.

### Phone soft-keyboard navigation keys

On a phone, SwiftKey's/Gboard's arrow row used to do nothing while ordinary typing worked. ghostty-web's `handleKeyDown` bails out immediately for `keyCode === 229` (the marker Android stamps on every soft-key event) and resolves a navigation key from `event.code` only, so a keyboard that delegates arrows through `InputConnection.sendKeyEvent` supplies no usable `code` and nothing is encoded (and no `preventDefault` happens). Ordinary text is unaffected because it rides `beforeinput`, not `keydown`. Backspace does not survive that route either; see the Backspace subsection below.

`terminalSoftKeyboard.ts` (`softKeyboardNavigationSequence`, `terminalSoftKeyboard.ts:91`) resolves the key by `event.key` → `event.code` → `event.keyCode` and maps ArrowUp/Down/Left/Right, Home, End, PageUp, PageDown, Insert, Delete to their DEC (`\x1b[A`) or application-cursor (`\x1bOA`) forms. The panel claims the leftovers in a capture-phase `keydown` on the panel root (`TerminalPanel.tsx:1119`–`1132`): it guards with `term.element.contains(target)` so the find bar's input is untouched, calls `preventDefault` + `stopPropagation`, then `term.input(seq, true)` (`TerminalPanel.tsx:1131`), so the pty sees exactly what a hardware arrow would send and the attach guard in `term.onData` applies. DECCKM comes from `term.getMode(1, false)` (`TerminalPanel.tsx:1125`), selecting `\x1bOA` vs `\x1b[A`.

Rules:
- Anything with a usable physical `code` and a non-229 keyCode stays ghostty-web's — including codes this table does not name (keypad arrows, F-keys): `terminalSoftKeyboard.ts:112` only claims soft-keyboard-shaped events (`keyCode === 229`, or no usable `code`), so Kitty/CSI-u and keypad encodings are neither bypassed nor double-sent.
- A modified arrow (ctrl/alt/meta/**shift**) stays ghostty-web's (`terminalSoftKeyboard.ts:100`): only the unmodified form is synthesised, and a plain arrow for a modified one would break selection or word-wise movement. Phone keyboards produce no modifiers.
- A nav key during an IME composition is ignored (`TerminalPanel.tsx:1120`) — the arrows move between candidates there and an escape sequence would corrupt the composition.
- Enter/Tab are deliberately not synthesised — they ride the text path and claiming them would double-send. Backspace is the exception; see the Backspace subsection below.
- The find-bar input is excluded by `term.element.contains(target)` (`TerminalPanel.tsx:1124`).
- `ghosttyWebMock.ts:105` mirrors the real `input(data, true)` by firing `_data` when `wasUserInput`, so the typed-input path is exercised in tests.

Regression suite: `web/src/components/Terminal/TerminalPanel.mobileKeys.test.tsx` (15 cases: 10 navigation, which were mutation-verified when written, and 5 Backspace) and `web/src/components/Terminal/terminalSoftKeyboard.test.ts` (8 unit cases for the pure functions).

### Phone soft-keyboard Backspace is dropped by ghostty-web (fix uncommitted, unverified on device)

ghostty-web drops a Backspace from an Android soft keyboard on two independent paths in the vendored build:

- Its keydown handler returns at once for `keyCode === 229` (`ghostty-web.js:956`), so the soft-keyboard Backspace keydown is never encoded.
- Its `beforeinput` handler maps `deleteContentBackward` to `""` (`ghostty-web.js:1108`–`1109`). The send guard `if (g)` (`ghostty-web.js:1126`) skips an empty string, so no `onData` fires.

Neither route reaches the pty. The earlier statement in this doc and in `TODO.md` that Backspace rides the text path and works was wrong.

Fix (uncommitted at time of writing): `softKeyboardBackspace` in `terminalSoftKeyboard.ts` (`terminalSoftKeyboard.ts:125`) returns `\x7f` for `key === "Backspace"` or `keyCode === 8`, only when unmodified and soft-keyboard shaped (keyCode 229, or no usable `code`). A hardware Backspace (real `code`, no marker) returns null and stays with ghostty-web, so it is not doubled. The panel calls it from the capture-phase keydown listener (`TerminalPanel.tsx:1126`) and adds a capture-phase `beforeinput` listener (`TerminalPanel.tsx:1144`–`1158`) that sends `\x7f` for a non-composing `deleteContentBackward`. Both paths call `inputGuard.noteInput()` and then `term.input("\x7f", true)`.

Unverified: the fix assumes `preventDefault()` on the keyCode-229 keydown suppresses the `beforeinput` that follows on Android. If both fire, one Backspace deletes two characters. Check on SwiftKey and Gboard with an empty prompt and a non-empty one, using a keydown/beforeinput logger on `chrome://inspect`.

Still open (hypotheses, not fixed; need an on-device event trace): doubled words from `insertReplacementText` (autocorrect), which is sent like `insertText` without erasing the word it replaces; and a missed `compositionend` leaving ghostty-web's `isComposing` set, so later text is dropped. Tracked in `TODO.md`.

### Phone soft-keyboard IME re-commits sent twice (addressed 2026-11-02, uncommitted at time of writing)

Symptom (reported): on a phone/tablet soft keyboard, typing in the terminal tab (and the embedded browser tab) often produced a duplicated word and the shell executed the command twice; typing also sometimes appeared to do nothing. The user had the desktop app and a browser tab open on the same project — relevant to one of the still-open items below, not the cause of the duplication.

Root cause (measured, not inferred): ghostty-web de-duplicates a re-delivered IME commit only inside its own 100 ms window (`BEFORE_INPUT_IGNORE_MS = 100`, `web/node_modules/ghostty-web/dist/ghostty-web.js:1356`, consulted by the vendored helpers `shouldIgnoreBeforeInput`, `shouldIgnoreBeforeInputFromComposition` and `shouldIgnoreCompositionEnd`, `ghostty-web.js:1292`–`1310`). Against a real ocode server (Playwright Chromium + CDP `Input.imeSetComposition` then `Input.insertText`, i.e. the Android soft-keyboard event shape) with an IDENTICAL DOM event sequence — compositionstart, compositionupdate, beforeinput(insertCompositionText, isComposing=true), input, compositionupdate, beforeinput, input, compositionend, then a later beforeinput(insertText) — only the timing differed: a re-commit 60 ms after the first sent `["ls"]` to the pty; a re-commit 250 ms after the first sent `["ls","ls"]` and the shell ran `ls` twice. A phone's main thread is busy enough that the second delivery is routine. Plain hardware-key typing was already correct — 45 keystrokes produced exactly 45 frames through one send site (`InputHandler.handleKeyDown` → `onData`), verified in both Chromium and WebKit — and the server writes each received frame to `sess.ptmx` exactly once (`internal/server/handler_terminal.go:591` `serveTerminalSocket`), so the duplication is entirely client-side between `onData` and the socket.

Fix: `web/src/components/Terminal/terminalInputGuard.ts` (`createTerminalInputGuard`, `terminalInputGuard.ts:59`; `IME_DUPLICATE_WINDOW_MS = 600`, `terminalInputGuard.ts:40` — the narrowest window the duplicate tests allow, since no event-level signal separates a re-delivery from a real repeat: both are a `compositionend` with the same text, so the window is the only discriminator). A frame is suppressed ONLY when all of these hold (`terminalInputGuard.ts:83`–`89`): it equals the text of a recorded `compositionend`, it equals the previous ACCEPTED frame (so nothing was typed in between), it is 2+ characters, it carries no C0 control characters, and it arrives within 600 ms of that previous frame. Any other frame updates the record (`terminalInputGuard.ts:92`–`96`), so Enter, a space or another word re-arms it. Keydown-derived text and pastes never match a composition commit, so ordinary typing, `ll`, key-repeat and repeated paste are never suppressed — swallowing real input is worse than showing a duplicate, so the scope is deliberately narrow. The guard also exposes `noteInput()` (`terminalInputGuard.ts:54`, both it and `reset` bound to the same `endCommit`, `terminalInputGuard.ts:100`–`101`) so a code path that sends input WITHOUT passing through `accept` can still end the pending commit.

Wiring: `TerminalPanel.tsx` holds ONE guard as panel state (`TerminalPanel.tsx:548`, `useState(() => createTerminalInputGuard())`), so the terminal effect and the input paths outside it share it, and `connectSocket` calls `reset()` on every new socket (`TerminalPanel.tsx:1695`). It registers a `compositionend` listener on `term.textarea` (`TerminalPanel.tsx:1219`–`1221`; the element is captured into `imeInput` first because `term.dispose()` clears `term.textarea`) and gates `term.onData` (`TerminalPanel.tsx:2120`–`2135`). The gate runs after the attach-handshake/socket-open check (`TerminalPanel.tsx:2123`), so a frame dropped there is never recorded. The listener is removed in the effect cleanup (`TerminalPanel.tsx:2178`). Every input path that sends WITHOUT going through `accept` calls `noteInput()` first, or an identical frame sent right after a commit would be dropped as its re-delivery: the file-upload name send (`TerminalPanel.tsx:601`), the voice transcript paste (`TerminalPanel.tsx:627`), the paste handler (`TerminalPanel.tsx:1097`), the soft-keyboard navigation write (`TerminalPanel.tsx:1130`) and the Shift+Enter send (`TerminalPanel.tsx:1309`). Keystroke frames flow through `accept`, and any frame that differs from the pending commit clears it (`terminalInputGuard.ts:96`). `web/src/components/Browser/ChromeViewport.tsx` uses the same guard on its composition commit: `onCompositionEnd` records and accepts the text and sends one `insertText` frame (`ChromeViewport.tsx:929`–`935`); its keydown and paste paths send CDP commands directly instead of through `accept`, so they call `noteInput()` explicitly (`ChromeViewport.tsx:855` and `ChromeViewport.tsx:944`) — but the paste itself is deliberately NOT deduplicated (a paste is a deliberate action, `ChromeViewport.tsx:940`–`947`). The viewport holds one guard for its lifetime (`ChromeViewport.tsx:133`–`134`).

Verification: `terminalInputGuard.test.ts` (36 cases: 15 `it` + 21 `it.each` rows, `terminalInputGuard.test.ts:17`, with the `isTerminalGeneratedReply` tables at `:141`); `TerminalPanel.imeDuplication.test.tsx` (6 cases, `TerminalPanel.imeDuplication.test.tsx:136` — the re-commit case was RED before the wiring (two sends) and is green after; per-keystroke typing and a post-Enter repeat are still delivered); `ChromeViewport.test.tsx:336` "types a re-delivered IME commit once, not twice" (mutation-verified). End-to-end: after rebuilding `web/dist`, the CDP probe's 250 ms case now sends `ls` once; the 60 ms case is unchanged (ghostty-web's own window already covered it).

Still open (recorded in TODO.md): a re-commit that arrives as a brand-new composition is still delivered (the guard only matches a recorded `compositionend`); the single attachment slot itself is unchanged, so a client that never received the `detached` frame can still take the terminal back on its own reconnect and a takeover can flip-flop; `terminalImeHygiene.ts` is still attached (`TerminalPanel.tsx:1212`) but is xterm-era dead code whose documented mechanism (xterm's textarea `value` diff, `terminalImeHygiene.ts:1`–`13`) does not exist in ghostty-web; and the repro is CDP-driven, not yet confirmed on a physical Gboard device.

### A displaced or not-yet-attached terminal now says so instead of eating keystrokes

The same phone report also said "typing sometimes isn't working". Two paths dropped every `term.onData` frame with no feedback: a superseded terminal (another client owns the id) and a terminal whose socket is down or still in its attach handshake. Both are now visible, and neither is queued — replaying stale keys into a shell is dangerous:

- A superseded terminal renders a BLOCKING overlay instead of the old bottom strip: `role="alert"`, `data-testid="terminal-taken-over"`, `inset-0`, "This terminal is open in another window or device." / "Typing here is paused so nothing is lost." plus the existing **Take over** button. `termRef.current?.blur()` runs when the takeover engages, so a phone closes its soft keyboard rather than typing into a detached socket.
- A keystroke arriving while `!attachedRef.current` or with the socket not OPEN sets `inputPaused` (`TerminalPanel.tsx:2128`), which renders "Reconnecting — input is paused until this terminal is attached." (`role="status"`, `TerminalPanel.tsx:2491`). Only real keystrokes raise it. Frames the terminal writes itself (focus in/out, DA/CPR replies, mouse reports) are dropped silently, because they are not typing (`isTerminalGeneratedReply`, `terminalInputGuard.ts:116`). The notice clears on the attach frame (`TerminalPanel.tsx:1811`), on takeover (`TerminalPanel.tsx:1890`) and on the clean-close branch (`TerminalPanel.tsx:1902`–`1910`). That branch also sets `sessionEnded`, so typing after a shell exit does not re-raise the notice and only the "[terminal session ended]" line shows. `sessionEnded` resets on each `connectSocket` (`TerminalPanel.tsx:1721`).
- Server-side, `websocket attach … remote=<addr>` and `reattached (pid N) remote=<addr>` make a phone report diagnosable, and the single-slot supersede logs `superseded socket remote=<old> (new remote=<new>)` before sending the `detached` frame — so "the client sent nothing" is distinguishable from "the frames never arrived".

Regression: `TerminalPanel.wake.test.tsx`, "TerminalPanel input while detached" (4 cases: paused on a keystroke, silent for the terminal's own replies, kept through an unexpected drop, cleared when the shell exits) and "TerminalPanel takeover" ("explains the takeover instead of claiming the session ended"). Dropping the paused state or the `blur()` call fails these.

### A tab switch can leave the terminal zoomed out at a stale size

Reported on the web and in the desktop shell: after a tab switch the terminal sometimes renders zoomed out at a very small font, and only resizing the window restores it. Two ghostty-web behaviours stack up. `FitAddon.fit()` early-returns while `_isResizing` is true, and `_isResizing` stays true for 50 ms after every resize the addon performs (its own `setTimeout(…, 50)`). A tab switch can hand the terminal a pane that has not reached its final size yet — a tab strip that re-wraps, a layout pass between `display: none` and visible — so the follow-up `ResizeObserver` fit lands inside that window and is dropped; nothing else changes the pane, so the transient proposal sticks. `TerminalPanel.tsx` now schedules ONE post-layout re-fit `FIT_RETRY_MS = 70` after every fit `fitAndResize` performs (`run()` arms `fitRetryTimerRef`, `retry()` re-checks that the container still has layout); the timer is one-shot, never chained, and cleared in the terminal effect cleanup. 70 ms clears the 50 ms guard, and a pane that has already settled makes the retry a no-op.

The second half is that a correct fit cannot repair a stale canvas. `fit()` is a no-op when the proposed cols/rows equal the current ones, so it cannot fix a backing store that went stale while an ancestor was `display: none` (WKWebView in the desktop app is the reported case). The render loop repaints only rows the wasm buffer flags dirty, so a lost or descaled backing store stays broken — which is why an unrelated window resize "fixes" it: `Terminal.resize` re-creates the canvas. `resyncTerminalViewport` (`ghosttyInternals.ts`) is that primitive in isolation: `renderer.resize(term.cols, term.rows)` (the only ghostty-web path that re-creates the backing store and re-applies the device-pixel transform) followed by a full-frame `redrawTerminal` (`renderer.render(buffer, true, …, term)`). The `[active]` effect snapshots `term.cols`/`term.rows` before the activation fit and calls it only when the fit left them unchanged — otherwise `Terminal.resize` already repainted. It is a no-op before `open()` and throws `ghostty-web internals changed: CanvasRenderer.resize is not a function` if a vendored bump renames the method.

Timing and cost: the 70 ms retry is one extra `fit()` per `fitAndResize` invocation (the `ResizeObserver` path included), never chained and a no-op once the size has settled, so it does not re-fit on every observer event. The canvas re-creation is activation-only — at most one `renderer.resize` plus a full-frame repaint per tab switch, i.e. the work the user's manual resize was doing.

Regression: `TerminalPanel.appearance.test.tsx` "TerminalPanel activation refit" (asserts the activation fit, a second fit after `FIT_RETRY_MS`, and the `resyncTerminalViewport` call; removing the retry timer or the resync call fails it) and `ghosttyInternals.test.ts` "resyncTerminalViewport" (resize arguments, full-redraw arguments, no-op before `open()`, and the loud failure on a renamed method). `ghosttyWebMock.ts` now records `FakeFitAddon` instances and exposes `resyncTerminalViewport: vi.fn()` so the panel test can observe both.

## Behaviour changes versus xterm.js

- A terminal scrolled up no longer bounces to the bottom while output streams: the viewport follows output only when already at the bottom (xterm.js/native Ghostty behavior), via `terminalScrollAnchor.ts` / `writePreservingScrollback` wrapping `writeOutput` and `writeBanner` in `TerminalPanel.tsx`.
- A changed scrollback setting applies to open terminals too, by a serialize, `reset()` and replay; running programs lose their terminal modes (see Traps).
- Find has no all-matches highlight.
- Under a program that owns the mouse, text selection is shift+drag or alt+drag on every platform.
- The WebGL renderer is gone; rendering is canvas 2D.

## Pty environment

`terminalEnv` in `internal/server/handler_terminal.go` starts every pty shell with `TERM=xterm-256color` and `COLORTERM=truecolor`. `TERM`, `COLORTERM`, `TERM_PROGRAM`, `TERM_PROGRAM_VERSION` and `GHOSTTY_*` inherited from a server launched inside Ghostty are dropped first, so the user's rc does not load Ghostty shell integration and ssh hosts without the `xterm-ghostty` terminfo entry keep working. Remote projects run the same code on the host.
