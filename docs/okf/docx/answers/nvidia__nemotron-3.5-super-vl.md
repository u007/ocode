# nvidia/nemotron-3.5-super-vl — closed-book answers for docx (openrouter, 2026-10-16); answerer saw only _prompts/docx.md
- id: docx-model-01
  answer: |
    A .docx is physically a ZIP package (Open Packaging Convention / OOXML): [Content_Types].xml, _rels/.rels, /word/document.xml, /word/styles.xml, /word/_rels/document.xml.rels, image parts under /word/media, and docProps. A table's data lives in word/document.xml inside <w:tbl>. The elements, table down to text, are: w:tbl → w:tblPr (tblW, tblBorders, tblLayout, tblLook, …) → w:tblGrid → w:gridCol (one per column) → w:tr → w:trPr → w:tc → w:tcPr (tcW, gridSpan, vMerge, shd, tcBorders, vAlign) → w:p → w:pPr → w:r → w:rPr (b, sz, color, rFonts) → w:t (the actual characters). Nested tables live inside a <w:tc>.
- id: docx-model-02
  answer: |
    Because no single run holds the whole string: "Widget C" is usually split across runs (e.g., "Widget " + "C"), or broken by <w:br/>, field characters (w:instrText / separate / end), a hyperlink, a nested table, or a text box, so run.text == "Widget C" never matches. cell.text concatenates every <w:t> in the cell but still does not locate run boundaries. Reliable fix: work at the XML level inside the <w:tc> — collect all <w:t> descendants, join their text, find the match across run boundaries, split the affected <w:t> nodes (or rebuild the runs) so the match is isolated, set its text, and leave surrounding runs/rPr intact. Do not rely on equality of a single run.text.
- id: docx-model-03
  answer: |
    Table/cell widths use twips (dxa, twentieths of a point): w:tblW/@w:w type="dxa", w:tcW/@w:w type="dxa", and w:tblGrid/w:gridCol/@w:w. 1440 twips = 1 inch; 20 twips = 1 point. Inline image sizes use DrawingML <wp:extent cx/cy> in EMUs: 914400 EMU = 1 inch; 12700 EMU = 1 point. Conversions: inches→twips ×1440; points→twips ×20; inches→EMU ×914400; points→EMU ×12700.

- id: docx-locate-02
  answer: |
    row.cells returns one _Cell per <w:tc> element in that <w:tr>. A cell spanning two columns is a single <w:tc> carrying <w:gridSpan w:val="2"/>, so row.cells returns ONE cell for the span, not two — len(row.cells) undercounts the real grid columns. Deleting row.cells[1] removes the wrong <w:tc> (the next logical cell), breaking the row's alignment with w:tblGrid/gridSpan and corrupting layout (misaligned columns or a Word repair prompt). Iterating row.cells to count columns is wrong with merges: count <w:gridCol> in w:tblGrid for the column count, and inspect tcPr/gridSpan per cell.
- id: docx-rowdel-01
  answer: |
    No — python-docx has no table.delete_row() or row.delete(). Remove the XML element directly: table._tbl.remove(row._tr) (equivalently row._tr.getparent().remove(row._tr)), then save. - id: docx-rowdel-02
  answer: |
    Just removing the restart row leaves the following cells' <w:vMerge/> ("continue") pointing at a merge origin that no longer exists, breaking the vertical-merge chain — Word may render the remaining cells merged with the wrong neighbor, split them unexpectedly, or flag the file as unreadable. Do it correctly by deleting every row in the merged group together, or if deleting only the first row, after removal re-anchor the chain: change the next row's first cell from continue to restart (<w:vMerge w:val="restart"/> or remove vMerge if it becomes a standalone cell), fix any text/row heights, then reopen and validate.
- id: docx-rowdel-03
  answer: |
    It still shows the stale cached sum, including the deleted row, because Word stores the field's last result in the XML and does not recalculate { =SUM(ABOVE) } when you edit; it recomputes only on update (F9, print, a macro, or <w:updateFields/> in settings.xml). Handle it by recomputing the sum in Python and writing the new cached result into the field's result runs, or by forcing recalculation (<w:updateFields/> so Word refreshes on open, or driving Word via a macro/F9 after saving). Do both and verify the displayed total.
- id: docx-rowdel-04
  answer: |
    It is not a deletion: the <w:tr>/<w:tc> elements remain in document.xml, so the row still counts, still participates in layout/pagination and merges, and hidden or white text is still extractable and searchable; zero exact height only hides it visually (borders/shading can still show). Prove it is really gone by confirming the specific <w:tr> element is absent from document.xml (len(table.rows) decreased by one with shifted indexes), the row's text is absent from all <w:t> in the package, the file opens without repair, and a before/after XML diff shows the row element removed — not merely formatted invisible.
- id: docx-cell-01
  answer: |
    Cell-level formatting survives (<w:tcPr>: shading w:shd fill, borders, width tcW, vMerge, vertical alignment, cell margins) and the table style/borders survive, because cell.text replacement does not touch <w:tcPr>. What is lost is all run/character formatting — bold, 9 pt size, white color, font (<w:rPr> on the old runs) — plus any extra paragraphs and their alignment, since cell.text = "SKU" clears the cell and writes one new paragraph with one default-formatted run. To preserve formatting, edit in place (set an existing run's .text), or copy the old w:rPr onto the new run, or rewrite only the <w:t> nodes.
- id: docx-cell-02
  answer: |
    That row's line total must be recomputed (Qty × Unit Price, so 5 → 12 changes it), and the grand Total field { =SUM(ABOVE) } changes too, plus any subtotal/tax cells. Make it consistent by changing the Qty cell text in place, computing the new row total = 12 × unit price and writing it to the line-total cell in the same number format, then refreshing the Total field — write the new cached field result or force recalculation (<w:updateFields/> / F9 / macro). Edit run-by-run to keep formatting, and verify Qty × Price = line total and the sum of line totals equals Total.
- id: docx-cell-03
  answer: |
    python-docx cannot create Word tracked revisions, so rewriting <w:t> text is a silent edit: even with w:trackRevisions on, Word records no revision (no w:ins/w:del, no author/date, no reviewing-pane markup) — it just becomes an ordinary accepted-looking change. Decide whether you want a true tracked revision (then insert w:ins/w:del around runs with w:author, w:date, w:id via raw XML, or toggle w:trackRevisions off / accept revisions first) or whether a clean silent edit is acceptable. Beware the change will not appear in review panes and may violate audit expectations; tracked edits require direct XML manipulation, not python-docx's text API.
- id: docx-relayout-01
  answer: |
    table.add_row() appends a new row at the END of the table (a <w:tr> after the last row) with default empty cells — it does not insert after a specific row and does not copy formatting. To insert after "Service G" and before Total, locate that row, deep-copy a neighboring line-item <w:tr> (preserving trPr, tcPr widths/borders/shading, fonts), insert the clone immediately after the Service G row with row._tr.addnext(clone), then clear the clone's cell texts and fill the new values. Columns/grid are unchanged by adding a row, so w:tblGrid stays the same; then refresh the Total field because SUM(ABOVE) now covers one more row.
- id: docx-relayout-02
  answer: |
    table.add_column(width) appends a new column at the RIGHT END of every row (one w:gridCol and one w:tc per row) — it does NOT insert after the Item column. To add SKU after Item, insert a new w:gridCol after Item's gridCol in w:tblGrid, and insert a new w:tc after the Item cell in every row (handle the header row and any gridSpan/vMerge cells), putting "SKU" in the header cell. To stay inside the page margins, adding a column widens the table, so set fixed layout (<w:tblLayout w:type="fixed"/>), set w:tblW (type="dxa") to page width minus margins so the gridCol sum matches, narrow other columns (e.g., Item) accordingly, set each new cell's tcW to match its gridCol, copy borders/shading/margins from the Item column, and turn autofit off.
- id: docx-relayout-03
  answer: |
    Word ignores w:tblGrid when the table is autofit (<w:tblLayout w:type="autofit"/>) or when cell-level w:tcW values disagree or are missing, and it also honors w:tblW and often sizes from the first row's tcW/content, so edited gridCols can be overwritten. Fix it by setting fixed layout, setting w:tblW (type="dxa") to the sum of the gridCol widths, and writing matching w:tcW (type="dxa") into EVERY cell of that column across all rows — not just gridCol — with no conflicting tblW="auto". Then reopen/regenerate layout so Word recalculates.
- id: docx-tblins-01
  answer: |
    doc.add_table(rows, cols) appends the table at the END of the document body — not after "Notes:". To place it right after the "Notes:" paragraph, find that <w:p> and insert the table element immediately after it: notes_paragraph._p.addnext(table._tbl), moving/building the <w:tbl> there instead of leaving it at the tail. Optionally add an empty paragraph after so following content is not absorbed; the table then sits between Notes and the next block.
- id: docx-tblins-02
  answer: |
    KeyError because "Grid Table 4 Accent 1" is a built-in/latent table style not actually declared in the template's styles.xml; python-docx resolves table.style through doc.styles, and many built-in table styles are absent. Get a ruled table by using a style that exists in the template (commonly "Table Grid") or by applying borders directly — add <w:tblBorders> (top/left/bottom/right/insideH/insideV with sz/color/space) to the table's w:tblPr instead of relying on a named style. - id: docx-tblins-03
  answer: |
    By default it has no fixed size: w:tblW is type="auto" and the layout is autofit, so Word sizes it from content/page width rather than a set inch measurement — columns are not fixed to a known width. To match the existing invoice table, read the invoice table's w:tblW (type="dxa" value), <w:tblLayout w:type="fixed"/>, every <w:gridCol w:w="…"/>, and each cell's w:tcW, then apply the same tblW, fixed layout, identical gridCol widths, and matching tcW on all cells of the new table; also copy style, borders, shading, and cell margins so it looks identical.
- id: docx-imgrep-01
  answer: |
    A picture is referenced indirectly: document.xml has <w:drawing> → <wp:inline>/<wp:anchor> → <a:blip r:embed="rIdN">, and document.xml.rels maps rIdN to a package part like /word/media/imageN.png holding the bytes. Position/size live in wp:anchor/wp:inline (extent cx/cy in EMUs, alignment/offsets). To replace ONE logo keeping position/size, locate that specific drawing (by alt text <wp:descr>/<a:title>, position, or unique rId), add the new image as a new package part plus a new relationship in document.xml.rels (new rId), then change only that drawing's <a:blip r:embed> to the new rId. Leave wp:extent and anchoring untouched; drop the old part only if nothing else references its rId (other pictures sharing the old rId keep the old image, which is correct for "one picture").
- id: docx-imgrep-02
  answer: |
    Because both pictures reference the SAME image part/relationship (same r:embed → same /word/media/imageN.png); image parts are shared across the document. Overwriting image_part._blob mutates the shared part, so every drawing using that rId — including the page 3 picture — shows the new bytes. - id: docx-imgrep-03
  answer: |
    It is in a header part (/word/headerN.xml) that repeats on every page — doc.inline_shapes covers only the body, and headers may be linked to previous (is_linked_to_previous) or differ for first page/odd-even. Find it by iterating doc.sections and each section's header/footer parts (header, first_page_header, even_page_header, following links to the real part), parsing each part's XML for <w:drawing>/<a:blip r:embed>, and matching the logo by position (top-anchored wp:anchor), size, or <wp:descr>/<a:title> alt text. - id: docx-imgins-01
  answer: |
    doc.add_picture() appends an inline image at the END of the document (in its own paragraph at the tail of the body) — not after "Approved by:". Place it correctly by finding the "Approved by:" <w:p>, inserting a new paragraph/run right after it (p._p.addnext(...)), and putting the picture there via run.add_picture("signature.png", width=Inches(1.5)) — passing only width lets python-docx compute height from the image's intrinsic aspect ratio, preserving it; equivalently add the picture at the end then move its paragraph: approved_paragraph._p.addnext(picture_paragraph._p). Keep it inline (wp:inline) so it flows with the text, and do not also set height or the aspect ratio breaks.
- id: docx-imgins-02
  answer: |
    The image will not shrink to fit: a 3-inch image in a 1.2-inch cell overflows the cell — Word may widen the column/table, or the drawing extends past cell borders/clips — since the cell width (tcW/gridCol) stays 1.2 inches. Size it to fit: limit width to the usable cell width (1.2 in minus left/right cell margins, roughly 1.0–1.1 in) and compute height from aspect ratio (run.add_picture(width=Inches(1.0))), set fixed table layout so columns do not auto-grow, or alternatively widen the cell/reduce cell margins. Always set tcW/gridCol deliberately instead of letting Word rescale.

- id: docx-verify-01
  answer: |
    Back up the original first (copy to .bak/timestamped copy; never edit the only copy). Edit a copy and save to a NEW file, then reopen it with python-docx to confirm it parses; verify structure (tables/rows/cells counts, the edited cell text, merges still valid, SUM field present) and that document.xml is well-formed XML; open the result in Word/LibreOffice and confirm no "unreadable content" repair and that values/total look right (update fields/F9 if needed); keep both files and compare checksums/diffs before replacing the original.
- id: docx-verify-02
  answer: |
    Common causes: (1) rows whose <w:tc> count no longer matches w:tblGrid/w:gridCol (cells added/removed without updating the grid); (2) gridSpan/tcW mismatches or cells whose tcW disagrees with gridCol; (3) wrong child order inside w:tblPr / w:trPr / w:tcPr (the schema requires a fixed sequence — e.g., tblW/jc/borders/layout/look order in tblPr; tcW near the end of tcPr); (4) missing required attributes (w:w with w:type="dxa" on tblW/tcW/gridCol); (5) a <w:tr> with no cells or an empty <w:tbl>; (6) broken vMerge/hMerge chains after deletions; (7) dangling or duplicate relationships/rIds. python-docx/lxml keeps XML well-formed, so the failure is usually semantic (schema/grid), which python-docx will not catch but Word will.
- id: docx-verify-03
  answer: |
