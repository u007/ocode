- id: tanstack-query-keys-01
  answer: |
    A query key is the serializable descriptor (top-level array, e.g. ['todos', 5, { status: 'done' }]) that uniquely identifies the cached data produced by a queryFn. The client decides two calls share one cache entry by hashing the key deterministically: TanStack Query runs its `hashKey` (a stable, recursive JSON-style stringify that sorts object keys) and compares the resulting hash strings. So key equality is deep equality over the serialized array — array order matters, but object property order does not. Keys must therefore be JSON-serializable (top level must be an array; functions/class instances break hashing).
- id: tanstack-query-keys-02
  answer: |
    Hierarchical keys enable prefix matching: by default, invalidation (and filters like cancelQueries / setQueriesData / removeQueries) matches any key that *starts with* the given segments — invalidateQueries(['todos']) hits ['todos'], ['todos', 5], ['todos', { page: 2 }] (fuzzy/partial match; `exact: true` disables it). That means one parent invalidation invalidates a whole family of entries without enumerating ids, and children can be invalidated independently. The convention is broad → narrow: entity first, then id, then sub-resource, then filters, so grouping, invalidation, and bulk updates target the right set of entries.
- id: tanstack-query-keys-03
  answer: |
    The key omits a variable the queryFn depends on, so the key identity never changes when userId changes: every consumer of ['projects'] shares one cache entry and the queryFn is never re-run for a different user. Concretely, the first userId's response poisons the entry — a second component with a different userId renders the first user's data from cache (wrong/foreign data), and switching users shows no refetch. The rule: every variable the queryFn closes over (ids, params, filters, pagination, user-scoped tokens) must be serialized into the key — variables drive the fetch, the key must reflect the variables.
- id: tanstack-query-keys-04
  answer: |
    Exactly one network request. Both mounts resolve to the same cache entry; the first observer's queryFn starts the fetch, and the second observer finds an in-flight fetch for that identical key and subscribes to it instead of starting its own (concurrent fetch deduplication). Both components then render from the one shared cache entry and update together when the single fetch resolves.
- id: tanstack-caching-01
  answer: |
    staleTime is freshness duration: after a successful fetch, data is considered fresh for staleTime and will NOT be refetched by automatic triggers (mount, window focus, reconnect) — default is 0, meaning immediately stale. gcTime (renamed from cacheTime in v5) is memory lifetime: how long *inactive* data (no observers/subscribers, after the last component unmounts) is retained before garbage collection — default 5 minutes. One governs refetching behavior, the other how long unused data sticks around; raising staleTime cuts refetch traffic, gcTime only decides whether a remount finds data at all, and gcTime: 0 drops data the instant the last observer leaves.
- id: tanstack-caching-02
  answer: |
    The entry is still in cache (assuming gcTime hasn't elapsed), so the component renders immediately with the previously fetched data — no loading spinner. But because staleTime is 0 that data is already stale, so the remount triggers a background refetch (default refetchOnMount: true). User-visible behavior: the old content appears instantly, then updates a moment later when the refetch resolves; an indicator tied to isFetching would show the background refresh. If gcTime already expired while unmounted, the data is gone and the user sees a full loading state again.
- id: tanstack-invalidation-01
  answer: |
    It finds every cached query whose key prefix-matches ['todos'] (fuzzy by default; exact: true restricts to only that key), marks them as stale, and refetches the ones that are currently active (mounted) — the default refetchType: 'active'; inactive matches are only marked stale and refetch on next mount. It also cancels in-flight refetches for those queries and starts fresh ones (cancelRefetch default true). It returns a promise that resolves when the triggered refetches settle, so you can await it (e.g. with invalidate({ queryKey }) inside onSuccess/after a mutation).
- id: tanstack-invalidation-02
  answer: |
    Use setQueryData when you already know the exact new server state — typically the mutation response returns the updated entity or list you can write straight into the cache. It updates the UI instantly with zero network round trip and no refetch flash. The tradeoff: the write is your client's belief, so it drifts from the server whenever other fields, derived rows, or counts changed server-side that your payload didn't cover; invalidateQueries is authoritative (server truth) but costs a request and returns slightly later. A common split: setQueryData for the single entity the mutation returned, invalidateQueries for dependent queries (lists, counts, filters) you can't compute exactly.
- id: tanstack-mutations-01
  answer: |
    useQuery models declarative, cached reads: keyed, deduped, auto-refetched on mount/focus, shared across components, with retries. useMutation models one imperative write — no cache entry, no key, no sharing; it runs only when you trigger it, and its state (isPending, error, data) is local to that hook instance. You trigger with mutate(variables) (v5 takes the variables directly; v4 wrapped them as mutate({ variables })) and track via status: 'idle' | 'pending' | 'success' | 'error' — v5 renamed 'loading' to 'pending', so use isPending, not isLoading. Lifecycle hooks: onMutate, onSuccess, onError, onSettled.
- id: tanstack-mutations-02
  answer: |
    The write changed server state, so every cached read derived from it — list queries, detail queries, counts, filtered variants — is now stale. Calling queryClient.invalidateQueries in onSuccess marks the matching keys stale and triggers refetches of the active ones, reconciling the client cache with the server. Without it, the UI keeps serving pre-mutation data until staleTime expiry, a focus refetch, or a remount. Do it in onSuccess (not after the mutate call) so invalidation only happens if the server actually accepted the write.
- id: tanstack-mutations-03
  answer: |
    onMutate (runs before the mutationFn, with access to variables): cancel in-flight refetches for the affected key so they can't clobber your optimistic write (queryClient.cancelQueries), snapshot the current data for rollback, write the optimistic value with setQueryData, and return the snapshot as context. onError(variables, error, context): restore the snapshot — setQueryData(key, context.previous) — rolling the UI back to pre-mutation state. onSettled: reconcile with the server regardless of outcome — cancel outstanding refetches then invalidateQueries for the key so the fresh server value wins (also the step that runs on success). Key detail: the snapshot must come from and go back to the same key, and the context chain (onMutate → onError/onSuccess/onSettled) is what carries the rollback data.
- id: tanstack-mutations-04
  answer: |
    mutate is fire-and-forget: it swallows the internal rejection (effectively .catch(noop)), so it never produces an unhandled rejection — failures surface only through onError, error, isError, and status === 'error'. mutateAsync returns the promise, putting ownership on the caller: you must await it inside try/catch (or .catch), otherwise a failed mutation becomes an unhandled rejection. That is exactly why both exist. A mutation knows it failed through onError / status becoming 'error' / the error field; with mutateAsync it's the rejected promise you catch.
- id: tanstack-query-fn-01
  answer: |
    fetch only rejects on network-level failures; a 500 response is a *resolved* Response with ok === false. A queryFn that just does `return res.json()` therefore returns successfully with the error body, and the query enters the success state with the error payload as data — no error state ever renders. The failure contract is: the queryFn must throw or return a rejected Promise; returning an error object or a resolved non-ok Response counts as success. The fix is to enforce it inside the queryFn: `if (!res.ok) throw new Error(...)` (optionally parsing the body for the message), which puts the query into the error state after retries are exhausted.
- id: tanstack-query-fn-02
  answer: |
    A queryFn is a fetch supplier, not a render scope: it can run any number of times (deduplication, retry after failure, stale refetch, remount after gc, background prefetch) and frequently when no component that asked for the data is mounted. Calling setState from inside it targets components that may be unmounted (leaked updates / warnings), double-applies effects on retries, and couples cache mechanics to view state. Do the fetching only in the queryFn; handle reactions through query options (onSuccess/onError), derived data via select or the returned data itself, and component lifecycle code (effects, events).
- id: tanstack-query-fn-03
  answer: |
    Gate it with enabled: `enabled: userId !== undefined` (or `!!userId`). While the dependency is missing the query is disabled: in v5 that's status 'pending' with fetchStatus 'idle' — no request fires, data stays undefined, and isLoading stays false (v4: status 'loading' with isInitialLoading false). The moment userId resolves, enabled flips true and the query automatically fetches; placeholderData or keepPreviousData can supply interim content meanwhile.
- id: tanstack-suspense-01
  answer: |
    useSuspenseQuery never exposes a pending or error branch: data is typed TData (not TData | undefined), and there is no isPending/isLoading/isError to render — instead the component *suspends* on first load, so an ancestor <Suspense fallback> is required, and errors require a companion <ErrorBoundary>. It also assumes the query is always enabled (no disabled/loading state exists to render). Smaller things (select, staleTime, refetchInterval, meta) work as usual, and the component reads plain data with no optional chaining.
- id: tanstack-suspense-02
  answer: |
    There is no isError branch — the error thrown by the queryFn propagates during render to the nearest React <ErrorBoundary>. Pair them explicitly: <Suspense fallback> owns the loading state, <ErrorBoundary> owns the failure state, both wrap the suspending component. Precondition: the queryFn must still throw on a bad response (check res.ok) — if it resolves with the 500 body instead, the boundary never fires and the error payload renders as ordinary data. For retry, use useQueryErrorResetBoundary / resetErrorBoundary so the boundary doesn't immediately re-throw before the refetch state settles; throwOnError: false is the opt-out if you'd rather render the error yourself.
- id: tanstack-suspense-03
  answer: |
    Each sibling suspends on its own first fetch. React renders siblings in order: if the first one suspends with no local boundary, React unwinds to the nearest boundary above both and stops — the second sibling never renders, so its fetch doesn't even start until the first promise resolves. That's a serial waterfall (fetch A resolves, then fetch B starts). Avoid it by starting both fetches before the children render: prefetch them in a router loader, beforeLoad, or a parent (queryClient.prefetchQuery / ensureQueryData) so the cache is warm when the children suspend — or wrap each child in its own Suspense boundary so both kick off in the same render pass instead of queueing.
- id: tanstack-suspense-04
  answer: |
    No. A suspense query must be able to resolve — it has no 'disabled' status to render — so enabled: false leaves it pending forever and the component suspends indefinitely (the fallback never gives way to content). Express the dependency by ordering instead: fetch the prerequisite first (router loader, beforeLoad, or a parent/ancestor useSuspenseQuery) and only render the second, dependent useSuspenseQuery once the dependency value exists — or prefetch the dependent query as soon as the parent's data arrives, keyed by that data. (useQuery's disabled/enabled option and skipToken are the non-suspense answer.)
- id: tanstack-prefetch-01
  answer: |
    Prefer ensureQueryData when you want the data itself: it returns the cached data when the cache can already satisfy the query (no refetch), otherwise fetches and resolves with the data — and it propagates a failed fetch's rejection. prefetchQuery is fire-and-forget warming: it returns void and swallows errors (the error just lands in the cache for the real observer to surface). Either one guarantees the cache is populated before the component renders if you await it in the loader; ensureQueryData is the safer loader primitive because it both returns data and lets failures propagate to route error handling.
- id: tanstack-prefetch-02
  answer: |
    Both warm the cache key, but fetchQuery returns the data and rejects on failure (after retries), while prefetchQuery returns void and never rejects. That error contrast matters when the caller must react to failure — in a router loader, a fetchQuery rejection throws and renders the route's errorComponent / feeds your ErrorBoundary; with prefetchQuery the failure is silent and only shows up when the user navigates and the component's useQuery/useSuspenseQuery observes the errored entry. So use fetchQuery (or ensureQueryData) where errors must propagate, prefetchQuery where a silent, "nice-to-have" warm-up (hover preload) is fine.
- id: tanstack-router-loaders-01
  answer: |
    A route loader is an async function that runs during navigation, before the route's component renders (and during preload). It receives an object with params, deps, context, location, abortController, cause, preload, route and navigate, and it may return data (which is cached and delivered to the component) or throw/redirect (routing to the errorComponent). The component reads it with const data = Route.useLoaderData(), typed from the loader's return type. Unlike a useEffect fetch, the loader runs before first paint (no loading flash, no mount-then-fetch waterfall for nested routes), the router awaits and can stream it (pendingComponent/errorComponent), it's cancellable via abortController when navigation changes, and matched routes' loaders can run in parallel.
- id: tanstack-router-loaders-02
  answer: |
    Use one shared QueryClient (put it on the router via the context option / createRootRouteWithContext<{ queryClient: QueryClient }>, plus the usual QueryClientProvider for components), then have the loader call `queryClient.ensureQueryData({ queryKey, queryFn })` (or fetchQuery) with the *same* key the component will use. The component's useQuery / useSuspenseQuery then mounts to an already-cached entry and doesn't refetch — one cache, one request. Two caveats: set a staleTime so the preloaded data counts as fresh on first mount (default staleTime 0 makes the immediately-mounted useQuery refetch in the background anyway), and ideally thread the loader's abortController.signal into the query's abortSignal so abandoning navigation cancels the fetch.
- id: tanstack-router-loaders-03
  answer: |
    Preloading starts the navigation machinery before a click — Link's default preload="intent" does it on hover/focus. It matches the target route and runs its beforeLoad and loader functions (they receive preload: true in their args, so you can branch off expensive work), warming loader data and context — but no component code renders. The payoff: after the click, data is already there so navigation feels instant. The cost: hovering can fire requests that are never used, which is what the preload flag is for.
- id: tanstack-router-loaders-04
  answer: |
    beforeLoad is the route-level gate that runs *before* the loader (outermost matched route first, sequentially): use it for auth checks, redirects (throw redirect(...)), and context shaping — whatever it returns is merged into the context handed to the loader and to deeper routes' beforeLoad. The loader is the data-fetching step that runs after all matched beforeLoads complete. Router context is a dependency-injection container created via the router's context option (typed by createRootRouteWithContext<Ctx>() on routes): anything route functions need — queryClient, auth services, API clients, SSR request info.
- id: tanstack-router-search-01
  answer: |
    Define validateSearch on the file route (a hand-written parser, or a zod schema via the Zod validator adapter). It runs on navigation and on useSearch, turning the raw, untrusted query-string object into a typed object: Route.useSearch(), <Link search={...}>, and loaderDeps all see the parsed result. Validate because: incoming URLs are untrusted (validation throws rather than rendering garbage), values arrive as strings and must be coerced (page: number), missing params get defaults, and you get one authoritative, typed shape that flows through every search-aware API.
- id: tanstack-router-search-02
  answer: |
    Store it in the URL: read with Route.useSearch(), write with navigate({ search: (prev) => ({ ...prev, page: page + 1 }) }) or <Link search={{ page: 2 }} /> (replace: true for filter tweaks so the back button isn't polluted by every keystroke). URL state is shareable, bookmarkable, survives reload, and integrates with back/forward. The anti-pattern is keeping pagination/filters in useState or an external store while the URL stays static — state is lost on reload, links can't carry it, and history breaks.
- id: tanstack-router-search-03
  answer: |
    Because by default a loader is keyed and re-runs on path params only — search params are not loader dependencies at all. validateSearch merely parses the query string into typed values for useSearch/Link/navigate; it does not feed the loader, and the loader argument has no search field (it has params, deps, context, location, abortController, cause, preload, route, navigate). Add `loaderDeps: ({ search }) => ({ page: search.page })` — the returned object becomes the loader's deps argument *and* part of its cache identity, so the loader receives deps.page and refetches when page changes. Reading location.search directly gives you the value but with no reload tracking.
- id: tanstack-router-search-04
  answer: |
    validateSearch's return type becomes that route's search type, enforced across APIs: <Link to="/posts" search={{ page: 2 }} /> errors at compile time on a missing required param, a wrong type (string where your schema says number), or an unknown key; navigate({ to, search }), Route.useSearch(), and loaderDeps are all typed from the same shape; child routes inherit/merge parent route search types. And because it's a runtime validator, it also catches params for hand-typed URLs — defense at compile time and at runtime.
- id: tanstack-router-typesafety-01
  answer: |
    The TanStack Router Vite plugin (or router-cli) scans your routes/ directory and *generates* routeTree.gen.ts — a typed tree where file names become routes ($postId → params: { postId: string }, _layout / pathless-layout files → nesting, __root → root). createRouter({ routeTree }) consumes that generated tree, and every downstream type — router.navigate, <Link to params search>, useParams, useSearch, useLoaderData — is inferred from it, end to end. The file is generated output: don't hand-edit it; it rewrites as you add or rename route files.
- id: tanstack-router-typesafety-02
  answer: |
    Against the route generated from posts.$postId.tsx, TypeScript checks that: the `to` path exists in the route tree; params contains exactly the params the route declares — a postId name is required (a typo like postID or a stray key is an excess/missing-property error); required params are present; and the value type matches — params arrive as strings, so '5' is correct and a numeric 5 is a type error. The same machinery validates `search` props against validateSearch's output type and rejects links to unknown routes.
