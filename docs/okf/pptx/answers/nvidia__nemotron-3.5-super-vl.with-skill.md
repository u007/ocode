- id: pptx-model-01
  answer: |
    A table sits in a p:graphicFrame on the slide as DrawingML <a:tbl>. Inside <a:tbl>: <a:tblPr> holds table properties (firstRow/bandRow flags and the <a:tableStyleId> GUID), <a:tblGrid> holds one <a:gridCol w="..."/> per column defining column widths, then one <a:tr> per row (height in @h). Each <a:tr> contains one <a:tc> per column, including covered (merged) cells, which are real elements and never omitted. Each <a:tc> has <a:tcPr> (properties/fill/merge attributes) and <a:txBody> with <a:bodyPr>, <a:lstStyle>, paragraphs <a:p>, runs <a:r>, text <a:t> and run properties <a:rPr>. python-pptx maps this to graphicFrame.table -> table.rows/columns/cell(r,c) -> cell.text_frame.
- id: pptx-model-02
  answer: |
    python-pptx / DrawingML uses EMU (English Metric Units): 914400 EMU per inch, 12700 EMU per point; positions and sizes are EMU ints/Length values. The default python-pptx template is 4:3: 9144000 x 6858000 EMU (10 x 7.5 in). A typical 16:9 deck is 12192000 x 6858000 EMU (13.333 x 7.5 in), but a deck can be any size - always read prs.slide_width and prs.slide_height instead of assuming 16:9.
- id: pptx-model-03

- id: pptx-rowdel-03
  answer: |
    It depends on how the deck shades rows. If banding comes from the table style (tblPr bandRow="1" with a tableStyleId and no explicit fills), PowerPoint recomputes the alternation, so deletion is safe. If rows carry explicit <a:tcPr><a:solidFill> colours, deleting a middle row leaves the surviving cells' fills unchanged, so two neighbours can end up the same colour and the alternation breaks - that is why it happens in one deck (explicit solidFill shading) and not another (style bandRow). The fix is the second half: walk body rows after the gap and re-assign alternating fills (copying the solidFill of the two reference rows), or remove the explicit fills and set bandRow="1" so the style banding recomputes.
- id: pptx-rowdel-04
  answer: |
    It is masking, not deletion. The row still exists in the XML (<a:tr> with cells, text and values), so the data remains extractable, the row still counts in the table model (heights, totals, banding, accessibility), screen readers and other consumers still see it, and a near-zero height or white box is fragile and can break or reappear when the layout changes. It also leaves Totals and banding inconsistent. Correct removal deletes the <a:tr> element and fixes height, fills and Totals properly.

- id: pptx-imgrep-03
  answer: |
    drop_rel removes the rel when its reference count < 2, but the count is an xpath for //@r:id. A picture references its image via <a:blip r:embed>, and r:embed is not an r:id attribute, so the library never sees picture users - an image rel always counts 0 and is always dropped, even when another p:pic on the slide still embeds it. Before dropping, scan slide._element.xpath("//@r:embed | //@r:link"), count users of that rId, and drop only if no other user exists; otherwise repoint survivors to a new part first or leave the rel.

- id: pptx-verify-02
  answer: |
    Common causes: per-row <a:tc> count not equal to <a:tblGrid> <a:gridCol> count (especially after merge edits - forgot to add/remove the covered cell when changing gridSpan/rowSpan); wrong element/attribute names (<a:textBody> instead of <a:txBody>, <a:tblStyleId> instead of <a:tableStyleId>, colSpan instead of gridSpan, span attributes on <a:tcPr>); wrong child-element order / missing required schema sequence in tblPr/tblGrid/tr/tc; bad or duplicate relationship IDs, dangling r:embed/r:link to missing parts, missing content types; invalid ext/transform values; a corrupt zip. python-pptx tolerates XML that PowerPoint rejects, so script-edited files often fail in PowerPoint.
