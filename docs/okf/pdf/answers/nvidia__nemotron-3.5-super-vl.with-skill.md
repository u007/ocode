- id: pdf-model-01
  answer: |
    A PDF does not contain a "table" object. It contains independent, absolutely positioned primitives: text glyphs at coordinates, vector lines/rects/fills for rules and shading, and possibly images — with no row/cell structure and no relationship tying a cell to its neighbors. Therefore there is no "delete row" operation. The edit must remove the row's glyphs and drawing operators, then close the gap by shifting everything below up (re-stamping via show_pdf_page or redrawing), and recompute/rewrite any Total that depends on the removed row.
- id: pdf-model-02
  answer: |
    A white fill only paints over the text; the original glyphs remain in the content stream and are still extractable and selectable (get_text still finds them), so it is a cover-up, not an edit. Use real removal: add_redact_annot over the glyph area, then page.apply_redactions() to delete the text (and, by default, covered line art/image pixels), then insert the new text/image. For images use replace_image for all occurrences of a shared xref, or redact+insert_image for a single occurrence.
- id: pdf-model-03
  answer: |
    The content stream is usually compressed (FlateDecode), so a raw byte search finds nothing until you decompress — and you must then recompress and fix /Length. Text may use a custom encoding/CID/glyph IDs so the byte sequence of "22.50" need not appear; a string can be split across several Tj/TJ operators with interleaved positioning/kerning numbers; operators carry explicit string/array lengths that a different-length replacement breaks; and text may be drawn as outlines (curves), not as text at all. Any of these makes a blind byte replace silently fail or corrupt the page; use PyMuPDF's text extraction/replacement instead.
- id: pdf-model-04
  answer: |
    PyMuPDF uses a top-left origin, y down, with (0,0) at the CropBox's top-left; raw PDF content-stream coordinates use a bottom-left MediaBox origin, y up. Convert between them with page.transformation_matrix (raw → PyMuPDF) and its inverse ~page.transformation_matrix (PyMuPDF → raw). On a /Rotate 90/270 page, page.rect reports the displayed size with width/height swapped, but get_text bboxes and all insert/draw rects stay in the unrotated page coordinate system. Anchor new content to extracted bboxes in the unrotated frame, converting to displayed coordinates with rect * page.rotation_matrix (back with derotation_matrix); do not lay out from page.rect.width/height on rotated pages.
- id: pdf-locate-01
  answer: |
    PyMuPDF has no table object or built-in table detector. Reconstruct it: page.get_drawings() returns each line/rect/fill with a .rect (rules, cell borders, shading); page.get_text("dict"/"words") returns text with bboxes. Cluster horizontal rule y-positions into row separators and vertical rule x-positions into column separators; a cell's bbox is the rectangle between adjacent horizontal and vertical rules, and the text inside it is found by matching spans whose bboxes fall within that cell. Images come from page.get_image_rects()/get_image_info(). There is no direct API for "row n, cell m."
- id: pdf-locate-02
  answer: |
    page.search_for("Widget C") returns only the bbox of that text's glyphs — not the cell padding, borders, shading, the other cells in the row, or the row's full height. Removing just that rect leaves the rest of the row behind. To get the full row region, extend vertically using the horizontal rules above/below the row (from page.get_drawings) or the line's text height plus cell padding, and horizontally using the vertical rules / column boundaries that contain that text. Build one redaction rect spanning the whole row (all cells) from those boundaries, then redact.
- id: pdf-locate-03
  answer: |
    Use page.get_text("dict") (or "rawdict"): blocks → lines → spans. Each span carries "font" (base/subset name), "size", "color" (integer RGB), "origin" (the baseline start point in PyMuPDF coords), and "bbox"; span["chars"] gives per-character origins/bboxes. The span origin is the text baseline; size and color come directly; the font name (possibly with a subset prefix like "AAAAAA+") identifies the family/weight. Read the target cell's span and reuse those values for the replacement.
- id: pdf-locate-04
  answer: |
    Column boundaries come from the vertical rules in page.get_drawings() — cluster the distinct x positions of line/rect edges (also shading rect edges). For right-aligned numbers, each number's span bbox (get_text "words"/"dict") gives x1 = where the text ends; right alignment means x1 sits at the column's right border minus padding, so the right-edge x for a column is the consistent x1 of its number spans (≈ right rule x − padding). Combine the vertical rule x's with measured text x1's to know both the boundaries and where values line up.
- id: pdf-rowdel-01
  answer: |
    1) Locate the row: find its text and y extent from horizontal rules/text; get row height h and full-width row rect R, plus the region below that must move up (from just under R to the table bottom). 2) Open an untouched copy src = fitz.open(path). 3) On the working page add redaction annotations covering R and apply_redactions() — defaults remove the row's text, shading fill and rules. 4) Restamp the below-row region up one row height: page.show_pdf_page(new_rect, src, pno, clip=old_rect), where old_rect is the below-row region and new_rect is it shifted up by h. 5) Redraw the new bottom edge rule, redo striping, recompute Total/subtotal/tax from remaining rows and insert the new Total one row lower (don't patch the old figure). 6) Move content below the table up by h the same way (or deliberately leave the gap and tell the user). Verify by re-extracting and rendering.
- id: pdf-rowdel-02
  answer: |
    Defaults: images=PDF_REDACT_IMAGE_PIXELS (2) blanks image pixels under the rect; graphics=PDF_REDACT_LINE_ART_REMOVE_IF_COVERED (1) removes every line/fill lying inside the rect; text=PDF_REDACT_TEXT_REMOVE (0) removes characters whose bbox overlaps. So a full-row redaction already deletes the row's shading rect and internal rules — no extra flag is needed to remove a whole row. It matters because if you only want to change one cell's text while keeping its borders and shading, the defaults would destroy the cell frame; then you must pass graphics=0 (PDF_REDACT_LINE_ART_NONE) and images=0 so only the text is removed.

- id: pdf-cell-02
  answer: |
    Make the rect just large enough to fully cover the glyphs (slightly beyond the text bbox to include descenders) but strictly inside the cell — not reaching the cell's border rules or shading, and not overlapping adjacent cells. Because removal is "characters whose bbox overlaps the rect" and default graphics removal deletes line art inside the rect, a too-large rect would delete parts of neighboring text and/or erase borders and shading you wanted to keep. If you do want the borders/shading gone too, let the rect extend to cover them.
- id: pdf-cell-03
  answer: |
    insert_textbox is all-or-nothing: if the text doesn't fit in the rect at the given font size it writes nothing, returns a negative number (the height shortfall), and raises no exception — it never writes a partial line. Options: check the return value; if negative, shrink the font and retry; make the rect taller so text wraps into more lines (but that grows the row and shifts rows below); widen the column/rect; use insert_htmlbox with scaling; or wrap manually and insert line by line with insert_text. Then shift/rebuild anything below if the row height changed.

- id: pdf-relayout-02
  answer: |
    Correct: pick new widths whose sum equals the same total width between the margins (take width from existing columns/padding, never widen beyond the margins). Measure every cell's text at its new width with get_text_length and per column decide to shrink the font slightly or wrap into a taller row. - id: pdf-imgrep-01
  answer: |
    Find the placement with page.get_image_info(xrefs=True) or page.get_image_rects(xref) to get the rect and xref. Then page.replace_image(xref, filename=new.png) swaps that shared XObject in place — every page drawing that xref shows the new PNG, and the placement rect is unchanged. - id: pdf-fonts-01
  answer: |
    An embedded subset font only contains glyphs for characters already used in the document. A new letter with no glyph in the subset has no code to map to, so reusing that font produces a missing/notdef glyph (blank or wrong character) — PyMuPDF may not raise. Fix: don't reuse the subset for new glyphs; load a real font that contains them (fitz.Font(fontfile) / doc.insert_font) and insert with that fontname/size, or embed a similar full font, or render the new text as outlines (loses selectability). Digits are usually present, but new letters are not guaranteed.
- id: pdf-fonts-02
  answer: |
    Built-in base-14 names: Helvetica regular = "helv", Helvetica bold = "hebo". Limitation: base-14 fonts are not embedded and rely on a viewer substitute, and they only cover the standard/Latin-1 encoding — they cannot reliably render non-Latin text (Cyrillic, CJK, Arabic) or special characters/emoji, which come out as blanks or wrong glyphs. For such text embed a real TTF/OTF font containing the glyphs.

- id: pdf-verify-04
  answer: |
    "done" only means no exception was raised. PyMuPDF fails silently in ways that still look correct: insert_textbox returns a negative number and writes nothing when text doesn't fit; a redaction rect can miss its target and remove nothing; wrong coordinates edit the wrong place; a wrong font yields missing glyphs without error; a restamped region can overlap existing content; an image can be drawn off-page or covered. You must inspect the actual output: re-extract text, confirm old/new values and positions, confirm recomputed totals, render and visually check, and verify no overlaps/gaps. Absence of errors is not evidence of correctness.
