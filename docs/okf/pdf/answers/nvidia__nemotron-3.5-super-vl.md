- id: pdf-model-01
  answer: |
    A PDF has no "table" object. A table is just absolutely positioned content-stream operations: text-showing operators (Tj/TJ) for cell text and line/rectangle/fill operators for rules and shading, each cell placed at explicit coordinates. There is no row object, no grid, and no semantic link between cells. So "delete the third row" means finding that row's text and rules (via words/drawings), removing or covering them, and then moving every element below the row up by the row height yourself — PDF is fixed-layout and nothing reflows automatically.
- id: pdf-model-02
  answer: |
    A white rectangle only hides the text visually; the original text-showing operators and glyph data remain in the content stream, so the text is still extractable, selectable, and recoverable, and can reappear if the rectangle is removed. That is a cover-up, not an edit. Use real redaction (PyMuPDF add_redact_annot + apply_redactions), which deletes the matching content from the stream (optionally images/vector graphics too), or edit the content stream directly to remove the text operators, then draw the replacement text.
- id: pdf-model-03
  answer: |
    Several reasons: (1) the stream is usually Flate-compressed, so the literal bytes "22.50" are not present until decompressed; (2) the string may be split across multiple Tj/TJ operands with spacing/positioning operators between glyphs, so it is not one contiguous byte run; (3) with a subset/custom encoding the stream bytes are glyph IDs/CMap codes, not literal ASCII; (4) the replacement changes string/stream length, so /Length, TJ position adjustments and offsets must be recalculated or the file is corrupted; (5) the "text" might actually be vector outlines or an image. - id: pdf-model-04
  answer: |
    PyMuPDF uses PDF user space with origin at the top-left, y increasing downward, in points relative to the page's CropBox (the visible page), so get_text("words") bboxes are top-left-origin crop-box coordinates. Raw PDF content-stream coordinates use bottom-left origin, y increasing upward, relative to the MediaBox. If /Rotate is set, PyMuPDF already presents the rotated view (page width/height swapped; text bboxes are in rotated space) — work with page.rect / derotation_matrix rather than raw stream coordinates. If CropBox is offset from MediaBox, PyMuPDF coordinates are relative to the CropBox origin, so you must translate by the crop offset and flip the y-axis to convert to raw content-stream coordinates.
- id: pdf-locate-01
  answer: |
    PDF has no native table, so PyMuPDF has no built-in "give me the table" API. Reconstruct it: get words with bboxes via page.get_text("words"), cluster rows by similar y (small tolerance) and columns by x alignment, and detect ruled boundaries from page.get_drawings() (horizontal/vertical line and rect items). Each row band is bounded by the horizontal rules around it; each cell is the intersection of a row band and a column band bounded by vertical rules, and cell text is the words whose bboxes fall inside. For a ready-made detector use pdfplumber (page.find_tables() -> .bbox/.rows/.cells); in pure PyMuPDF you build row/cell bboxes yourself from words + drawings.
- id: pdf-locate-02
  answer: |
    search_for("Widget C") returns only the bbox of the matched word itself — just that one cell's text, not the other cells, not the row's borders/shading, and not the full row width — so it cannot define the whole row to remove. Get the row region by taking the matched word's y-band (its y0-y1, extended to the horizontal rules above and below found in get_drawings, or to the cluster of words on the same line) and spanning the full table width (left to right table border, with a little padding). That full-width rect across that row band is the rectangle to redact/remove.
- id: pdf-locate-03
  answer: |
    Use page.get_text("dict") (or "rawdict"), which returns blocks -> lines -> spans. Each span carries "font", "size", "color" (integer 0xRRGGBB -> convert to 0-1), "origin" (the baseline start point, x and y), and "bbox". Find the span covering the target cell and read those fields; "origin" gives the baseline position. Reuse the same font name, size, color, and baseline y for the replacement text. For exact glyph metrics/ascent-descent use rawdict; note PyMuPDF y is top-left-origin, so baseline y is larger than the text top.
- id: pdf-locate-04
  answer: |
    Column boundaries come from the vertical ruled lines in page.get_drawings() (vertical line/rect items give x positions) and from the x alignment/clustering of cell text, cross-checked with cell left/right edges. The x where each right-aligned number ends is the right edge (x1) of that cell's number bbox from get_text("words")/span bbox — right-aligned numbers terminate at the column's right boundary minus padding. To line up new values, measure the new text width with fitz.get_text_length(text, fontname=..., fontsize=...) and place it so its right edge equals that same x1 (x = x1 - width). Use the existing right-aligned cells in the same column as the reference.
- id: pdf-rowdel-01
  answer: |
    1) Open the page and locate the target row (match its cell text; cluster words by y into that row band). 2) Determine the full row rect: table width x row height, bounded by the horizontal rules above and below (get_drawings) including shading and borders. 3) Remove the row content: add a redaction annot for that row rect and apply_redactions (choosing images/graphics options so rules/shading also go), or delete the row's content-stream operators. 4) Move the rows below up by the row height — PyMuPDF has no native "shift region up," so you must rewrite/shift the content below (translate text and drawing operators, or re-draw them at y - row_height); a plain redaction only leaves a gap. 5) Update the Total cell (redact old value, insert new total at the same baseline with matching style). 6) Save to a new file (full rewrite, not incremental if data must be gone) and verify by text + render.
- id: pdf-rowdel-02
  answer: |
    Default apply_redactions() treats images and vector graphics as NONE: only text whose bbox overlaps the rect is removed; images inside the rect are left intact and vector rules/fills are left in place unless you pass images=fitz.PDF_REDACT_IMAGE_PIXELS/REMOVE and graphics=...REMOVE. This matters for a table row/cell because redacting the text would leave behind the cell borders, horizontal rules and shading fills (vector graphics) and any logo image in the cell — producing a broken table with floating lines/shading and possibly still-recoverable confidential data. You must explicitly blank/remove images and graphics and pad the rect to cover the cell's borders.
- id: pdf-rowdel-03
  answer: |
    No. PyMuPDF cannot move an existing page region up while preserving its exact appearance — there is no "copy this rectangle up by delta h" operation. apply_redactions removes content but does not close the gap or shift content below. insert_text/insert_image only add new marks. - id: pdf-cell-01
  answer: |
    1) Open the page; find the old value ("22.50") with search_for or get_text("words") and confirm it is the right cell by row/column. 2) Read its style from get_text("dict") span: font, size, color, origin (baseline), and bbox; get the cell's right edge x1 (where the right-aligned number ends). 3) Remove the old text: add a tight redaction rect around just that word and apply_redactions, or cover the glyph area with a fill rect in the cell background. 4) Compute new text width with fitz.get_text_length("54.00", fontname=font, fontsize=size); for right alignment set start x = x1 - width_new, baseline y = origin y. 5) Insert new text: page.insert_text((x, y), "54.00", fontname=font, fontsize=size, color=color). If the embedded subset lacks the new glyphs, embed a full font via fontfile instead. 6) Save to a new file and verify (text search + render).
- id: pdf-cell-02
  answer: |
    Size the rect snugly around only the target cell's text glyphs (small padding, ~1-2 pt), spanning the cell width but stopping before neighboring cells' text and rules. Because apply_redactions removes every character whose bbox even slightly overlaps the rect, an oversized rect would also delete digits/text in the cell above, below, or next column and could clip shared grid lines. In a tight table the tolerance between cells is tiny, so clamp the rect to the target cell's text bbox and do not cross into adjacent cell bboxes or ruled borders; include borders/shading only if you intend to remove them and can do so without touching neighbors.
- id: pdf-cell-03
  answer: |
    insert_textbox wraps words within rect.width and renders as much as fits within rect.height; text that still does not fit is silently not drawn (no exception), and it reports the overflow/remaining space. It will not auto-shrink the font. Options: measure with fitz.get_text_length and reduce fontsize until it fits; use a narrower/condensed font; reduce cell padding; allow more lines by making rect taller; abbreviate the value or split it onto two lines; or widen the column (which means moving the vertical rules and re-aligning the column — a relayout). Pick the smallest change that keeps it native-looking.
- id: pdf-cell-04
  answer: |
    point is the text baseline origin — the (x, y) where the baseline of the first glyph starts (left side at the baseline), in top-left-origin page coordinates; it is not the top-left corner of the bounding box. Passing the old word's bbox top-left (x0, y0) is wrong: y0 sits above the baseline, so the new text is painted too high (wrong baseline, colliding with the line above), and x0 is the left edge — for right-aligned text you must align right edges, not left edges. Result: the new number is vertically shifted up and horizontally misaligned, so it will not line up with the column. Use the span's "origin" for the baseline and compute x = cell_right_edge - new_text_width for right alignment.
- id: pdf-relayout-01
  answer: |
    The Total row and everything below the table must move down by the new row's height — PDF does not reflow. Insert the new row's text and rules/shading just above the Total row; translate the Total row (its text, borders and shading) down by delta h; shift every table rule and all page content below the insertion point down by delta h; add the new row's horizontal rules and side borders; repaint the new row's shading; recompute the Total if the new row changes it. If pushing content down runs off the bottom of the page, content flows to the next page and pagination changes, which must be handled. Essentially: from the insertion line downward, shift everything down by delta h and redraw the new row's rules.
- id: pdf-relayout-02
  answer: |
    You cannot just append a column — the table already spans margin to margin, so there is no spare width. Correct approach: recompute all column widths so the existing columns shrink, shift all cell text and vertical rules to the new column boundaries, recompute each right-aligned number's ending x (cell right edge - text width), re-wrap headers if needed, insert the new column within the same total outer width, and redraw the complete grid. Common mistake: adding the new column's width on top of the full-width table so it overflows the right margin/off the page, or appending it to the right into the margin; equally, forgetting to shift existing columns' content and rules so old and new cells overlap or the grid no longer lines up.
- id: pdf-relayout-03
  answer: |
    Acceptable only when the document is simple, text-focused and exact visual fidelity/pagination does not matter (e.g., a draft invoice where approximate layout is fine) — and only if you will visually QA the round-trip. Risks: PDF->DOCX/HTML converts absolute coordinates into flow layout, so positions, right-alignment, column widths, ruled lines/shading and page breaks change; fonts/subsets are substituted or lost; embedded subset fonts cannot render new glyphs; images and vector graphics may shift or drop; pagination and headers/footers can move; signed/PDF/A PDFs break. The result rarely looks identical, so for "native-looking" table edits this reconstruction is generally unacceptable.
- id: pdf-relayout-04
  answer: |
    Compute occupied regions: text bboxes (get_text("words"/"blocks")), drawing rects (get_drawings()), image rects (get_image_rects per xref), and annotations. A candidate placement rect is free if it lies inside the page margins and its fitz.Rect does not intersect (with a small padding tolerance) any occupied text/drawing/image/annotation rect — use rect.intersects() or check intersection area is zero. To grow a table, check the band from the table's bottom edge down by the needed row height across the table width is clear and still above the bottom margin. PyMuPDF has no built-in "largest empty rectangle," so you compute free space by subtracting occupied rects from the page rect yourself.
- id: pdf-tblins-01
  answer: |
    Way A — draw directly on page 1: find a free rect (relayout-04), fix column widths and row heights, draw header fill and all horizontal/vertical rules with draw_rect/draw_line using the document's stroke/fill colors and line width, then place each cell's text with insert_text at the cell baseline origin, computing right-aligned x = cell_right - fitz.get_text_length(text, fontname, fontsize).   answer: |
    Options: (1) shrink the paragraphs (reduce font size/line spacing/space-before-after) to free a gap; (2) make the table smaller (smaller font, fewer/shorter columns, tighter rows) so it fits existing whitespace; (3) move the second paragraph and all following content down by the table height to open a gap — but PyMuPDF cannot shift existing content natively, so this requires rewriting/re-drawing downstream content; (4) move the second paragraph to the top of the next page (page break) and place the table in the freed space; (5) place the table elsewhere on the page or on the next page where there is free space. - id: pdf-imgrep-01
  answer: |
    Find the logo's placement: page.get_images(full=True) gives the image xref, and page.get_image_rects(xref) gives the rect(s) where it is drawn on page 1. For each rect, remove the old image (add_redact_annot(rect) then apply_redactions(images=fitz.PDF_REDACT_IMAGE_PIXELS) to blank those pixels, or cover with a background-colored fill rect), then page.insert_image(same_rect, filename=new_png) to place the new PNG at the same position/size (insert_image stretches to fill the rect, so match aspect or accept stretch). Catch: the same image xref is often shared across many pages — blanking one placement only affects that page (other pages keep the old logo), while inserting a new image per page embeds a fresh copy each time (file bloat). You cannot simply "swap" one shared XObject in place for all pages; you must update every placement or replace the shared xref stream (which changes every page using it).

    The visible "logo" may not be an image at all: it could be vector paths (get_drawings()), outlined text (get_text()), a Form XObject/group, or an image masked by an SMask — none of which page.get_images() (image XObjects) necessarily lists. - id: pdf-fonts-01
  answer: |
    An embedded subset font (e.g., "AAAAAA+Georgia") contains glyphs only for characters already used in the document. If the new item name uses letters never seen before, the subset has no glyph/cmap entry for them, so reusing that font renders those letters as notdef (blank or black boxes) — the text will not display correctly. Do not reuse the subset for new glyphs; instead embed a full font that contains the needed characters (PyMuPDF insert_text(..., fontfile="font.ttf") embeds a TTF on the fly, or insert a full non-subset font via doc font insertion) and use that font name for the replacement, or fall back to a base-14 font only if the characters are WinAnsi/Latin-1.
- id: pdf-fonts-02
  answer: |
    PyMuPDF built-in base-14 names: Helvetica regular = "helv", Helvetica bold = "hebo" (others: heit, hebi, cour, cobo, coit, cobi, tiro, tibo, tiit, tibi, symb, zadb). Limitation: base-14 fonts are not embedded and use WinAnsi/Latin-1 encoding, so the viewer must supply a substitute font and they cannot reliably render non-Latin text (CJK, Arabic, etc.) or special symbols outside Latin-1 — those glyphs appear as blanks/notdef, and metrics depend on the viewer's substitute (so text can reflow).

- id: pdf-verify-02
  answer: |
    No. An incremental save (doc.save("same.pdf", incremental=True)) appends a new revision but leaves the original objects — including the pre-redaction content stream containing the confidential row — intact in the file, so the row remains recoverable by parsing older objects/streams. apply_redactions only marks/rewrites content for the new revision; the old data is still there.
