# step-5-preview-free — closed-book answers for elixir (opencode-go, 2026-10-12); answerer saw only _prompts/elixir.md
- id: elixir-pm-01
  answer: "`=` is pattern matching, not assignment. `{:ok, value} = fetch()` matches the right-hand term against the left pattern: the right side must be a 2-element tuple whose first element is the literal atom `:ok`; the second element is then bound to the variable `value`. If `fetch()` returns `{:error, :notfound}`, the first elements do not match (`:error` vs `:ok`) and the sizes still match but the atoms differ, so the match fails and Elixir raises a `MatchError` at runtime. `value` is never bound. The idiomatic handling is to match instead of asserting, e.g. `case fetch() do {:ok, v} -> ...; {:error, r} -> ... end` or a function clause per shape, so the error path is a designed branch rather than a crash."
- id: elixir-pm-02
  answer: "Each function head is a standalone pattern plus optional guards, and Elixir tries the clauses top to bottom at call time, executing the first one whose arguments match and whose guards all evaluate to truthy. Pattern matching chooses by shape (literals, tuple/list/map structure, types) and guards add constraints that cannot be expressed structurally, such as comparisons (`when x > 0`) and type checks (`is_binary/1`, `is_map/1`), which must be side-effect free. Example: `def f(0), do: :zero` runs first for `0`; `def f(n) when is_integer(n) and n > 0, do: :pos` runs only if the clause above did not match; a bare `def f(_), do: :other` is the fallback. Clause order therefore matters, since a specific clause placed after a catch-all is dead code and generates no error by default."
- id: elixir-pm-03
  answer: "The pin operator `^` means: use the existing value of this variable as a literal in the pattern instead of rebinding it. On the left, a bare `x` either binds `x` if it is unbound or re-binds it to whatever is on the right, always succeeding structurally; `^x` requires the right side to be equal to `x`'s current value already, and raises `MatchError` otherwise. Example: `x = 1`; `[x, 2] = [1, 2]` succeeds but rebinds `x` to `1` again, whereas `[^x, 2] = [1, 2]` succeeds because the first element equals the pinned value, and `[^x, 2] = [9, 2]` raises `MatchError`. Pin is how you compare against a bound variable while still binding others in the same pattern."
- id: elixir-pm-04
  answer: "Partial: `%{name: n} = user` requires only that the `:name` key exists in `user` and binds `n` to its value. It does NOT require exactly those keys, and it does not care about the map's size or any other keys. List and tuple matching are strictly positional: `[a, b] = [1, 2]` requires exactly two elements, `[h | t]` matches any non-empty list, and `{:a, b} = {:a, 1, :x}` raises `MatchError` because the sizes differ. So map matching is lookup-based and tolerant of extra fields (great for slicing a subset out of a big map), while list/tuple matching asserts the whole shape."
- id: elixir-otp-01
  answer: "`spawn/1` (or `spawn/3`) creates a new lightweight BEAM process isolated from the caller, running a function, and returns a PID; a spawned process that finishes its function simply exits normally. `send/2` is asynchronous, fire-and-forget: `send(pid, msg)` copies `msg` into the target process's mailbox and returns the message immediately, never waiting for delivery or a reply. `receive` runs inside the receiving process, scans its own mailbox, and pattern-matches against stored messages: it takes the first message that matches, binds variables from it, and removes it from the mailbox, or blocks and sleeps if nothing matches. Importantly, `receive` selectively searches the whole mailbox and leaves non-matching messages in place; it waits indefinitely with no timeout unless you add `after` (e.g. `receive do ... after 5000 -> :timeout end`)."
- id: elixir-otp-02
  answer: "`handle_call/3` handles a synchronous request sent with `GenServer.call/3`: the caller blocks until the server replies, so it is for asking for a result (queries and transformations that must return data). Its return values are `{:reply, reply, new_state}`, or `{:reply, reply, new_state, timeout_or_hibernate}`, plus `{:stop, reason, reply, new_state}` when the call should also terminate the server. `handle_cast/2` handles an asynchronous message sent with `GenServer.cast/2`: the caller does not wait, so it is for fire-and-forget commands with no reply. It returns `{:noreply, new_state}` (or `{:noreply, new_state, timeout_or_hibernate}`), and likewise `{:stop, reason, new_state}`. Rule of thumb: use `call` when the caller needs the answer or ordering/acknowledgement, `cast` when you only need to notify."
- id: elixir-otp-03
  answer: "`handle_info/2` receives everything that is NOT a `call` or `cast`: plain raw messages sent directly to the PID with `send/2`, messages from other processes, exit signals from linked processes when the server traps exits, and OTP system messages such as timeout ticks and shutdown requests. `GenServer.call` and `cast` are typed through wrapper messages (containing a `:'$gen_call'` ref or a `:'$gen_cast'` payload) and are dispatched by the generic server loop to `handle_call` and `handle_cast`; `handle_info` is the catch-all fallback for untyped traffic, so it is also where you handle things like `:timeout`, task replies, and periodic work. It returns the same shapes as `handle_cast`: `{:noreply, state}` or `{:stop, reason, state}` (timeout/hibernate variants exist), because by definition there is no reply channel to fill."
- id: elixir-otp-04
  answer: "`one_for_one`: if a child crashes, only that child is restarted and the others keep running. `one_for_all`: if one child crashes, all currently running children are terminated first and then all are restarted together, which fits children that are strongly coupled. `rest_for_one`: when a child crashes, that child plus all children started after it are terminated and only that suffix is restarted, which fits pipelines or dependency chains where later children depend on earlier ones. A child spec is the declarative description of one supervised process: its unique `:id`, the start function (a module/function/args tuple, usually `{MyGenServer, :start_link, [arg]}`), whether it is a `:worker` or a `:supervisor`, its restart policy (`:permanent` always restarted, `:transient` restarted only after abnormal exit, `:temporary` never restarted), the shutdown strategy/timeout (`:brutal_kill`, an integer ms timeout, or `:infinity`), and its `:type`. `use GenServer` and friends generate a default spec, overridable via `child_spec/1`."
- id: elixir-data-01
  answer: "`list` is unchanged. Elixir data is immutable, so `List.delete/2` does not modify the list in place: it builds and returns a new list `[1, 3]`, and the binding `list` still refers to the original `[1, 2, 3]`. The result is simply discarded unless you rebind it, e.g. `list = List.delete(list, 2)`. Rebinding does not mutate anything: it just makes the name `list` point at a different immutable term for the rest of the current scope. The old term still exists as long as something else references it (another binding, a process message, an ETS entry) and is freed by per-process garbage collection when nothing references it."
- id: elixir-data-02
  answer: "Keyword lists (`[a: 1, b: 2]`, really a list of `{atom, value}` two-tuples) use them when the keys are atoms, duplicates may matter, order should be preserved, values stay small and the list is short, and especially for optional function arguments and options passed to functions; they are the only one of the three where order is guaranteed and a key may appear multiple times. Maps (`%{...}`) use them as the general-purpose key-value structure: arbitrary keys, potentially many entries, constant-time lookup, and full pattern matching against any subset of keys. Structs use them when the shape is known and fixed at compile time: `defmodule User do defstruct [:name, :age] end` gives compile-time key validation and default atom keys, so typos are caught early and they define your domain's records. Prefer keyword lists for options, maps for flexible/dynamic data, structs for well-defined domain entities."
- id: elixir-data-03
  answer: "With `%{map | key: val}`, `key` must already exist in `map`; if it does not, Elixir raises a `KeyError` (this is checked at compile time for literal keys and at runtime for expression keys, e.g. `key1`). It updates an existing entry and returns a new map, e.g. `%{user | name: \"new\"}`. `Map.put(map, key, val)` never raises: it returns a new map with `key` set to `val`, adding the key if it did not exist and overwriting it if it did. So map-update syntax is for 'only change a field that must be there' and `Map.put/3` is for 'set or add', which is what you want for optional fields and defaults."
- id: elixir-data-04
  answer: "Because data is immutable, nested updates must rebuild every level between the root and the value you change. `get_in(data, [:user, :address, :city])` reads a deep value, `put_in(data, [:user, :address, :city], \"KL\")` returns a whole new structure with only that leaf replaced, and `update_in(data, [:user, :address], fn addr -> ... end)` applies a function to a nested node and writes the result back (it returns the current value if an intermediate node is missing). `get_and_update_in/3` reads and writes in one step. A convenience form like `data.user.address.city` also works since each segment is an `Access` call. Manually nesting is worse because you must explicitly rebuild each level (`%{data | user: %{user = data.user | address: %{addr = user.address | city: \"KL\"}}}`), which is verbose and fragile: forgetting a level silently drops data, and you have to handle `nil` intermediates yourself. With the `_in` functions that rebuilding is mechanical and consistent, and the same path list drives both reads and writes, so the two cannot drift apart. (Also available: `pop_in/2`, `fetch_in/2`, and `Access.pop`, `get_in` being the thin read-side wrapper over `Access.get/3` paths.)"
- id: elixir-pipe-01
  answer: "`x |> f(a) |> g()` is syntactic sugar for `g(f(x, a))`: it takes the left-hand value and passes it as the FIRST argument of the right-hand function call, keeping the value flowing left to right so a sequence of transformations reads like a pipeline. The one rule to remember: the piped value goes in as the first argument, which is why you sometimes need `then/2` to use it in another position, e.g. `user |> then(&File.read!(&1))` or `string |> then(&String.replace(&1, \"a\", \"b\"))` instead of putting the piped result where it does not belong. Only expressions that return a value can be piped, and it is a scoping tool too: `raw` in a head `raw |> String.trim()` is in scope for the whole pipeline without shadowing. (There is no runtime cost: it rewrites to plain nested calls.)"
- id: elixir-pipe-02
  answer: "`with` solves the 'staircase of nested cases' problem: several steps must run in sequence, and if any step returns something other than the happy shape you want to bail out immediately instead of nesting deeper and deeper. Each clause `pattern <- expr` first evaluates `expr`, then matches it against `pattern`; if it matches, the variables from the pattern are in scope in all later clauses and the body, and the pipeline continues. The moment a clause DOES NOT match, evaluation stops right there and the whole `with` returns that non-matching value as-is. Example: `with {:ok, user} <- fetch_user(id), {:ok, acct} <- fetch_account(user.id) do {:ok, acct}` continues only while each call returns `{:ok, _}`; if `fetch_user` returns `{:error, :not_found}` the first clause fails and `with` returns `{:error, :not_found}` without ever calling `fetch_account`. The body runs only if every clause matched, and it should return the final `{:ok, _}` result."
- id: elixir-pipe-03
  answer: "As soon as `pattern <- expr` fails to match, `with` short-circuits and returns that non-matching value from the expression itself; none of the remaining `<-` clauses and no `do` body are evaluated. Because the raw failure value can be ambiguous (is `:error` an error or legit data?), the optional `else` block lets you translate those unmatched values into something more meaningful. It takes a `case`-like list of clauses, and every non-matching value is matched against them in order; the first match wins, otherwise a `WithClauseError` is raised if none match (or the original value is returned if `else` is omitted). Example: `with {:ok, u} <- fetch(id) else {:error, r} -> {:error, {:fetch_failed, r}}` renames the reason, and having `else` means `{:error, _}` no longer silently leaks out uninterpreted. Note that guards are not allowed in `do` bodies but `else` clauses can carry guards."
- id: elixir-pipe-04
  answer: "Pipes are the wrong tool when the next step needs the piped value somewhere other than first position, or when the flow is not a straight line. Two concrete cases. One: `text |> String.upcase() |> String.replace(\"a\", \"b\")` reads fine, but `String.replace(text, \"a\", \"b\") |> ...` with several positional arguments in order becomes unreadable, e.g. `value |> Enum.at(Enum.reverse(list), 0)` style nesting forced by arity; fix by capturing the intermediate (`trimmed = String.trim(text)` then pipe `trimmed`) or using `then/2` to put it last (`raw |> then(&Regex.run(~r/\\d+/, &1))`). Two: when multiple variables are in play, e.g. formatting where you need both `user` and `request` at each step, a pipe only threads one value, so the chain degenerates into fake steps; fix by using `with` to bind each intermediate (`with {:ok, u} <- fetched, {:ok, a} <- account(u), do: render(a)`) or by ordinary sequential statements with named lets, which document intent better than a mega-pipe. Also do not pipe a value that is itself a keyword list into a function that treats trailing keyword lists as options, since `kw |> f(opt: 1)` can silently add your keywords to the option list."
- id: elixir-error-01
  answer: "Return `{:ok, value}` / `{:error, reason}` for expected, recoverable domain failures that the caller is meant to branch on: a record missing, a validation failing, a network hiccup, a file not readable. It makes failure part of the return contract (the compiler even warns on unmatched shapes), keeps control flow explicit in `case`, `with`, or function clauses, and costs nothing on the success path. Raise for conditions that are truly exceptional or indicate a bug: contract violations by the caller (bad arguments to an internal function), broken invariants/state that should not persist, and setup assumptions failing ('config key missing'). If you cannot name a meaningful recovery for the caller, raise, since silently swallowing that into a tuple just moves the problem. Practical split, matching stdlib: `File.read` returns a tuple, `File.read!` raises, and your code documents which expectation it follows by name."
- id: elixir-error-02
  answer: "A trailing `!` is Elixir's convention for the version of a function that raises on failure instead of returning a tagged tuple: `File.read/1` returns `{:ok, contents}` or `{:error, reason}`, while `File.read!/1` returns the contents directly or raises `File.Error`. So the bang pair always has the same core behaviour, and the only difference is the failure representation: a tuple you must handle versus an exception that unwinds if you do not `rescue` it. The rule of thumb: use the non-bang function in library code so your callers get to handle failure, and the bang version in scripts, tests, and pipeline code where failing fast with a stack trace is more useful than a tuple."
- id: elixir-error-03
  answer: "`try` starts an expression that is executed inline; `rescue` clauses catch raised exceptions (`rescue e in RuntimeError -> ...` binds the struct, `rescue UndefinedFunctionError -> ...` matches its type), and the block's value is the `try`'s value when nothing raises. `catch` covers the other two throwable categories for use with `throw` (non-local exits, e.g. `throw {:halt, x}`) and `exit` (signals), with clauses written as `catch :throw, value ->`, `catch :exit, reason ->`, or `catch kind, reason ->` to see all; plain `rescue` only intercepts `:error` exceptions. So `rescue` is for Erlang/Elixir errors in the structured `%Exception{}` sense, `catch` is for `throw`, `exit` and error kinds alike. `after` runs unconditionally once the body has finished, whether it returned normally, raised, threw, exited, or was matched by a `rescue`/`catch`/`else`, and its own value is discarded: it exists purely for cleanup like closing a file or releasing a connection. If both the body and `after` raise, the exception from `after` propagates instead."
- id: elixir-error-04
  answer: "\"Let it crash\" means: instead of writing dense defensive code that tries to anticipate and handle every possible failure, you write the straightforward happy path and let a failure take the process down; the supervisor tree then restarts it, discarding the corrupted state and returning to a known-good condition. This works because BEAM processes are isolated: each has its own heap and mailbox with no shared mutable state, so a crash can only break that one process, never corrupt others. Recovery becomes uniform and reusable, all crash reasons funnel to the supervisor, which resets to initial state, and restart storms escalate to the supervisor's own supervisor. You still defend where a process cannot fix itself (validating user input is not a crash, and an infinite loop or OOM in the crashing process cannot be rescued by restarts), so 'let it crash' complements defensive coding rather than replacing it."
- id: elixir-enum-01
  answer: "The core difference is when the work happens. `Enum` is eager: every call walks the whole enumerable immediately and produces a concrete new list (or other collectable), so `list |> Enum.map(&f/1) |> Enum.filter(&g/1) |> Enum.sum()` allocates two intermediate lists and does three full passes. `Stream` is lazy: each function returns a stream, a recipe of composed transformations, and nothing runs until an eager terminal operation forces it, such as `Enum.sum`, `Enum.to_list`, or `Enum.count`. So streams can short-circuit before touching the whole input and fuse multiple transformations into one pass, avoiding intermediate collections, at the cost of extra bookkeeping that makes them slower than `Enum` for small in-memory one-shot operations."
- id: elixir-enum-02
  answer: "First, working with large or unbounded input: reading a very large file line by line, e.g. `file |> File.stream!() |> Stream.map(&String.trim/1) |> Stream.filter(&(&1 != \"\")) |> Enum.count()`, streams one line at a time instead of loading the whole file into memory; likewise `Stream.iterate(1, &(&1 * 2)) |> Stream.take(10) |> Enum.to_list()` would hang or exhaust memory if the iteration were eager, but laziness only ever produces the first ten elements. Second, when you chain several operations over a large collection and do not need the intermediates, e.g. `big_list |> Stream.map(f) |> Stream.filter(g) |> Stream.map(h) |> Enum.sum()` streams each element through the entire composed pipeline in one pass, avoiding two or three temporary lists that `Enum` would allocate. (Both are cases where the input or the intermediates cannot or should not exist all at once.)"
- id: elixir-enum-03
  answer: "`Enum.reduce(enumerable, acc, fn element, acc -> new_acc end)` walks the enumerable from the start, threading an accumulator: each element is combined with the current accumulator by your function, whose return value becomes the next accumulator, and the final accumulator is returned. It is the building block because it makes no assumption about the output: the accumulator can be anything (a number, a list, a map, a tuple), so the other functions are `reduce` plus a chosen reducer. `Enum.map/2` is reduce where the function returns `[result | acc]` reversed at the end; `Enum.filter/2` keeps the element or discards it while building a list; `Enum.sum/1` is reduce with `0` and `+`; `Enum.count/1`, `Enum.group_by/2`, `Enum.frequencies/1`, `Enum.max_by/2` and friends all fall out the same way. `reduce_while/3` adds early stopping for the cases where you want to halt before the end."
- id: elixir-enum-04
  answer: "`for` is a comprehension made of generators, filters, and a body: `x <- list` is the generator that draws each element from the enumerable and binds it to `x`, running the rest once per element; `rem(x, 2) == 0` is a filter (truthy test) that keeps only matching elements, which can use pattern matching too; `into: %{}` sets the collectable, so the results are gathered into a map instead of the default list (key-value pairs are produced by the body); and `do: {x, x * x}` is the body expression whose value is collected for each element that survived the filters. So `for x <- [1,2,3,4], rem(x,2) == 0, into: %{}, do: {x, x*x}` yields `%{2 => 4, 4 => 16}`. You can have several generators (producing a cross product), several filters, and `:reduce`/`:uniq` options alongside `:into`."
- id: elixir-proto-01
  answer: "A protocol is Elixir's mechanism for polymorphism over data types: it declares a set of functions, and any module or built-in type can provide its own implementation, with dispatch decided at runtime from the first argument's type. `defprotocol Blank do def blank?(data) end` declares the API, then `defimpl Blank, for: Integer do def blank?(0), do: true; def blank?(_), do: false end` supplies implementations per data type using `for: Type` (an Atom, Tuple, List, Map, or struct). The caller just writes `Blank.blank?(42)` and the VM picks the right implementation, including a `defimpl Blank, for: Any` fallback when no specific one exists. This is how stdlib protocols like `Enumerable`, `String.Chars`, `Inspect` and `Jason.Encoder` let many unrelated types share one interface."
- id: elixir-proto-02
  answer: "A behaviour is a compile-time contract that a module must implement a specified set of functions, used for pluggable, dynamically dispatched components like `GenServer`, `Supervisor`, or `Plug`. `@callback` declares the required function's name, arity, and spec (e.g. `@callback init(opts :: term()) :: {:ok, state} | {:stop, reason}`), and optional and default implementations are not a thing: the behaviour just states what implementers must provide. `@behaviour MyBehaviour` in a module tells the compiler to check that the module actually defines those callbacks, so a mismatch or missing callback becomes a warning at compile time. `@impl true` marks one function in that module as an implementation of a callback from the nearest `@behaviour`, letting the compiler verify it really matches a declared `@callback`, and it documents for readers which functions are the contract's functions as opposed to ordinary helpers."
- id: elixir-proto-03
  answer: "The fundamental difference is what they dispatch on. A protocol dispatches on the DATA type of an argument: the call site passes a value (`String.Chars.to_string(1)`), and at runtime the implementation is chosen from the value's type, so the same code can handle types that were not known when the call was written, and third parties can add implementations for their own types. A behaviour dispatches on the MODULE: the call site passes a module (`GenServer.start_link(MyWorker, arg, [])`), and the generic server code in `GenServer` calls `MyWorker.handle_call/3` etc., so the behaviour defines a set of functions a module must implement. In short, protocols are open and additive over data types (you can `defimpl` for a type the protocol never anticipated), while behaviours are a compile-time contract between a piece of library code and the modules that plug into it."
- id: elixir-proto-04
  answer: "`@impl true` (or `@impl SomeBehaviour` when several apply) marks the following function as an implementation of a callback from the module's `@behaviour`, which buys you compile-time verification: if you annotate a function that does not match any callback (wrong name, wrong arity, wrong spec, or typo), the compiler emits a warning such as 'function foo/1 is not a callback (there is no such callback)', and if you mark a function as `@impl` for a behaviour you never declared, it warns too, so you cannot claim a contract you are not fulfilling. It is not runtime metadata but a documentation and safety aid: it shows readers which functions are part of the contract versus ordinary helpers, and it makes refactors safer because renaming or changing a callback breaks loudly at compile time instead of at runtime with a confusing `UndefinedFunctionError`."
- id: elixir-conc-01
  answer: "BEAM concurrency is based on processes in the Erlang sense, not OS processes: `spawn` creates a lightweight, user-space unit of concurrency with its own heap, own mailbox, and own garbage collection, scheduled preemptively by reductions inside a VM thread (an OS scheduler thread per core). The model is strictly share-nothing: there is no shared mutable memory and no locks; the only way to communicate is `send`, which deep-copies a term into the target's mailbox while also being non-blocking for the sender. This matters because isolation makes failures contained (a crashed process cannot corrupt another's state, so supervision can restart it safely), it makes reasoning sequential per process, per-process GC stays cheap so pauses are short and independent of system size, and message passing scales horizontally on multicore without contention. The trade-off is that immutability means large data structures must be copied to pass them, which is why refc binaries are the usual trick for shipping megabytes around."
- id: elixir-conc-02
  answer: "`Task.async(fn -> work() end)` spawns a new process linked to the caller and monitored, starts running `work` immediately, and returns a `%Task{}` struct (which you can pass to `Task.await/2` or `Task.yield/2`) rather than the result, so multiple `async` calls run concurrently before anything is awaited. `Task.await(task)` blocks the caller until the task replies, returning `{:ok, result}` on success and `{:exit, reason}` if the process dies, with a default timeout of 5000 ms. Crucially, the task process is LINKED to the caller: if the task raises, its exit signal kills the caller too, which is deliberate so a bug in concurrent work does not silently return a value, and on timeout the task is shut down and `await` exits with a `timeout` error. Note that `Task.async` is meant for `await`-style use with linked processes and supervision, whereas `Task.Supervisor.async_nolink` is the supervised, link-free variant, and unawaited tasks leak mailboxes, which is why `Task.yield` plus `Task.shutdown` exists."
- id: elixir-conc-03
  answer: "An `Agent` is a thin wrapper around a process that holds a piece of state, providing a focused API for reading and updating it without writing callback boilerplate: `Agent.start_link(fn -> %{} end, name: :cache)` starts it, then `Agent.get(:cache, & &1)`, `Agent.update(:cache, &Map.put(&1, :k, 1))` and `Agent.get_and_update(:cache, ...)` run your function inside the agent's process against its state. You use an `Agent` when the state is simple and you only need plain get/update semantics (a counter, a cache, a set of connected callers), because all the `GenServer` ceremony disappears: you still get serialized access, a clean crash-and-restart boundary, and the same process isolation, with significantly less code. The difference from a full `GenServer` is capability: a `GenServer` gives you typed messages via `handle_call` and `handle_cast`, custom `init`/`terminate`, timeouts, `handle_info`, and nested replies, so anything more interesting than 'read/modify this state' should be a `GenServer`; treat `Agent` as the minimal specialised wrapper (it is literally `GenServer` with callbacks you never see) rather than a general server."
- id: elixir-conc-04
  answer: "ETS (Erlang Term Storage) is an in-memory key-value store built into the BEAM: a table is created by an owning process, and it is a term-storage engine optimised for key lookup, with access options such as `:set`, `:bag`, `:ordered_set` and `:duplicate_bag`, `read_concurrency`/`write_concurrency` tuning, and crucially it does NOT route every operation through a process mailbox, so concurrent reads do not serialise the way a GenServer's mailbox does. Because it lives in shared memory with fine-grained per-record locking, it can be orders of magnitude faster and far more concurrent than a process-based store for read-heavy and hot-path data. Use ETS instead of a GenServer/Agent when you need a shared cache or lookup table that is read far more often than written, when the data is large enough that process serialisation is a bottleneck (event registries, ETS-backed caches, term lookup indices), and when you can accept its trade-offs: no ACID transactions, only term matching (plus `select`/`match` and `ordered_set` ranges), no per-item side effects, and the table is destroyed when its owner dies, so a supervised holder process is needed for durability. Use a process when you need serialized side effects, complex validation, or transactional multi-key updates; use ETS when you need fast, concurrent reads (or key-range scans) over a large set, often alongside a GenServer that owns and writes it."
