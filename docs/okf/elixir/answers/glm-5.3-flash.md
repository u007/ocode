- id: elixir-pm-01
  answer: |
    `=` pattern-matches the left-hand pattern against the right-hand value and binds the free variables in the pattern. `{:ok, value} = fetch()` destructures the result: if fetch() returns `{:ok, 42}`, `value` is bound to 42. If the right side is `{:error, :notfound}`, the match fails and a `MatchError` is raised at runtime — nothing is bound, there is no fall-through to other code.
- id: elixir-pm-02
  answer: |
    Each function head is a clause; clauses are tried top-to-bottom and the first one whose argument pattern matches AND whose guard (`when ...`) evaluates to truthy runs. Guards restrict matches to a limited set of allowed expressions (type checks like `is_integer/1`, comparisons, `and`/`or`/`not`, arithmetic). If no clause matches, a `FunctionClauseError` is raised. This turns if/else/cond chains into declarative dispatch on data shape:
      def classify(n) when n < 0, do: :negative
      def classify(0), do: :zero
      def classify(n) when is_integer(n), do: :positive
    What decides which clause runs: clause order + pattern match + guard truthiness of the actual arguments.
- id: elixir-pm-03
  answer: |
    `^` pins a variable so the pattern matches against its *current* value instead of rebinding it. `^x = y` succeeds only if `y` equals the value x already holds (otherwise `MatchError`); it never changes x. A bare `x` on the left always rebinds: `x = y` replaces x's binding with y's value regardless of what x held before. So `^x` reads "the existing x"; `x` reads "whatever comes next".
- id: elixir-pm-04
  answer: |
    Map patterns match partially: `%{name: n} = user` succeeds for any map that has at least a `:name` key; other keys are ignored and `n` binds to the value. It does NOT require exactly those keys — extra keys are fine, but every listed key must be present. By contrast, tuple matching is exact on size/shape (`{a, b} = t` requires exactly two elements), and list matching matches the prefix you write (e.g. `[h | t]`). Note: when matching a struct like `%User{name: n}`, the struct module itself must match exactly, though the field match within it is still partial.
- id: elixir-otp-01
  answer: |
    `spawn/1,3` starts a new lightweight BEAM process (not an OS thread/process) running a function and returns its pid immediately. `send/2` asynchronously puts a message (any term) into the target process's mailbox; it never blocks. `receive/1` scans the mailbox for the first message matching one of its patterns, executes the matching branch and removes that message; non-matching messages are left in the mailbox. When no message matches, `receive` suspends the process until a matching message arrives — unless an `after` clause gives a timeout (including `after 0`, which gives up immediately when nothing matches).
- id: elixir-otp-02
  answer: |
    `handle_call(msg, from, state)` is synchronous: the caller blocks (default timeout 5s) waiting for a response, so it's for requests that need a reply or backpressure. It must return `{:reply, reply, new_state}` (also `{:noreply, new_state}` or `{:stop, reason, reply, new_state}`). `handle_cast(msg, state)` is asynchronous fire-and-forget: the caller returns immediately and no reply is possible; it returns `{:noreply, new_state}` (or `{:stop, reason, new_state}`).
- id: elixir-otp-03
  answer: |
    `handle_info` receives everything that arrives outside GenServer's call/cast protocol: raw `send/2` messages from any process, `Process.send_after` timeouts, monitor `:DOWN` messages, `:EXIT` signals when trapping exits, and port/socket messages. `handle_call`/`handle_cast` only handle messages sent through `GenServer.call/cast` (an internal tagged-message protocol); everything else falls through to `handle_info`. If you don't define it, GenServer's default implementation logs the unexpected message and continues rather than crashing.
- id: elixir-otp-04
  answer: |
    - `:one_for_one`: only the crashed child is restarted; siblings are untouched.
    - `:one_for_all`: when a child crashes, all other children are terminated and then all are restarted.
    - `:rest_for_one`: the crashed child plus every child started after it (in start order) are terminated and restarted.
    (A legacy fourth strategy, `:simple_one_for_one`, was replaced by `DynamicSupervisor`.)
    A child spec describes how a supervisor starts, supervises, and shuts down one child: a map/keyword with `:id`, `:start` (an MFA), `:restart` (`:permanent` | `:transient` | `:temporary`), `:shutdown` (`:brutal_kill`, `:infinity` for supervisors, or milliseconds), and `:type` (`:worker` | `:supervisor`). Modules typically export `child_spec/1` (auto-generated by `use GenServer`), which `Supervisor.start_link/2` consumes.
- id: elixir-data-01
  answer: |
    Nothing happens to `list` — it still evaluates to `[1, 2, 3]`. `List.delete/2` returns a *new* list, `[1, 3]`; the original is never mutated (new values share structure with old ones where possible). Rebinding with `list = List.delete(list, 2)` doesn't change the data either — it re-points the *variable name* to the new value. The old `[1, 2, 3]` is unchanged and becomes garbage once nothing references it, so any other code holding the original value still sees it.
- id: elixir-data-02
  answer: |
    - Maps: the general key→value store. Any term as key, unique keys, no meaningful order, great for pattern matching. Default choice for dynamic data.
    - Keyword lists: lists of `{atom, value}` pairs (sugar `[key: value]`). Keys must be atoms, duplicates allowed, order preserved; the call-site sugar makes them the convention for options/arguments (`def f(opts \\ [])`). Use when order or duplicate keys matter, e.g. option lists and DSLs.
    - Structs: compile-time-defined maps with a fixed key set and defaults (`defstruct`), tagged with their module; `%{}` will not match a struct, and only declared keys exist. Use for domain entities where an enforced, known shape matters.
- id: elixir-data-03
  answer: |
    `%{map | key: val}` is the update syntax: it only works on keys that already exist, and raises `KeyError` if `key` is missing. `Map.put(map, key, val)` inserts the key when absent (adding it) and updates when present. So the update syntax guarantees the map's shape can't gain keys and fails loudly on absent keys/typos; `Map.put` is insert-or-update. The update syntax also works on structs.
- id: elixir-data-04
  answer: |
    They take a path (a list of keys, or the macro form like `data.a.b`) plus an operation and return a new top-level structure with just that leaf changed — e.g. `update_in(user.profile.address.city, &String.upcase/1)` or `get_in(data, ["a", "b"])`. Benefits over manual nesting: one expression instead of destructuring and rebuilding at every level (where it's easy to drop or mis-rebuild a branch), the path can be computed at runtime, they compose with Access for lists (`Access.at/1`) and with update-syntax semantics for structs, and they make the copy-on-write-along-the-path nature of immutable updates explicit and safe.
- id: elixir-pipe-01
  answer: |
    `x |> f(a, b)` rewrites to `f(x, a, b)`: the value on the left is inserted as the *first argument* of the call on the right. That's the one rule — which is why pipelines read naturally only when each function takes its "subject" as the first parameter, the convention the stdlib follows (`list |> Enum.map(f) |> Enum.filter(p)`).
- id: elixir-pipe-02
  answer: |
    `with` flattens the nested-case pyramid you get when a sequence of steps can each fail. Each `<-` line pattern-matches that step's result: on match, execution proceeds to the next step; on non-match (typically `{:error, reason}`), the with short-circuits and stops evaluating further steps.
      with {:ok, user} <- fetch_user(id),
           {:ok, perms} <- fetch_perms(user) do
        {:ok, build(user, perms)}
      end
    The happy path reads linearly at one indentation level, and all error paths funnel to a single place.
- id: elixir-pipe-03
  answer: |
    When a `<-` pattern doesn't match, the with stops and hands the non-matching value onward: with an `else` block, that value is matched against the `else` clauses (so you can normalize/translate errors, log, or return `{:error, reason}`); a value matching no `else` clause raises `WithClauseError`. Without `else`, the raw non-matching value is returned as-is — which is why `with` without `else` is only safe when the failure shapes are already what you want to return.
- id: elixir-pipe-04
  answer: |
    Piping reads badly when the data isn't the first argument of the next call — you end up with anonymous-function gymnastics like `value |> then(&Map.put(ctx, :key, &1))` — or when a step discards the subject so what "flows" no longer matches the next step's first parameter, and `case`/`with` get jammed into pipes. Fix: write a small wrapper function with the subject first (e.g. `put_key(ctx, value)`), use named intermediate variables with meaningful names for genuinely distinct stages, or restructure so each step genuinely transforms the previous result. Also avoid burying side effects mid-pipe where ordering matters silently.
- id: elixir-error-01
  answer: |
    Tagged tuples for *expected* failures: invalid input, record not found, validation errors — outcomes the caller is expected to branch on. Raise for *exceptional* situations: programmer errors, broken invariants, impossible states, or anywhere the current process can't meaningfully continue — the crash is then handled by supervision ("let it crash"). Rule of thumb: libraries return `{:ok, _}`/`{:error, _}` for anticipated outcomes; raising is right in scripts/top-level code where you want to fail fast, and for truly exceptional conditions rather than ordinary control flow.
- id: elixir-error-02
  answer: |
    The trailing `!` marks a variant that raises on failure instead of returning an error tuple. `File.read(path)` → `{:ok, binary} | {:error, reason}`; `File.read!(path)` → the binary, or raises `File.Error`. Use the bang version when failure is exceptional or you want the process to crash (let-it-crash) instead of threading error tuples through the call chain.
- id: elixir-error-03
  answer: |
    `try/do ... rescue ... after ... end`: the body runs; if an exception occurs (anything raised via `raise`, including runtime errors like `MatchError`/`ArgumentError`, which are Exception structs), `rescue` clauses match it by exception type/pattern; `after` is the cleanup block. `catch` is a separate mechanism: it matches values thrown with `throw/1` (and can also match exits, or raw errors via `catch :error, value`) — so `rescue` handles exceptions while `catch` handles throws/exits/errors; they're different classes. `after` is guaranteed to run when the try block exits by any means — success, raise, throw, or exit — the real exceptions being hard kills that can't be trapped (another process exits this one with `:kill`, or the VM/node dies).
- id: elixir-error-04
  answer: |
    Instead of defensively rescuing every possible error in place, let a process crash when it hits something it doesn't know how to handle, and let a supervisor restart it in a clean, known state. Rationale: you usually can't do anything useful about an unexpected bug locally — the process's state may be corrupted or inconsistent, and "recovering" in place risks persisting bad state. Crashing isolates the failure (only that process dies), centralizes recovery in the supervision tree, keeps business code simple, and guarantees a restarted process begins from known-good state. Rescue-everywhere code hides bugs and can leave inconsistent state behind.

    Enum is eager: every function walks the whole collection immediately and returns a fully materialized result, so a chain of Enum calls builds an intermediate list at each step. Stream is lazy: the Stream functions just build a description/composition of transformations; no work happens until a driving function like `Enum.to_list/1`, `Enum.take/2`, or `Enum.reduce/3` pulls elements through — then each element flows one at a time through the entire pipeline.
- id: elixir-enum-02
  answer: |
    1) Huge or unbounded input where you only need a few results: `File.stream!() |> Stream.map(&parse/1) |> Stream.filter(&valid?/1) |> Enum.take(5)` stops at the first matches instead of processing everything; infinite streams only work this way.
    2) Long chains of transformations over large collections where eager Enum would materialize an intermediate list after every step — Stream composes into a single pass. (Closely related: anything bigger than memory, streamed from a file, socket, or DB cursor.)
- id: elixir-enum-03
  answer: |
    `Enum.reduce(enumerable, acc, fun)` folds the collection into one value: starting from `acc`, it calls `fun(element, acc)` for each element in order, feeding each result back as the next accumulator, and returns the final accumulator. map/filter/sum etc. are special cases: map = reduce appending each transformed element to a list; filter = reduce keeping elements conditionally; sum = reduce with `&+/2`. Anything expressible as "walk the elements, accumulate a result" can be written as reduce, which is why it's the fundamental iteration primitive.

- id: elixir-proto-01
  answer: |
    A protocol defines a polymorphic API without implementations: `defprotocol Blank, do: def blank?(data)`. `defimpl Blank, for: SomeType` supplies the implementation for one concrete data type (built-ins like Integer/List/Map, or a struct like `%Date{}`); `defimpl ... for: Any` (with `@fallback_to_any`) is the fallback. Dispatch happens on the type of the first argument at call time — same call site, different implementation per value's type. It's Elixir's equivalent of type classes/interfaces, implemented as separate protocol+impl modules (with protocol consolidation pre-resolving dispatch for speed).
- id: elixir-proto-02
  answer: |
    A behaviour defines a contract a module must fulfil: a set of named callbacks with arities and typespecs. `@callback handle(msg) :: :ok` declares one callback in the behaviour module (name, signature, types). `@behaviour MyBehaviour` in an implementing module declares "I implement this contract", and the compiler then warns if required callbacks are missing or have the wrong arity. `@impl true` (or `@impl MyBehaviour`) annotates a function as the implementation of a callback, enabling compile-time checks (it must correspond to a declared callback, correct arity; required when multiple behaviours share a callback name) and documenting intent. GenServer, Supervisor, and Application are common behaviours.
- id: elixir-proto-03
  answer: |
    Protocols dispatch dynamically on the *type of the data*: which implementation runs is decided at runtime from the value passed as the first argument — one implementation per data type, and you can add implementations for types you don't own. Behaviours are a static, module-level contract: the implementing module is chosen explicitly by the caller (passed as a module atom, injected, or configured), the compiler checks conformance, and dispatch is by module identity, not data shape. In short: protocol = polymorphism on values; behaviour = polymorphism on modules (strategy/injection style).
- id: elixir-proto-04
  answer: |
    It tells the compiler "this function implements callback X of behaviour Y". That buys: (1) compile-time verification that the function matches a declared callback — catching typos, wrong arity, and outdated names (e.g. after a GenServer callback changed) which would otherwise be a silent bug; (2) documented intent — the reader sees which contract the function serves; (3) mandatory disambiguation when a module implements several behaviours whose callbacks share a name (`@impl MyBehaviour`); (4) a warning if a function marked `@impl` doesn't actually match any callback.
- id: elixir-conc-01
  answer: |
    The BEAM runs very large numbers of lightweight processes (each with its own isolated heap, stack, and mailbox, starting at a few hundred bytes to a few KB), preemptively scheduled by the runtime across one scheduler per core — a misbehaving process can't starve the others. There is no shared mutable memory: processes exchange data only by sending messages, which are copied between heaps (large binaries are an optimized ref-counted exception). That isolation matters because a crash or GC in one process can never corrupt another's data; there are no data races or locks on shared state; GC is per-process with no global stop-the-world pauses; and supervision/restart works because a crashed process's state dies with it while everything else stays intact.
- id: elixir-conc-02
  answer: |
    `Task.async(fun_or_mfa)` spawns a new linked process running the function and immediately returns a `%Task{}` handle; starting several tasks and then awaiting each is the standard way to run work concurrently. `Task.await(task, timeout \\ 5_000)` blocks the caller until that task's result arrives. If the task raises, the failure is propagated to the caller at `await` (tasks are linked, so an unhandled task error takes the awaiting process down too). If `await` exceeds the timeout, the caller exits, which through the link also stops the task; code needing finer control uses `Task.yield/2` plus `Task.shutdown/1`, or `Task.async_stream` with `:max_concurrency` and `:timeout`.
- id: elixir-conc-03
  answer: |
    An Agent is a minimal abstraction over a state-holding process: `Agent.start_link(fn -> %{} end)`, then `Agent.get/3`, `Agent.update/3`, and `Agent.get_and_update/3` run your function *inside* the agent process and return the result. It's implemented on top of GenServer but exposes no custom messages or callbacks — you never write handle_call/handle_cast/handle_info. Use an Agent when the only job is "hold state and read/update it"; move to a GenServer when you need named operations, multiple message types, custom timeouts, async/periodic work (handle_info), or a clear client/server API split.
- id: elixir-conc-04
  answer: |
    ETS (Erlang Term Storage) is the BEAM's built-in in-memory key-value table facility: tables hold arbitrary terms, are owned by a creating process, and with `:public` visibility any process can read/write them concurrently, with `read_concurrency`/`write_concurrency` options and `:set`/`:ordered_set`/`:bag`/`:duplicate_bag` table types. Use it instead of a GenServer/Agent when many processes need fast concurrent shared access — a process serializes every request through one mailbox, so for read-heavy caches, counters, rate limiters, config/lookup tables, or dedup sets ETS removes that bottleneck. Trade-offs: it is mutable shared state with no message/behaviour guarantees, the table dies with its owner unless an heir is set, and it isn't distributed or persisted (that's what :dets or external stores are for).
