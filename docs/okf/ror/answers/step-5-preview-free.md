Since Rails 5, a `belongs_to` is required by default (`config.active_record.belongs_to_required_by_default` is set true for new apps): Rails adds a presence validation on the association, so a record with a missing parent fails `valid?`/`save` (returns false) with a "must exist" error, and `save!` raises `ActiveRecord::RecordInvalid`. - id: ror-activerecord-02
  answer: |
    `has_and_belongs_to_many` is a direct many-to-many through a bare join table with no join model: no primary key, no validations, no callbacks, no `created_at`, no way to store extra attributes on the join, and no first-class record you can query. `has_many :through` goes through a real model (e.g. `has_many :tags, through: :taggings`), so the join is a full ActiveRecord model that can hold its own attributes, validations, callbacks, scopes, and dependent behavior — and you can build association chains across multiple joins. Reach for `has_many :through` in essentially every real case; use HABTM only for a dead-simple, attribute-free, never-queried join table (and even then `has_many :through` with a join model is usually worth it).

- id: ror-activerecord-03
  answer: |
    `dependent: :destroy` — Rails loads each child and calls `destroy` on it, so `before_destroy`/`after_destroy` callbacks run, each child's own `dependent:` chains cascade, and validations... (destroy skips validations but runs callbacks). Complete lifecycle, but slow: one destroy per row.
    `dependent: :delete_all` — a single SQL `DELETE` for all children, no model instantiation, no callbacks, and no per-child dependent cleanup (a grandchild's `:nullify`/`:destroy` is skipped). Fast and blunt; correct only when children have nothing to run.
    `dependent: :nullify` — a single `UPDATE ... SET fk_id = NULL`; children survive as orphans. Also skips callbacks and requires the FK column to be nullable.
    (Also exist: `:restrict_with_exception` / `:restrict_with_error`, which raise when children are present.) If you declare no option, children are simply left pointing at a row that no longer exists — nothing is cleaned up.

- id: ror-activerecord-04
  answer: |
    `validates :email, uniqueness: true` is application-level only: on save it runs a `SELECT` to check, and then inserts — a classic TOCTOU race, so two concurrent requests can both pass the check and both insert. It is also database-collation-dependent (it may or may not treat `"A@x.com"` and `"a@x.com"` as duplicates), and it costs a query per save. You must add a unique index on the column — `add_index :users, :email, unique: true` — which is the only thing that actually guarantees uniqueness (the validation then just gives users a nice error message instead of a raw `RecordNotUnique`). For case-insensitive uniqueness, add a functional index on `lower(email)` (Postgres) or use `citext`.

- id: ror-activerecord-05
  answer: |
    `normalizes` (Rails 7.1) declares a normalization for an attribute at the type layer: `normalizes :email, with: -> email { email.strip.downcase }`. The block is applied wherever the attribute is cast — on assignment, on read from the database (so existing rows are normalized lazily without a data migration), and for values used to build queries (`where`/`find_by`). Better than `before_save` because: (1) the in-memory object is correct immediately after `user.email = " X@Y.COM "`, so validations, comparisons, and queries all see the normalized value; (2) it covers every path that touches the attribute (new records, updates, seeds, imports) rather than only persistence; (3) `before_save` only fires on `save`, runs on every save even when that attribute didn't change, races with other callbacks and dirty tracking, and can never help before you query the record.

- id: ror-querying-01
  answer: |
    All three eliminate the N+1, but the SQL differs. `preload` always issues separate queries: one for the base records, then one `SELECT ... WHERE fk IN (...)` per association. `eager_load` forces a single query with `LEFT OUTER JOIN`, returning base+associated rows and instantiating both object graphs — use it when you must filter or order by the joined table's columns. `includes` is Rails choosing for you: it uses the preload strategy by default and falls back to `eager_load`'s JOIN when you reference the joined table in the SQL (`User.includes(:posts).where(posts: { draft: false })` or `references(:posts)`). Preload is usually faster and more predictable (JOINs can multiply rows); `strict_loading` raises if an association you forgot is lazily loaded.

- id: ror-querying-02
  answer: |
    That's the N+1 query problem: 1 query fetches the posts, then 1 query per post (N of them) fetches each author. Fix it in the controller (or a model scope) by eager loading the association before the view runs: `@posts = Post.includes(:author)` — exactly 2 queries instead of N+1 (`preload`/`eager_load` work too). The Bullet gem detects N+1s (and unused eager loads) in development so they're caught instead of guessed. In the view you can't "fix" it reliably — if the relation is already loaded there, `includes` is a no-op — so the query must be built upstream.

- id: ror-querying-03
  answer: |
    `find` looks up by primary key and returns the record itself — `find(1)` or `find([1,2])` — raising `ActiveRecord::RecordNotFound` when nothing matches. `find_by` takes attribute conditions and returns the first matching record or `nil` (`find_by!` raises `RecordNotFound` instead); it's essentially `where(...).first` with `LIMIT 1`. `where` returns an `ActiveRecord::Relation` — lazy (no query yet), chainable, and an empty relation (not `nil`, no exception) when nothing matches; the DB is hit only when the relation is used. So: `find`/`find_by` give you one object or raise/`nil`; `where` gives you a composable set.

- id: ror-querying-04
  answer: |
    `User.pluck(:email)` pushes the projection into SQL (`SELECT "users"."email" FROM "users"`) and returns a plain array of just that column's values. It never instantiates `User` objects, so there's no object allocation, no callbacks, no hydration of unused columns, and memory stays flat regardless of row count. `User.all.map(&:email)` does `SELECT *`, builds one fully initialized AR object per row (all columns) in memory, then throws them away after reading one attribute — far slower, and it can exhaust RAM loading an entire table at once. `pluck(:id, :email)` even returns arrays of arrays for multiple columns. Rule: `pluck` when you need values, not records.

- id: ror-callbacks-transactions-01
  answer: |
    Any hook other than an `*_commit` one runs while the save's database transaction is still open. If you enqueue the job in `after_save`/`after_create` and the transaction later rolls back — a later statement in the same transaction fails or another callback raises — the job has already been handed to the queue and will run against a record that never committed: the worker hits `RecordNotFound`, or worse, you call an external API about state that doesn't exist, which you can't take back. `after_commit` fires only after the outermost transaction has actually committed (variants: `after_create_commit`, `after_update_commit`, `after_destroy_commit`), so external side effects only fire on durable data. Caveat for tests: transactional fixtures mean `after_commit` doesn't fire in tests unless you disable the fixture transaction (older Rails needed the `test_after_commit` gem).

- id: ror-callbacks-transactions-02
  answer: |
    Both run validations and callbacks inside a transaction. `save` returns `true` on success and `false` when a validation fails (no exception raised), so a controller can branch and `render :new`. `save!` raises instead: `ActiveRecord::RecordInvalid` on validation failure (the exception carries `record`, so `e.record.errors` is available) and `ActiveRecord::RecordNotSaved` when a callback halted the chain via `throw :abort`. `create`/`create!` and `update`/`update!` follow the same pattern. Rule of thumb: bang versions in seeds, scripts, jobs, and tests where failure is exceptional and you want it loud; non-bang in controllers where a `false` return is a normal request flow.

- id: ror-callbacks-transactions-03
  answer: |
    Raising any exception inside the block rolls the transaction back and re-raises. `raise ActiveRecord::Rollback` is the special case: it rolls the transaction back but Rails swallows it internally, so execution continues after the block normally instead of an exception bubbling to the caller — use it when the rollback is an expected outcome, not an error. Two caveats: nested `transaction` blocks are not real savepoints unless you pass `requires_new: true`, so a `Rollback` deep inside a nested block can take the whole outer transaction down with it (use `requires_new: true` when you need a genuinely independent inner block); and a rolled-back transaction skips any `after_commit` callbacks, by design.

- id: ror-callbacks-transactions-04
  answer: |
    For `record.save` on a new record the order is: `before_validation` → validators run (`valid?`) → `after_validation` → `before_save` → `before_create` → INSERT → `after_create` → `after_save` → `after_commit` (once the enclosing transaction commits; `after_create_commit`). For an existing record the create triple is replaced by `before_update` → UPDATE → `after_update`. Heavy callbacks are a design smell because the model's behavior stops being readable from its public API: `save` can quietly send mail, charge cards, and mutate other models; the effects fire on every save regardless of whether the relevant attribute changed; ordering between callbacks from different sources becomes invisible coupling; tests need heavy fixtures to touch the object; and external side effects dragged inside the DB transaction can't be rolled back. Keep callbacks for invariants intrinsic to the record (normalizing, maintaining a counter/denormalization) and push coordination to service objects and `after_commit`/ActiveJob.

- id: ror-migrations-schema-01
  answer: |
    A single `change` works when every command in the migration is one ActiveRecord knows how to invert — the `CommandRecorder` records the operation and replays its inverse on rollback: `create_table`, `drop_table`, `add_column`, `add_index`, `add_reference`, `add_timestamps`, `add_foreign_key`/`remove_foreign_key`, `change_column_default`, `change_column_null`, `enable/disable_extension`. You need explicit `up`/`down` (or a `reversible do |dir| ... end` block) whenever the migration has no recoverable inverse: raw `execute` SQL, data backfills and transformations, anything where "down" requires knowing a value Rails can't infer (e.g. `remove_column` without recording the column type), or renames/irreversible data changes. If Rails can't invert it, `db:rollback` raises `ActiveRecord::IrreversibleMigration` — so write `up`/`down` deliberately rather than discovering it later.

- id: ror-migrations-schema-02
  answer: |
    `schema.rb` is a Ruby DSL snapshot (`ActiveRecord::Schema.define(version: ...)`) dumped from your migrations via the adapter API: adapter-agnostic, human-readable diffs, easy to merge, and it's what `db:schema:load` restores on fresh databases and CI. `structure.sql` is a raw dump executed by the database's own tooling (`pg_dump` for Postgres) after setting `config.active_record.schema_format = :structure`. Switch to `:structure` when your schema contains things the Ruby schema cannot express: database extensions, views, materialized views, functions, triggers, custom/enum types, check constraints, DB-function defaults, security policies — otherwise `db:schema:load` silently drops them. Trade-offs: heavier, noisier diffs and merge conflicts, and it requires the DB client tools available when dumping/loading.

- id: ror-migrations-schema-03
  answer: |
    Two classics on a large production table (Postgres):
    1) `add_index` — a plain `CREATE INDEX` takes a SHARE lock that blocks `INSERT`/`UPDATE`/`DELETE` for the whole build; on a big table that's minutes of blocked writes plus a pile-up of queued queries. Safe version: `add_index :table, :col, algorithm: :concurrently`, which requires `disable_ddl_transaction!` in the migration (CONCURRENTLY can't run inside a transaction); keep in mind it can leave an `INVALID` index if it fails, which you must drop and retry.
    2) A column type change (`change_column`) rewrites the entire table while holding an exclusive lock. Safe version is expand/contract: add a new column of the target type, backfill it in batches with a background job (`find_each`), verify, then flip the application to read/write the new column in a separate deploy, add constraints safely (`NOT NULL` via a `CHECK ... NOT VALID` then `VALIDATE CONSTRAINT`), and drop the old column in a later deploy.
    Related traps: adding `NOT NULL` with a default on old Postgres rewrites tables, and removing/renaming a column while older app instances are still running breaks them mid-deploy. The `strong_migrations` gem flags these.

- id: ror-migrations-schema-04
  answer: |
    It generates a `comments.post_id` column (bigint, named from the reference) plus a foreign-key constraint pointing at `posts(id)`. Options shape it further: `polymorphic: true` produces `post_type` + `post_id` (with a composite index) instead, `null: false` adds the NOT NULL, and `index: true` adds an index — the FK does not create the index for you (except automatically for polymorphic references). Why both: the FK enforces referential integrity in the database, which model-level associations and validations cannot guarantee (races, console edits, stale records all bypass them), and it lets the DB enforce behavior on deletes (`on_delete: :cascade/nullify/restrict`). And the FK column must be indexed because every join/lookup goes through it, and when a parent row is deleted or updated the database must scan the child table for rows referencing it — without an index that's a full table scan per parent delete, holding locks that block the child table (Postgres does not index FK columns automatically). So `add_reference :comments, :post, null: false, foreign_key: true, index: true`.

- id: ror-controllers-routing-01
  answer: |
    `resources :photos` declares the seven RESTful routes: `GET /photos` → `photos#index`, `GET /photos/new` → `new`, `POST /photos` → `create`, `GET /photos/:id` → `show`, `GET /photos/:id/edit` → `edit`, `PATCH/PUT /photos/:id` → `update`, `DELETE /photos/:id` → `destroy`. Named helpers come along for free: `photos_path`, `new_photo_path`, `photo_path(@photo)`, `edit_photo_path(@photo)`. You can trim it with `only:`/`except:`, nest it inside another resource, and add extra `member`/`collection` routes. If a mapped action doesn't exist on the controller, dispatch fails with `ActionNotFound` (404 in production). `resource :photo` (singular) would declare the same routes without `:id` and without an index route.

- id: ror-controllers-routing-02
  answer: |
    They solve mass assignment: in the old style `User.new(params[:user])` trusted the whole incoming hash, so a client could submit `user[admin]=1` or any other column and set attributes the form never offered — a privilege-escalation bug. Strong Parameters moves the whitelist decision to the controller, which is the layer that knows what a given request should legitimately change. `params.require(:user)` asserts the payload shape: it raises `ActionController::ParameterMissing` (a 400 response) unless the `:user` key is present — fail fast instead of silently permitting nothing. `.permit(:name, :email)` then filters the nested hash down to exactly those scalar keys and returns a `Parameters` object marked permitted, which you pass to the model (`User.new(user_params)`). Anything not listed is stripped, nested structures are declared by shape (`permit(address: [:city, :zip], tags: [])`), and passing un-permitted params into mass assignment raises `ForbiddenAttributesError`. `permit!` whitelists everything — write it down whenever you see it in review.

- id: ror-controllers-routing-03
  answer: |
    `before_action :authenticate` runs that filter method before the action executes (with `only:`/`except:` scoping; related hooks `after_action`, `around_action`, `prepend_before_action`; filters are inherited by subclasses and can be removed with `skip_before_action`). Typical uses: auth checks, loading a shared resource, setting the layout. If the filter calls `render` or `redirect_to`, the filter chain halts and the action method never runs — the response is exactly what you rendered or redirected to. Note the rule since Rails 5: returning `false`/`nil` from a filter no longer halts anything; only `render`/`redirect_to` (or `throw :abort`) stops the chain. So `def authenticate; redirect_to login_path unless current_user; end` both protects the action and defines the response in one line.

- id: ror-controllers-routing-04
  answer: |
    `member` routes act on one existing resource and always carry the `:id`: inside `resources :photos do; member { get :preview }; end` you get `GET /photos/:id/preview`, helper `preview_photo_path(@photo)`, dispatched to `PhotosController#preview`. `collection` routes act on the whole collection and have no `:id`: `collection { get :search }` → `GET /photos/search`, helper `search_photos_path`, handled by `PhotosController#search`. A successful API `create` should return `201 Created` — that's what `rails g scaffold --api` generates (`render json: @photo, status: :created, location: @photo`), ideally with a `Location` header pointing at the new resource; HTML creates redirect (302) to the created record instead.

- id: ror-controllers-routing-05

Reach for Devise when you want those batteries included; use the built-in generator when transparent email/password auth you can read and extend is enough.

- id: ror-views-helpers-01
  answer: |
    Pass locals: `render partial: "shared/header", locals: { title: "Hello" }` or the shorthand `render "shared/header", title: "Hello"`; inside the partial you reference the plain local variable `title` (referencing a local that wasn't passed raises `NameError`). When you pass a variable named after the partial you can shorten further — `render partial: "photo", photo: @photo`, and `render @photo` infers the partial and local from the object (`_photo.html.erb`, local `photo`). `render @posts` renders the partial once per post in the collection (equivalently `render partial: "posts/post", collection: @posts`), naming each local `post` (rename with `as: :item`); it's efficient because it renders the same partial per element, supports a spacer template, and — crucially — plugs into collection caching so each element's fragment is cached under its own key, meaning re-rendering the list only re-renders records that actually changed.

- id: ror-views-helpers-02
  answer: |
    `form_with` unifies `form_for` (model-backed) and `form_tag` (URL-only): one helper that binds to a model (`form_with model: @post` — URL, HTTP method and param namespacing inferred from the record) or takes an explicit `url:`, spoofing PATCH/PUT/DELETE through the hidden `_method` field for browsers that can't send them, auto-switching to `multipart/form-data` when the form contains a file field, and emitting the CSRF token for you. In current Rails it generates a LOCAL, standard HTML form — no `data-remote` attribute. That changed over time: it debuted in Rails 5.1 defaulting to remote (Rails-UJS AJAX) forms, 5.2 added `local: true`, and since the 6.1 framework defaults (`config.action_view.form_with_generates_remote_forms = false`, with the UJS machinery removed entirely in Rails 7) local is the default. Even so, Turbo Drive intercepts local form submissions, so they still submit without a full page reload without you writing JS.

- id: ror-views-helpers-03
  answer: |
    Rails uses the per-session authenticity token: with `protect_from_forgery` (default in modern Rails; `strategy: :exception` in ApplicationController), each request has a session-derived token, and any non-GET request must present a valid one or Rails raises `ActionController::InvalidAuthenticityToken` (→ 422). `form_with` does this automatically — it embeds a hidden `authenticity_token` field in every form it builds (a per-form masked token since Rails 5, so tokens are single-use and not replayable across forms). You only handle the token yourself when Rails' helpers aren't involved: hand-written forms need `<%= hidden_field_tag :authenticity_token, form_authenticity_token %>`, and `fetch`/XHR posts must send it in the `X-CSRF-Token` header, commonly read from the `<meta name="csrf-token">` Rails puts in the layout. `SameSite=Lax` cookies (default) add a second layer of mitigation; GET requests are deliberately exempt because they must be side-effect free.

- id: ror-views-helpers-04
  answer: |
    In the controller (or a model scope like `Post.with_authors`) — wherever the query is assembled, before the view ever sees it: `@posts = Post.includes(:author)`. The controller's job is to prepare exactly the data the view needs; the view's job is presentation. "Fixing" it in the view is wrong even when it appears to work: the same partial is rendered by other actions, callers, and cache warmers that would each need the identical patch; eager loading is per-render state, so a view-level `includes` silently stops working the moment the relation was already loaded (calling `includes` on a loaded relation no-ops and the lazy per-row queries still fire); and it puts a query-cost concern in the least testable layer, where it's invisible until production. Let the view declare data needs (touch the association), let the query layer satisfy them once, and use Bullet in development to find the N+1s.

- id: ror-concerns-services-01
  answer: |
    `ActiveSupport::Concern` is the supported wrapper for building mixin modules: it provides dependency tracking (a module that does `include SomeOtherModule` will, when itself included, drag that dependency in too) and the `class_methods do ... end` hook, which makes those methods available as class-level methods on the including class. The `included do ... end` block runs inside the including class via `class_eval` at include time, so the module can add `belongs_to`/`has_many`, `validates`, `scope`s, `has_secure_password`, `before_action` (in controller concerns), and any other class-level DSL. A plain module mixed in with `include` can only contribute instance methods cleanly — to add class macros the includer must `extend` a `ClassMethods` submodule by hand and dependencies must be repeated in every including class, which is exactly the boilerplate Concern removes.

- id: ror-concerns-services-02
  answer: |
    A service object is a plain PORO that performs one domain action or use case — typically `Service.new(inputs).call` with a single public entry point (and often a `Result` value object, `result.success?`). Extract one when the logic is a verb rather than a property of one record: it spans multiple models or an external system (`PlaceOrder` touching orders, payments, inventory and mail), it's a workflow with a transaction that would otherwise be a long private method in the controller, or you're about to put a method on a model only because one controller needs it. Keep it boring on the outside: plain inputs in, a result or value out, expected failures expressed as a failed result rather than an exception, no base-class or generator infra beyond what earns its keep. The controller then stays a thin HTTP adapter: parse/authorize params → call the service → render the response.

- id: ror-concerns-services-03
  answer: |
    The guideline: controllers should be thin — authenticate/authorize params, delegate one call, choose the response — while models own validations, associations, scopes and business rules. Taken too far it yields god models: a 1000-line `User` that knows about orders, billing, notifications and logins; callback chains so interdependent that any `save` can trigger ten other things you can't see from the caller; models that can't be understood by reading a method because the real behavior is in `after_save`; and test suites that need heavy fixtures just to touch the object. The modern correction: don't relocate the bloat from controller into model — keep ActiveRecord models close to persistence plus row-level invariants, and let the model LAYER be rich while the model file stays small: service objects for cross-record actions, concerns for behavior genuinely shared across classes, query objects and value objects where they clarify.

- id: ror-concerns-services-04
  answer: |
    A concern is mixed in — it extends what a class and its instances can do, so it's about shared capability across a family of similar classes (code reuse by trait: `Taggable`, `Archivable`), and it usually depends on state/methods the including class provides. A service object is instantiated and called — it performs one specific action for explicit inputs, coordinating whatever models it needs and returning a result, with its dependencies handed to it. Practically: if the logic answers "what can this object do?", it belongs on the model as private methods or a concern; if it answers "what should happen when the system does X?" and X touches orders, payments, mailers and three tables, it's a service. Different failure modes too: concerns creep into cross-cutting magic that surprises everyone who later reads the model, while services can become the dumping ground for anything that wasn't obviously a model method — used well, concerns stay local to the includer's state and services stay independently testable and callable from controllers, jobs, and the console.

- id: ror-caching-jobs-01
  answer: |
    Russian-doll caching is nested fragment caching: an outer cache (a collection or the whole page fragment) with a separately cached inner fragment per record — when one post changes, only that inner fragment (`cache @post`) is invalidated and rebuilt, while the unchanged siblings' fragments are reused from cache even while the outer layer re-renders. Using the record in the key is what makes invalidation automatic: `cache @post` builds the key from `@post.cache_key_with_version`, i.e. `posts/#{id}-#{updated_at}` (+ the record's cache version), so the moment the record is saved the key changes and the stale fragment is simply never looked up again — no `expire` call anywhere, no manual bookkeeping, and old fragments fall out naturally under the cache's LRU. Two requirements: every input that changes the rendered output must participate in the key (`cache [post, post.author]` if the author's name renders inside, `touch: true` on associations so a new comment bumps the parent's `updated_at`), otherwise the cache serves stale HTML.

- id: ror-caching-jobs-02
  answer: |
    ActiveJob is Rails' framework-level API for background work: one place to declare jobs (`ApplicationJob`, `queue_as`, `retry_on`/`discard_on`, job callbacks), to enqueue them (`perform_later`, `set(wait:).perform_later`, `set(queue:).perform_later`), and to run them, so job code stays backend-agnostic and moves between backends unchanged. The queue adapter (`config.active_job.queue_adapter`) is the pluggable bridge to a specific backend — Sidekiq, Resque, Que, Delayed Job, Good Job, Solid Queue, plus the in-memory `:async` and the test-only `:test` adapter — and it is what actually serializes args, transports the job, and provides workers/retries. The default adapter is `:async`: an in-process thread pool with no persistence, so queued jobs vanish on restart/deploy, there's no real worker, no durability, no cross-process visibility — fine for development and tests, not suitable for production. (New Rails 8 apps are generated pointing production config at Solid Queue, but the choice is still yours.)

- id: ror-caching-jobs-03
  answer: |
    Because delivery is at-least-once: a worker can crash after performing the side effect but before acking, brokers redeliver on timeouts, `retry_on` storms re-run failed jobs, and upstream double-enqueue happens too — so the same job can legitimately run twice, and a job that "charges 20", "sends the welcome email" or "increments a counter" produces double charges, duplicate emails and skewed totals. Make it idempotent by computing end state instead of applying deltas: write final values rather than incrementing; guard with the database, not a read-then-write check (upsert on a business key, `find_or_create_by` backed by a unique index, or a guard row whose unique constraint raises on replay and gets rescued); for external APIs pass the provider's idempotency key (Stripe's `Idempotency-Key`) or check the remote state first (`return if user.fulfilled?`). Design each job so that running it twice leaves the same terminal state — a retry should be a no-op, not a duplicate effect.

- id: ror-caching-jobs-04
  answer: |
    `perform_later` enqueues the job onto the configured adapter for asynchronous execution by a worker process; `perform_now` runs it inline, synchronously, in the current process and thread immediately — used in tests, rake tasks, the console, and any path that must complete the work before returning. Pass a record's id rather than the record because queue payloads are serialized and shipped to another process at an unpredictable future time: ActiveRecord objects can't round-trip safely as arguments, an id keeps the payload tiny, and it forces `perform` to load fresh state from the database instead of trusting a snapshot captured at enqueue time (the record may have been changed — or deleted — while the job sat in the queue). ActiveJob's GlobalID feature lets you pass an object and serializes its id under the hood, but the reasons are the same; handle the missing case (`discard_on ActiveRecord::RecordNotFound`) so a retry doesn't spin forever on a deleted record.
