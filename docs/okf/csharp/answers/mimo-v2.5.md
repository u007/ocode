- id: csharp-null-01
  answer: |
    Nullable reference types provide compile-time warnings about potential null dereferences. They do not change the runtime representation — a string? and a string are both still reference types at runtime. The `?` annotation on a reference type declares that null is a valid value and instructs the compiler to emit warnings if that value is used without a null check. The `!` (null-forgiving) operator suppresses the compiler's null warning for a specific expression, telling the compiler "I know this isn't null" — it has no runtime effect. `#nullable enable` turns on nullable analysis for the file or project; `#nullable disable` turns it off. When enabled, non-annotated reference types are treated as "oblivious" or "not null" depending on context, and the compiler warns on possible null assignments and dereferences.

- id: csharp-null-02
  answer: |
    Value types (structs, enums, primitives like int, double) are stored on the stack (or inline in other objects) and are copied by value. Reference types (class instances, arrays, delegates, strings) are heap-allocated and variables hold a reference (pointer) to the object. The surprising mutation behavior: structs are value types, so when you store a struct in a readonly field or in a collection like List<T>, the collection/field holds a copy. Mutating that copy via a method call (e.g., `readonlyField.DoSomething()` where DoSomething mutates internal state) will either fail to compile (for readonly fields, the compiler returns a defensive copy) or silently mutate only a copy (for collection indexing — `list[0].X = 5` compiles but the mutation is lost because indexing returns a copy). To mutate structs in collections you need to reassign the entire struct (e.g., `list[0] = new Point(1,2)`) or use ref returns.

- id: csharp-null-03
  answer: |
    A `record` (record class) is a reference type with built-in value-based equality (Equals, ==, !=, GetHashCode are synthesized comparing all properties/fields), a deconstruct method, a printMembers method, and a `with` expression for non-destructive mutation. It is mutable by default unless properties are `init`-only. A `record struct` is a value type with the same synthesized value-based equality and `with` support; it is mutable by default (though you can make it `readonly record struct`). A plain `class` uses reference equality by default (same object identity) and has no built-in equality, deconstruction, or `with` support unless you implement them yourself. Key distinction: record equality compares all members structurally; class equality compares object identity. Records also get `EqualityContract` for polymorphic equality. Mutability: records are not inherently immutable — you must use `init` or `readonly` to enforce immutability.

- id: csharp-null-04
  answer: |
    `init`-only properties (C# 9+) allow a property to be set only during object initialization or within a constructor, but never afterward. After construction, the property is immutable. `required` members (C# 11+) require that the consumer must set the member during object initialization — the compiler produces an error if it is not set. They combine powerfully: a `required init` property must be set at construction time and then cannot be changed afterward, giving you immutable objects with guaranteed initialization. Without `required`, init-only properties can be left unset (defaulting to default(T)), which may be undesirable. Together they enforce both completeness and immutability at compile time.

- id: csharp-pattern-01
  answer: |
    A switch statement is a control flow statement that executes a block of code based on matching patterns or values; it requires explicit `break`, `return`, `goto`, or `throw` in each arm (no fall-through in C#). A switch expression is an expression that returns a value — each arm produces a value, there is no fall-through, and the syntax uses `=>` instead of `:` with blocks. A switch expression must be exhaustive (all possible input values must be covered by the arms), or you must include a discard pattern (`_`) as a default. If arms are not exhaustive and there is no discard, the compiler produces a compile-time error (for expressions) or a warning for statements (C# 9+ exhaustiveness checking for switch statements). The switch expression is often more concise and enforces completeness.

- id: csharp-pattern-02
  answer: |
    Property patterns match on properties of the input using `{ Property = subPattern }` syntax. For example: `obj is { Name: "foo", Age: > 18 }` checks that the Name property equals "foo" and Age is greater than 18. You can nest sub-patterns. Positional patterns match using the Deconstruct method of a type. For example: `point is ( > 0, > 0)` matches a point where both x and y are positive (assuming Deconstruct returns two values). You can name the deconstructed values: `point is (var x, var y)`. Both property and positional patterns can bind values using `var`: `{ Name: var n }` binds n to the Name value. Property patterns use recursive pattern matching, so each property value can itself be a nested pattern.

- id: csharp-pattern-03
  answer: |
    Relational patterns use comparison operators to match values: `> 0`, `< 100`, `>= 18`, `<= 65`. They are used in pattern matching contexts like switch expressions or `is` expressions. Logical patterns combine patterns using `and`, `or`, and `not`. For example: `> 0 and < 100` matches values between 0 and 100; `not null` matches non-null; `A or B` matches if either A or B matches. List patterns (C# 11+) match arrays/lists/collections against a sequence of element patterns: `[1, 2, 3]` matches a three-element collection with those values; `[_, var second, ..]` matches any first element, binds the second, and discards the rest; `[1, .., 100]` matches a sequence starting with 1 and ending with 100 (with any elements in between via the slice pattern `..`).

- id: csharp-pattern-04
  answer: |
    `obj is Customer c` performs a type check AND a cast in one operation, binding the result to variable `c` of type `Customer`. If obj is null or not a Customer, c is assigned null (for reference types) and the pattern doesn't match. A plain type check plus cast (`obj is Customer && (Customer)obj == ...`) requires two separate operations and you'd need to cast again to use the value. The `is` declaration pattern is more concise and avoids the double-cast. The bound variable `c` is in scope only within the pattern's scope — for `if (obj is Customer c) { ... }` it is in scope inside the if-block; for switch arms it is in scope within that arm; for `obj is Customer c && c.Name == "foo"`, c is in scope in the subsequent conditions and the if-body.

- id: csharp-linq-01
  answer: |
    Deferred execution means the query is not executed when it is defined but rather when the results are enumerated (iterated). Immediate execution means the query runs at the point the method is called and returns results (or a scalar). Deferred operators include: Where, Select, SelectMany, OrderBy, ThenBy, GroupBy, Join, Zip, Take, Skip, Distinct, Union, Concat, AsEnumerable, and most query-producing methods. Immediate operators include: ToList, ToArray, ToDictionary, ToLookup, Count, LongCount, Any, All, First, FirstOrDefault, Last, LastOrDefault, Single, SingleOrDefault, Min, Max, Sum, Average, Aggregate, Contains, ElementAt, ElementAtOrDefault, SequenceEqual. With deferred execution, re-enumerating the query re-executes it; with immediate execution, the results are materialized once.

- id: csharp-linq-02
  answer: |
    `IEnumerable<T>` executes queries in-memory on the client side — the entire result set is fetched and then filtered/processed locally. `IQueryable<T>` translates the query into an expression tree that is evaluated on the server side (e.g., translated to SQL by an ORM like Entity Framework). The query provider builds the expression tree and optimizes it. The danger of mixing: if you fetch an `IQueryable<T>` as `IEnumerable<T>` (e.g., by calling `.AsEnumerable()` or using a method that forces client evaluation) and then apply further LINQ operators, those operators run in-memory rather than being translated to SQL. This can cause massive performance issues — for example, loading an entire table into memory to filter one row. Conversely, applying IQueryable-specific operations after materializing to IEnumerable won't compile. The key is to keep the IQueryable chain intact as long as possible so the provider can optimize the full query.

- id: csharp-linq-03
  answer: |
    Re-enumerating the same LINQ query variable executes the query again each time because most LINQ operators use deferred execution. If the query involves a database, network call, or file read, each enumeration triggers a new round-trip or I/O operation, which is wasteful and may return different results if data has changed. Additionally, if the source is non-repeatable (e.g., a network stream), re-enumeration may fail or produce unexpected results. To avoid this, materialize the query by calling `.ToList()`, `.ToArray()`, or another immediate operator after constructing the query. This executes the query once and stores the results in a concrete collection that can be enumerated multiple times without re-executing the underlying source.

- id: csharp-linq-04
  answer: |
    `First()` returns the first element of a sequence and throws `InvalidOperationException` if the sequence is empty. `FirstOrDefault()` returns the first element or `default(T)` if the sequence is empty — for reference types, `default(T)` is `null`; for value types, it is `default(TValue)` (e.g., 0 for int, false for bool, DateTime.MinValue for DateTime). `Single()` returns the only element and throws if the sequence has more than one element or is empty. `SingleOrDefault()` returns the only element, default(T) if empty, or throws if more than one. The value-type gotcha with `FirstOrDefault`: since default(int) is 0, you cannot distinguish between "the first element was 0" and "the sequence was empty." If your domain uses 0 or false as valid values, consider using `First()` (which throws on empty) or `TryFirst()` patterns, or use nullable value types with `FirstOrDefault`.

- id: csharp-async-01
  answer: |
    Return `ValueTask<T>` instead of `Task<T>` when the operation is likely to complete synchronously most of the time, avoiding the heap allocation of a Task object. ValueTask is a struct, so it avoids boxing and GC pressure when the result is available synchronously. Use it in high-performance, hot-path code where the sync completion is common (e.g., reading from a buffer that may already have data). Rules for consuming ValueTask: you may only await it once — after that the result has been consumed. You must not call .Result, .Wait(), .GetAwaiter().GetResult(), .ContinueWith(), .Result, or store it in a variable and await it later (unless you use .Preserve() or call .AsTask() first). You must not await it in multiple concurrent awaits. In short: ValueTask is designed for a single consume; if you need to consume multiple times, convert to Task first via .AsTask().

- id: csharp-async-02
  answer: |
    The compiler transforms async methods into a state machine that captures the execution context, suspend points at each await, and resumes on the continuation. When an await is reached, if the awaited task is not completed, the method returns (as an incomplete Task) to the caller and registers a continuation to resume when the task completes. The state machine handles moving between states (not started, running, completed). Blocking on an async call with `.Result` or `.Wait()` causes a deadlock in contexts with a SynchronizationContext (e.g., WPF, WinForms, ASP.NET classic). The async method posts its continuation back to the captured SynchronizationContext, but the original thread is blocked waiting for the task to complete, creating a circular wait: the continuation can't run because the thread is blocked, and the thread can't proceed because it's waiting for the task. On thread pool threads (console apps) there is no SynchronizationContext, so this deadlock does not occur, but blocking is still discouraged as it wastes a thread.

- id: csharp-async-03
  answer: |
    `ConfigureAwait(false)` tells the awaiter not to capture the SynchronizationContext, so the continuation runs on the thread pool rather than posting back to the original context. In library code, this is recommended because libraries should not assume they need to run on a particular thread — they don't have UI or request contexts. This avoids deadlocks when library code is awaited from contexts with a SynchronizationContext (e.g., if the caller blocks with `.Result`). It also avoids unnecessary context-switch overhead. In application code (UI controllers, page handlers) you typically do NOT use ConfigureAwait(false) because you need to return to the UI thread. Starting with .NET 8, the default behavior in ASP.NET Core has changed, and ConfigureAwait(false) is less critical in that context, but it remains best practice for reusable libraries.

When the source's Cancel() is called, all registered callbacks fire and tokens enter the canceled state. Methods should check the token and either throw OperationCanceledException or return gracefully. `IAsyncEnumerable<T>` is the async equivalent of IEnumerable<T>, representing a sequence of values that can be produced asynchronously (e.g., reading rows from a database cursor, streaming data). `await foreach` is the syntax for consuming IAsyncEnumerable<T> — it asynchronously iterates over the sequence, awaiting each element as it becomes available. This enables streaming patterns where data is produced and consumed asynchronously.

- id: csharp-generics-01
  answer: |
    A `where` constraint on a type parameter restricts what types can be used as that generic argument. Main kinds: `where T : class` — T must be a reference type; `where T : class?` — reference type or nullable (C# 9+); `where T : struct` — T must be a non-nullable value type; `where T : struct?` — T must be a nullable value type; `where T : notnull` — T must be a non-nullable type; `where T : new()` — T must have a public parameterless constructor; `where T : U` — T must derive from or implement U (type constraint); `where T : delegate` — T must be a delegate type; `where T : unmanaged` — T must be an unmanaged type (no reference types, no pointers, no type parameters); `where T : default` — allows unconstrained type parameters to be used where constraints are needed (C# 7.3+); `where T : allows ref struct` — permits ref structs in generic contexts (C# 13+). Constraints enable the compiler to generate code that assumes certain capabilities (e.g., calling methods on T, boxing/unboxing).

- id: csharp-generics-02
  answer: |
    Generic variance applies to generic interfaces and delegates with a single type parameter. `out` marks a type parameter as covariant: the interface/delegate can be used where the type parameter appears only in output (return) positions. This means `IEnumerable<Dog>` can be assigned to `IEnumerable<Animal>` because Dog derives from Animal and the type only produces values. `in` marks a type parameter as contravariant: the type parameter appears only in input (parameter) positions. This means `IComparer<Animal>` can be assigned to `IComparer<Dog>` because if you can compare any Animal, you can compare a Dog. Variance only applies to interfaces and delegates, not classes, structs, or methods. The type parameter must be used only in the designated position (out for covariant, in for contravariant) — mixing positions makes the type parameter invariant (neither covariant nor contravariant). Examples: `IEnumerable<out T>`, `Action<in T>`, `Func<in T, out TResult>`.

- id: csharp-generics-03
  answer: |
    Type inference for a generic method works by the compiler examining the arguments passed to the method and inferring the type parameters from them. For example, `void Foo<T>(T x)` called as `Foo(42)` infers T as int. The compiler uses the types of all arguments and sometimes the return type (in C# 10+ with natural types) to find a consistent type assignment. You must specify type arguments explicitly when: (1) the compiler cannot uniquely determine the type from the arguments alone, (2) you want a different type than what would be inferred (e.g., `Enumerable.Empty<int>()` where no arguments are provided), (3) the method has constraints that the inferred type does not satisfy, (4) there is ambiguity in the inference, or (5) you are calling a method where the type parameter does not appear in any parameter (e.g., `default(T)` usage or static methods with no parameters). You specify them with angle brackets: `Foo<int>(42)`.

- id: csharp-generics-04
  answer: |
    `default(T)` produces the default value for type T: for reference types it is null; for value types it is the zero-initialized value (0 for numeric types, false for bool, DateTime.MinValue for DateTime, etc.); for nullable value types it is a Nullable<T> with HasValue = false. Generic code needs it because you cannot use `null` for value types, cannot use `0` for reference types, and cannot use `new T()` without a constraint. `default(T)` provides a type-safe way to produce the default value in generic contexts regardless of whether T is a value or reference type. For example, in a method that returns `T` and needs a fallback value, or when initializing a variable of type T where you don't know if T is a reference or value type. Note: `default` without the type parameter (just `default`) infers the type from context, and `new()` constraint allows `new T()` but still requires a parameterless constructor.

- id: csharp-delegate-01
  answer: |
    A delegate is a type-safe function pointer — a reference type that holds a reference to a method (or multiple methods). It defines a signature (return type and parameter types) that the referenced method must match. `Func<T, TResult>` is a built-in delegate type for functions that take 0 or more parameters and return a value. Variants exist: `Func<TResult>` (no parameters), `Func<T, TResult>` (one parameter), up to `Func<T1,...,T16, TResult>`. `Action` is a built-in delegate type for void-returning methods. Variants: `Action` (no parameters), `Action<T>` (one parameter), up to `Action<T1,...,T16>`. `Predicate<T>` is a built-in delegate that takes one parameter and returns bool — used for methods like `List<T>.Find(Predicate<T>)`. All three are just delegate types with predefined signatures; you can define your own delegate types as well, but these built-in ones cover most cases and reduce boilerplate.

- id: csharp-delegate-02
  answer: |
    The `event` keyword restricts access to a delegate field so that outside code can only add (`+=`) or remove (`-=`) handlers, not invoke it, assign to it, or clear it. A plain public delegate field allows any code to invoke it, assign a new delegate (replacing all existing handlers), or set it to null. Events enforce encapsulation: only the declaring class can raise (invoke) the event. Behind the scenes, the compiler generates add/remove accessors that use `Delegate.Combine`/`Delegate.Remove` with thread-safe (volatile read) access. Events also enable the use of event accessors (custom add/remove) for more control (e.g., lazy initialization, logging, synchronization). Without the event keyword, external code could accidentally replace all handlers with a single assignment instead of adding to them.

- id: csharp-delegate-03
  answer: |
    In a `for` loop, the loop variable is captured by reference — all lambdas created in the loop body share the same variable, so they all see the final value of that variable after the loop completes. This is a classic closure pitfall. In a `foreach` loop (C# 5.0+), the loop variable is re-declared for each iteration, so each lambda captures a separate variable and sees the correct per-iteration value — they are safe. In C# 4.0 and earlier, even foreach captured the same variable. The fix for for-loop captures is to declare a local variable inside the loop body and copy the loop variable into it: `for (int i = 0; i < n; i++) { int captured = i; /* use captured in lambda */ }`. In modern C# (12+), `foreach` loop variables are properly scoped per iteration, and some `for` loop scenarios may also be improved, but the explicit capture pattern is still the safest approach.

- id: csharp-delegate-04
  answer: |
    A multicast delegate is a delegate that holds references to multiple methods (combined via `Delegate.Combine` or the `+`/`+=` operators). When invoked, all methods are called in the order they were added. For return values: only the return value of the last method in the invocation list is returned; earlier return values are lost. For exceptions: if any delegate in the invocation list throws an exception, subsequent delegates are not called, and the exception propagates. This can be problematic because an early delegate's exception prevents later delegates from executing. To handle this, you can manually iterate the invocation list using `Delegate.GetInvocationList()` and invoke each delegate individually, catching exceptions per delegate. Multicast delegates are commonly used with events, where multiple handlers subscribe and are all called when the event is raised.

- id: csharp-dispose-01
  answer: |
    `IDisposable` defines a `Dispose()` method for deterministic cleanup of unmanaged resources (file handles, database connections, network sockets, etc.) and any managed resources that need explicit cleanup. It enables the `using` statement/declaration pattern. A `using` statement (traditional) wraps a block of code and automatically calls `Dispose()` on the resource when the block exits (even on exceptions). A `using` declaration (`using var x = ...;`) declares a variable that is disposed at the end of the enclosing scope (the method, block, or property) rather than at the end of an explicit block. Both ensure Dispose is called, but the using declaration is more concise and disposes at scope exit rather than block exit. The using declaration is syntactic sugar — the compiler generates equivalent try/finally code.

- id: csharp-dispose-02
  answer: |
    `IAsyncDisposable` defines `DisposeAsync()` which returns a `ValueTask`, enabling asynchronous cleanup of resources (e.g., closing a network connection asynchronously, flushing an async stream). `await using` is the async equivalent of `using` — it ensures `DisposeAsync()` is called asynchronously at the end of the scope. Use `IAsyncDisposable` and `await using` when disposal itself is asynchronous and you want to avoid blocking the thread. Use `IDisposable` and `using` when disposal is synchronous (most common case — e.g., closing a file handle, releasing a lock). Many types implement both interfaces; the synchronous `using` is preferred when possible, but when working with async I/O streams, HTTP clients with async teardown, or other async resources, `IAsyncDisposable` is necessary.

- id: csharp-dispose-03
  answer: |
    `Dispose()` is called deterministically — either explicitly by the consumer, by a `using` statement/declaration, or by the framework (e.g., ASP.NET). It runs on the calling thread and allows cleanup of both managed and unmanaged resources. A finalizer (`~ClassName`) is called by the garbage collector non-deterministically during garbage collection — you have no control over when (or if) it runs. A type actually needs a finalizer only when it holds unmanaged resources directly (not via wrappers like SafeHandle). If a type only holds managed resources (which themselves implement IDisposable), it should implement IDisposable but not have a finalizer. The finalizer is a safety net to release unmanaged resources if the consumer forgot to call Dispose. Having a finalizer has a performance cost — the object is placed on the finalization queue and requires at least two GC cycles to be collected.

- id: csharp-dispose-04
  answer: |
    The full dispose pattern for a class owning both managed and unmanaged resources: (1) Implement `IDisposable`. (2) Add a protected virtual `Dispose(bool disposing)` method. (3) Add a finalizer (`~ClassName`) that calls `Dispose(false)`. (4) Implement the dispose method: call `Dispose(true)` and suppress finalization via `GC.SuppressFinalize(this)`. (5) In `Dispose(bool disposing)`: when `disposing` is true (called from Dispose()), clean up both managed resources (call Dispose on owned IDisposable objects) and unmanaged resources. When `disposing` is false (called from finalizer), clean up only unmanaged resources — do not touch managed objects as they may already be finalized. (6) Use a disposed flag (`_disposed`) to make Dispose idempotent (safe to call multiple times). (7) For managed resources that are expensive to clean up, also implement `IAsyncDisposable` if asynchronous cleanup is beneficial. The pattern protects against accessing managed objects during finalization (they may already be collected) while ensuring unmanaged resources are always released.

- id: csharp-span-02
  answer: |
    `Span<T>` is a ref struct that provides a type-safe view over a contiguous block of memory (array, stack memory, native memory). It is a lightweight, stack-only type containing a reference and a length. `ReadOnlySpan<T>` is the read-only counterpart — it provides read-only access to a memory region. `Memory<T>` is similar to Span but is a regular struct (not a ref struct), so it can be stored in fields, passed to async methods, and used across await boundaries. Span cannot be stored in a field because it is a ref struct — ref structs are restricted to the stack and cannot be boxed, stored in heap objects, or used in async methods (which may resume on a different thread after an await). The runtime guarantees Span's memory is always valid while the Span is in use, which would be impossible if it escaped to the heap. Memory<T> wraps a MemoryManager<T> and can persist across async boundaries safely.

- id: csharp-span-03
  answer: |
    `stackalloc` allocates memory on the stack instead of the heap, returning a `Span<T>` (or `ReadOnlySpan<T>`) pointing to that memory. It is fast because stack allocation is essentially just moving the stack pointer — no GC overhead. You must be careful about: (1) The memory is only valid for the duration of the current method — it is automatically freed when the method returns. You cannot return it or store it in a field. (2) Stack space is limited (typically 1MB per thread), so large allocations can cause StackOverflowException. (3) Do not use stackalloc in async methods (compiler error — the stack frame may not exist when the continuation resumes). (4) Initialize the memory before use — stackalloc does not zero-initialize in release builds (it does in debug for safety). (5) Be aware of potential security issues with uninitialized stack memory if it could leak sensitive data. (6) In .NET 8+, stackalloc into `Span<T>` or `ReadOnlySpan<T>` is preferred over the older pointer syntax.

- id: csharp-span-04
  answer: |
    An array (`T[]`) is a fixed-size, contiguous collection of elements. Once created, its length cannot change — adding or removing elements requires creating a new array. A `List<T>` is a dynamic, resizable collection backed by an internal array. It supports adding, removing, inserting, and resizing, and automatically grows its internal buffer as needed (typically doubling). Arrays have lower overhead and better performance for fixed-size data; List<T> has convenience methods but slightly more overhead (object header, internal array, count tracking, potential reallocations). `params` collections (C# 12+) allow a method to accept a variable number of arguments of a collection type — e.g., `void Foo(params int[] numbers)` can be called as `Foo(1, 2, 3)` or `Foo(new[] {1, 2, 3})`. In C# 12+, params works with Span<T>, IEnumerable<T>, ReadOnlySpan<T>, and other collection types, not just arrays, enabling `void Foo(params List<int> numbers)` or `void Foo(params ReadOnlySpan<int> numbers)`.
