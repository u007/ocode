- id: csharp-null-01
  answer: |
    Nullable reference types (C# 8) are a compile-time/static-analysis feature, not a runtime one. With the nullable context enabled, the compiler performs flow analysis to track whether a reference may be null and emits warnings (e.g., dereferencing a possibly-null value, assigning null to a non-nullable). The `?` annotation on a reference type has NO runtime effect — it is erased; it only records intent in metadata (attributes/annotations) so the compiler (and other analyzers) can warn. `!` is the null-forgiving operator: it suppresses the compiler's null warning at that expression; again zero runtime effect — if the value IS null at runtime you still get a NullReferenceException. `#nullable enable` turns on the nullable-analysis context for that file or region (`disable`/`warnings`/`annotations` for finer control), so legacy code can be migrated incrementally. Nothing is checked or thrown at runtime by any of these; correctness still depends on you.

- id: csharp-null-02
  answer: |
    Value types (structs, enums, primitives) hold their data inline; assignment/parameter passing copies the whole value. Reference types (classes, arrays, delegates, string) hold a reference to a heap object; assignment copies only the reference, so two variables alias the same object and mutations are visible through both. The surprise: if a struct is stored in a readonly field, the compiler treats the field as immutable and makes a DEFENSIVE COPY before calling any non-trivial method on it — so a method that mutates `this` silently mutates the copy and the change is lost. The same happens through collection indexers/`foreach` because they return a copy of the struct value (e.g., `list[0].X = 5` won't even compile for a method call like `list[0].Mutate()`; the indexer returns a temporary). The usual fixes are making structs `readonly struct` or using `ref`/`ref returns` deliberately.

- id: csharp-null-03
  answer: |
    `record class`: a reference type where the compiler synthesizes value-based equality (Equals/GetHashCode over all instance fields/properties, not identity), value-friendly ToString, a copy constructor and `with` expressions, and (for positional records) init-only properties. Two distinct instances with the same values are Equal, but it's still a mutable-capable reference type unless you use init-only/readonly members. `record struct`: a value type with compiler-synthesized equality (including ==/!= and GetHashCode), also supporting `with` and positional syntax; often declared `readonly record struct` for true immutability; copies like any struct. Plain `class`: reference-equality (identity) by default — two instances with identical data are not equal unless you hand-implement Equals/GetHashCode/IEquatable<T>; mutable by default, no with-support. Summary: records trade in identity semantics for structural semantics, with the reference-vs-copy behavior of their underlying kind.

- id: csharp-null-04
  answer: |
    `init`-only properties can be set only during object creation — in a constructor or an object initializer — and are immutable afterwards; enforcement is via a modreq (IsExternalInit), so older consumers can't set it and later mutation is a compile error. `required` members MUST be initialized in an object initializer (or by a constructor marked [SetsRequiredMembers]); the compiler errors if you create the object without setting them. They compose naturally: `public required string Name { get; init; }` forces callers to supply Name at construction and forbids changing it afterward. Caveat: `required` is enforced by the compiler (with RequiredMemberAttribute metadata); it can be bypassed by reflection-based construction, so serializers/deserializers need special support.

- id: csharp-pattern-01
  answer: |
    A switch expression (`x switch { ... }`) is an expression that produces a value, evaluates arms top-down, and must be EXHAUSTIVE — the compiler errors (CS8509-ish "not exhaustive") unless every possible input is covered, typically by adding a discard arm `_`. It has no fallthrough and no break/return; each arm maps an input (which can itself be a tuple or a pattern) to a result. A switch statement is a statement: cases with break/return/goto, no exhaustiveness requirement, historically constant labels but modern C# also allows pattern labels in statements. The exhaustiveness rule is why switch expressions pair so well with enums and discriminated-union-style patterns: add a new enum member and every non-exhaustive switch expression becomes a compile error.

- id: csharp-pattern-02
  answer: |
    Property patterns match on the properties of the matched object: `obj is Customer { Name: "Alice", Age: > 30 } c` — each property is matched against a nested pattern (constant, relational, another property pattern, etc.), and the trailing designation `c` binds the whole matched value to a new strongly-typed variable. Positional patterns match using Deconstruct: `shape is Point(0, 0)` deconstructs the object into positional components and matches each against sub-patterns; `Point(var x, var y)` binds the components to variables. Both can bind: `var`/type patterns inside bind sub-values, and a designation at the end binds the entire object. Property patterns go through actual properties; positional patterns require a compatible Deconstruct (or matching positional record parameters).

- id: csharp-pattern-03
  answer: |
    Relational patterns compare the input with <, >, <=, >=, e.g. `n is > 0 and < 10`. Logical patterns combine patterns with `and`, `or`, and `not` (precedence: not > and > or), letting you build conjunctions/disjunctions/negations: `not null`, `string and { Length: > 0 }`. List patterns (C# 11) match sequences (arrays, List<T>, anything countable/indexable): `list is [1, 2, 3]` matches exactly; elements may be arbitrary patterns; the slice element `..` matches zero or more elements in the middle/end and can be captured: `[var first, .. var rest, var last]`. They require an indexer (or Slice) and a Length/Count, and they do not work on bare IEnumerable.

- id: csharp-pattern-04
  answer: |
    `obj is Customer c` does three things atomically: tests the type, checks null (null fails the pattern — no separate null check needed, unlike `obj is Customer` + cast, which would need `obj != null` first or a pattern), and declares+assigns a strongly-typed variable in one step — avoiding the double lookup/cast and the window where the variable could be null. It also works with subtypes and upcasts. Scope: the variable is in scope in the enclosing block/statement, but it is only DEFINITELY ASSIGNED where the pattern is known to have matched — e.g., inside the true branch of an `if`, or after `if (!(x is Customer c)) return;` in the following code. Using it in a false branch (or after a failed match) is a compile error under definite-assignment analysis.

- id: csharp-linq-01
  answer: |
    Deferred execution: the query is just a description (a chain of enumerable wrappers); nothing runs until you enumerate it (foreach, or a consuming operator). Standard sequence operators — Where, Select, SelectMany, OrderBy/ThenBy, GroupBy, Join, Zip, Take/Skip, Concat, Distinct, Reverse — are deferred (some, like OrderBy/GroupBy/Join, buffer internally when executed, but still only when enumerated). Immediate execution: operators that must produce a concrete value or collection now — ToList/ToArray/ToDictionary/ToHashSet, Count, Sum, Min, Max, Average, Aggregate, First/FirstOrDefault, Single/SingleOrDefault, Last, ElementAt, Any, All, Contains (these last three short-circuit but still execute immediately). Pitfalls that flow from this: multiple enumeration re-runs the whole pipeline, and captured variables are read at enumeration time, not build time.

- id: csharp-linq-02
  answer: |
    Over IEnumerable<T> it's LINQ-to-Objects: extension methods take delegates and run in memory in your process. Over IQueryable<T> the lambdas become expression trees that a provider (e.g., EF Core) translates into a query (SQL) executed by the data source, with filtering/projection done server-side. The danger of mixing: the moment you call an IEnumerable-based extension (explicitly, or implicitly by e.g. passing a method group / calling a non-translatable method), the provider must materialize the data — you can silently pull entire tables into memory, or your filtering happens client-side after fetching everything. AsEnumerable()/ToList() are deliberate switch points to client evaluation; mixing them in early accidentally is a classic performance bug. IQueryable also cannot execute arbitrary C#, so non-translatable calls throw or force client evaluation.

- id: csharp-linq-03
  answer: |
    A LINQ query variable (especially deferred/IQueryable) is a recipe, not a result. Enumerating it again re-executes the entire pipeline: for LINQ-to-Objects that's recomputation (and re-invocation of side effects); for a database it's another round trip. Worse, the two enumerations can return different results if the underlying data changed between them (or if the query captured a mutable variable). A common bug is `if (query.Any()) { foreach (var x in query) ... }` — two executions. Avoid it by materializing once — ToList()/ToArray() (or AsEnumerable + materialization) — and iterating the stored result; for EF you can also use explicit/compiled queries when appropriate. Just be aware materialization trades memory for consistency and single execution.

- id: csharp-linq-04
  answer: |
    `First` throws InvalidOperationException when the sequence is empty or no element matches the predicate; `FirstOrDefault` returns default(T) instead — null for reference types, zero/false for value types. `Single` requires exactly one match — throws on zero AND on more than one; `SingleOrDefault` throws if there is more than one but returns default on zero (a common misconception is that it returns default on duplicates — it doesn't). Value-type gotcha: with FirstOrDefault over e.g. int, you can't distinguish "no match" from "a legitimate 0" — the default is indistinguishable from real data. Workarounds: use First when emptiness is a bug (the exception is the feature), use `.NET 6+`'s FirstOrDefault(predicate, defaultValue) overload, project to nullable (`Cast<int?>()`), or check Any()/Count first (which costs an extra pass).

- id: csharp-async-01
  answer: |
    ValueTask/ValueTask<T> avoids allocating a Task on hot paths where the method usually completes synchronously — e.g., cached lookups, buffered readers, or validators that often return without I/O. Task<T> allocates even for a synchronous completion; ValueTask can wrap the result directly. Constraints (important!): a ValueTask may be awaited AT MOST ONCE; you must not await it twice, await it from two consumers, call .Result/.GetAwaiter().GetResult() before it completes (except when you know it's synchronously completed), or poll it — the backing IValueTaskSource may be pooled/recycled after the single await. If you need multiple awaits or fire-and-forget, convert once with .AsTask(). Rule of thumb: default to Task; use ValueTask only for measured hot paths and keep consumption simple (immediate await).

- id: csharp-async-02
  answer: |
    The compiler rewrites an async method into a state machine: locals are hoisted into a state-machine object, each `await` splits the method, and the awaiter's continuation (OnCompleted/UnsafeOnCompleted) resumes at the next state. An AsyncTaskMethodBuilder creates/attaches the returned Task and moves it to Completed on finish; exceptions are captured into the Task. Deadlock with blocking: on a context with a SynchronizationContext (UI thread, classic ASP.NET), `SomeAsync().Result` blocks the context thread. When the awaited task completes, the continuation captured inside the async method needs to marshal BACK to that same (now blocked) context thread to resume — it never can, and the blocked thread never releases → classic deadlock. Fix: "async all the way" (await instead of .Result/.Wait()), or ConfigureAwait(false) inside library code so continuations don't need the original context.

- id: csharp-async-03
  answer: |
    `await task.ConfigureAwait(false)` tells the awaiter NOT to capture the current SynchronizationContext/TaskScheduler, so the continuation resumes on an arbitrary thread-pool thread instead of marshaling back to the caller's context. It's recommended in library code because libraries shouldn't depend on (or be broken by) the caller's context: it avoids the classic .Result deadlock when some caller blocks, and it avoids unnecessary context switches (performance). Caveats: it does not guarantee thread affinity or make code thread-safe; it's about where the code AFTER the await runs. In ASP.NET Core / console there's no SynchronizationContext so it mostly doesn't matter there, but it still matters for UI/classic ASP.NET callers. Application (UI) code usually should NOT use it when it needs to touch UI afterwards. (.NET 8 adds ConfigureAwaitOptions for finer control.)

- id: csharp-async-04
  answer: |
    Cancellation is cooperative: a CancellationTokenSource produces a CancellationToken you pass into async methods. Nothing is forcibly killed — the callee must opt in by checking token.IsCancellationRequested, calling token.ThrowIfCancellationRequested(), or registering callbacks via token.Register; the source's Cancel() flips the token and fires those registrations. Operations respond by throwing OperationCanceledException (with the token attached), which the Task surfaces as Canceled state. CancellationTokenSource also supports CancelAfter(timeout) and linked tokens. IAsyncEnumerable<T> + `await foreach` are async streams: instead of a synchronous IEnumerable that blocks on MoveNext, each item's production can await (MoveNextAsync returns ValueTask<bool>). You author them with `async IAsyncEnumerable<T>` + `yield return` (and `await` inside), enabling async producers — paginated DB queries, network/SSE streams, sensor data — consumed with `await foreach (var item in stream)`. Tokens thread through with [EnumeratorCancellation].

- id: csharp-generics-01
  answer: |
    `where T : ...` constrains which type arguments are allowed, and in return gives the compiler knowledge to let you use the constrained capabilities inside the generic code. Main kinds: `where T : SomeBaseClass` (must derive from / be that class); `where T : ISomeInterface` (implements it); `where T : class` / `where T : struct` (reference / non-nullable value type); `where T : notnull`; `where T : unmanaged` (value type with no reference-type fields — good for interop/unsafe); `where T : new()` (has a public parameterless constructor, letting you `new T()`); and `where T : U` (must derive from/implement another type parameter). Multiple constraints are comma-separated per parameter; new() must come last; class/struct must come first if present. Constraints also enable nullability analysis (`T?` meaning differs between class and struct).

- id: csharp-generics-02
  answer: |
    Variance describes how generic types relate when type arguments are related. Covariant (`out T`): T appears only in output positions; `IEnumerable<Cat>` is convertible to `IEnumerable<Animal>`. Contravariant (`in T`): T appears only in input positions; `Action<Animal>` is convertible to `Action<Cat>` (a handler that accepts any Animal can accept a Cat). Built-in examples: IEnumerable<out T>, IReadOnlyList<out T>, Func<out TResult>, and contravariant Func<in T> parameters, Comparer<in T>, Action<in T>. They apply ONLY to interfaces and delegates (classes are always invariant) and ONLY when the type argument is a reference type — variance doesn't work with value types because it relies on reference representation. The compiler enforces the in/out positions to keep it type-safe.

- id: csharp-generics-03
  answer: |
    The compiler infers type arguments from the method's arguments by matching each parameter's type against the type parameters (a fixpoint/"lower bound" inference, considering convertibility and covariance of arguments). You must specify explicitly when inference has nothing to go on or is ambiguous: methods whose type parameters appear only in the return type (e.g., `T Create<T>()`), calls where arguments are lambdas, method groups, or null (no concrete type to infer), cases where different arguments imply conflicting type arguments, or generic methods with default parameter-only usage. You also specify explicitly when you want a base type/interface rather than the exact argument type (e.g., passing a List<string> but wanting T = IEnumerable<char>-ish scenarios). Type inference never "guesses" from return type assignment context for method calls.

- id: csharp-generics-04
  answer: |
    `default(T)` produces the zero value for T: null for reference types and nullable value types, 0/0.0/false for numeric/bool primitives, and a fully zero-initialized struct (all fields at their defaults) for value types. Generic code needs it because T's concrete default is unknown at compile time — you can't write `null` for a possibly-struct T or `0` for a possibly-class T. Typical uses: initializing fields/locals of T, returning a "no result" value without throwing, resetting state. C# 7.1 added the `default` literal (compiler infers T), and C# 8's `T?` in generic code interacts with constraints (for unconstrained T, `default!` is the escape hatch to silence nullability). Note default(T) is NOT a meaningful "empty" for user-defined structs that define invariants — it always bypasses constructors.

- id: csharp-delegate-01
  answer: |
    A delegate is a type describing a method signature; an instance holds a reference to a method (plus its target object for instance methods) and can be invoked like the method — effectively a type-safe function pointer with built-in support for multicast and closures (lambdas compile to delegate instances, often over compiler-generated closure classes). The generics: `Action<T1..T16>` wraps a void-returning method; `Func<T1..T16, TResult>` wraps a method returning TResult (TResult is last); `Predicate<T>` is essentially Func<T, bool> for a test — it predates Func/.NET 3.5 and is a distinct delegate type (no implicit conversion between Predicate<T> and Func<T,bool> despite identical shape). Prefer Func<T,bool> in modern APIs; Predicate survives in List<T> (Find, RemoveAll, etc.).

- id: csharp-delegate-02
  answer: |
    The `event` keyword imposes access restrictions on a delegate-typed member. Outside the declaring class, subscribers can only use += and -= (which map to add/remove accessors the compiler generates, typically backed by an Interlocked-backed field). They CANNOT invoke the event, assign to it (=), set it to null, or read the invocation list — so external code can't overwrite other subscribers' handlers, clear them, or raise the event itself. Only the declaring class may raise it (invoke it as if calling the delegate, with a null check). Plain public delegate fields would let any code do all of that — replacing all handlers is the worst offender. Events can also be abstract/virtual and have custom add/remove bodies (e.g., backed by a handler collection).

- id: csharp-delegate-03
  answer: |
    Lambdas capture variables by reference (the variable itself, not its value). In a `for` loop, the loop variable is ONE variable declared once for the whole loop, so lambdas created in different iterations share it — when invoked after the loop, they all see the final value (classic `for (int i=0;i<10;i++) actions.Add(() => Console.WriteLine(i));` prints 10 ten times). Since C# 5, the `foreach` iteration variable is a fresh variable per iteration, so foreach-created lambdas each see that iteration's value — safe. `for` still has the shared-variable behavior. Fixes: copy to a local inside the loop body (`var copy = i;` then capture copy), or restructure with LINQ. Also safe when the lambda is invoked within the same iteration before the variable changes. The general rule: capture = share the storage; per-iteration locals give per-iteration storage.

- id: csharp-delegate-04
  answer: |
    A multicast delegate combines multiple targets in an invocation list (built via +=, from Delegate.Combine). Invoking it calls every entry synchronously, in the order they were added. Return value: you get back only the LAST handler's return value — earlier ones are discarded, which is why multicast makes sense mainly for void-returning delegates (events). Exceptions: if any handler in the list throws, the iteration stops immediately — the exception propagates to the invoker and REMAINING handlers never run (no automatic aggregation). If you need all handlers to run or to collect return values, iterate manually: `foreach (var d in myDelegate.GetInvocationList()) { try { ((MyDel)d)(); } catch ... }`. Delegate removal (-=) removes the last matching entry; removing a non-existent handler is a silent no-op.

- id: csharp-dispose-01
  answer: |
    IDisposable.Dispose performs deterministic cleanup — releasing unmanaged resources (handles, native memory) and managed ones (streams, connections) that finalizers/GC can't handle promptly or at all. `using (var x = expr) { ... }` statement: acquires, wraps the body in try/finally, and calls Dispose in finally — so it runs even on exception, at the END OF THE BLOCK; multiple resources in one using are nested. `using var x = expr;` declaration (C# 8): no braces — the variable is disposed at the END OF THE ENCLOSING SCOPE (method/block), with the same exception safety, just a different (usually later) timing; you can't constrain the dispose point to an inner block without braces. Both handle null safely, and C# 8 adds pattern-based disposal for ref structs (a public Dispose method suffices without implementing IDisposable).

- id: csharp-dispose-02
  answer: |
    IAsyncDisposable (DisposeAsync returning ValueTask) is for resources whose release involves asynchronous I/O — flushing network/buffered streams, closing DB connections gracefully, HTTP/2 streams — where a synchronous Dispose would block a thread or force sync-over-async. `await using (var x = ...) { }` / `await using var x = ...;` await DisposeAsync at scope end, with the same exception-safety semantics as `using`. Use it when the type's natural cleanup is async; use plain IDisposable when Dispose is truly synchronous. In practice types that do async I/O implement BOTH (Dispose delegates to a synchronous best-effort, DisposeAsync does the real work via a DisposeAsyncCore pattern), so consumers can use either form. `await foreach` over async streams and async disposal pair naturally.

- id: csharp-dispose-03
  answer: |
    A finalizer (~ClassName) is run by the GC, non-deterministically, at some point after the object becomes unreachable but before its memory is reclaimed — on a dedicated finalizer thread, and it forces the object to survive an extra GC generation (promotion), making it expensive. Dispose is deterministic: the consumer calls it exactly when done, via using or manually. A type needs a finalizer ONLY if it directly owns an unmanaged resource (a raw OS handle, IntPtr to native memory, FILE*, etc.) that would leak forever if the consumer forgets to Dispose — the finalizer is the safety net. If the unmanaged resource is wrapped in SafeHandle (or you own only managed resources), you should NOT add a finalizer — it adds GC cost for nothing. Finalizers must never touch managed (finalizable) objects, only their own unmanaged state.

- id: csharp-dispose-04
  answer: |
    The full pattern (for a non-sealed class owning both kinds): implement IDisposable with a public `void Dispose()` that calls `Dispose(true)` and `GC.SuppressFinalize(this)` (the object is fully cleaned up; skip the finalizer for performance). Provide `protected virtual void Dispose(bool disposing)`: when disposing is true, dispose managed members (call their Dispose, null the references) AND release unmanaged resources; when false (called from the finalizer), release ONLY unmanaged resources — never touch managed objects (they may already be finalized). Add a finalizer `~T() { Dispose(false); }` only if you own raw unmanaged resources. Guard against double disposal (a bool flag is fine; Dispose must be idempotent and must not throw). Prefer wrapping native handles in SafeHandle to avoid the finalizer entirely. Derived classes override Dispose(bool). The async analog: DisposeAsync() → DisposeAsyncCore() (virtual) + SuppressFinalize.

- id: csharp-span-01
  answer: |
    Collection expressions (C# 12) are a literal syntax — `[1, 2, 3]` or `[]` — that can produce any supported collection type based on the TARGET type: arrays (T[]), List<T>, Span<T>/ReadOnlySpan<T>, ImmutableArray<T> and other types with suitable CollectionBuilder/Add patterns. They're target-typed, so `int[] a = [1,2,3]; List<int> b = [1,2,3];` both work, and `[]` means empty. The spread element `..` inline-expands another enumerable/collection's ELEMENTS into the new collection: `int[] both = [..first, middle, ..second];` — it copies elements rather than nesting, and works with any spreadable type (including spans). They allocate efficiently (compiler can size arrays/lists exactly) and replace many Add-ranges/ToArrays boilerplate idioms.

- id: csharp-span-02
  answer: |
    Span<T> is a ref struct representing a contiguous slice of memory — an array, part of an array, a string, stack memory, or native memory — with Length and a ref-returning indexer; slicing is O(1) and reading/writing is as fast as arrays, with zero heap allocation. ReadOnlySpan<T> is its read-only counterpart (string.AsSpan() gives one; can't write through it). Memory<T> is the heap-safe counterpart: it wraps the same idea but is a regular struct usable in fields, as async method state, and across awaits; you get a Span<T> from it via .Span when needed (it also supports pooling via IMemoryOwner). Span<T> can't be stored in a field or used across await because it's a ref struct: it may point to stack memory, so the runtime forbids it from being boxed, on the heap, in a class field, in async/iterator methods (the state machine would hoist locals to the heap), or in interface implementations. If you must persist it, copy the data or hold a Memory<T>/array instead.

- id: csharp-span-03
  answer: |
    stackalloc allocates a block of memory directly on the current thread's stack, automatically freed when the method returns — no GC pressure. Idiomatic modern use is with spans: `Span<int> buf = stackalloc int[128];`. The main care point: stack space is tiny (~1 MB by default), so NEVER allocate large or unbounded sizes — especially sizes derived from user input — because overflowing the stack throws StackOverflowException, which cannot be caught and kills the process. The standard pattern is a size check: allocate on stack for small n, fall back to a pooled array/ArrayPool for large n. Also beware stackalloc inside loops within the same method (allocations from multiple iterations can accumulate in that stack frame) and avoid letting it defeat inlining in hot paths. C# 8+ allows stackalloc in nested expressions but each is still a real stack allocation.

- id: csharp-span-04
  answer: |
    Array (T[]): fixed size fixed at creation, contiguous memory, direct indexing, supports multi-dimensional/jagged forms; it's covariant with reference types (string[] can be assigned to object[] — which can throw ArrayTypeMismatchException at runtime, a wart); implements IList<T> read/write but can't grow. List<T>: a resizable wrapper over an internal array — grows by doubling capacity with amortized O(1) Add, supports Add/Insert/Remove/RemoveAt/Find/Sort/etc.; indexing is O(1) like arrays; slight overhead (object header, capacity slack). Choose arrays for fixed-size, high-performance data (or as span sources); List<T> for anything that changes size. `params` lets the last parameter of a method accept a variable number of arguments at the call site (`M(1,2,3)`), compiled into an array in classic C#; C# 13 extends this to "params collections" — the parameter can be Span<T>, ReadOnlySpan<T>, IEnumerable<T>, List<T>, and other supported collection types, letting you avoid array allocation (e.g., params ReadOnlySpan<T>).
