Artifact IDE on ocode via kakiit

DRAFT PROPOSAL — NOT APPROVED   2026-11-27

1. Understanding

Give ocode an artifact IDE: build a small interactive app in chat, preview it live in the ocode desktop app, and give it working shared storage like Claude Artifacts. kakiit already hosts published artifacts as a hub; the new work is a live runtime with storage on that hub. ocode stays the authoring surface.

Assumptions to correct if wrong: (a) kakiit remains the hub, not ocode; (b) "isolated service" means a separate artifact runtime origin, not a separate kakiit deployment; (c) "public" means a link usable with no account. Success = build in ocode, preview in desktop, persist data, share privately / to an org / publicly under one permission model.

2. Delta: what exists, what is new

Mode B publish: ocode uploads blobs to kakiit S3 and finalises immutable versions; a stored local public token keeps re-publish on the same link. Hub failure → 502, no local fallback; a failed first publish is undone.Runtime that serves the hub version as a live app, not just static files.

No migration question: publishing already targets kakiit. New work starts at the hub.

3. Storage (new)

PoolSemanticsKey rule
PersonalOne private dataset per signed-in viewerIsolated from shared
SharedOne dataset all viewers read and writeServer records the writer; the page never sees it
FilesBlobs behind the service, not in the pageOwner / org editors only

Documents (JSON), not SQL tables exposed to the app. Start at 100 MB / 25,000 records, 20 MB per file; enforce server-side. Authorisation and auditing stay server-side — the page cannot enforce visibility.

4. Access: reuse, then gap

Reuse the existing public | password | allowlist modes, hashed capability tokens, signed cookies bound to mode, invite expiry and uniform 404. Add org mode for signed-in kakiit members; public links keep working without an account. Public serving stays under /p only, built through newArtifactTailscaleShare(); a public funnel requires authConfigured(). Serve from an opaque origin (sandbox allow-scripts, no allow-same-origin).

Gap: an opaque-origin iframe cannot send cookies or hold a bearer token. Storage calls need a postMessage bridge through the host frame, which authorises the viewer and proxies the call. The bridge is the core design problem, not a detail. A public link opened in a plain browser has no ocode host frame, so kakiit must serve a wrapper page around the artifact iframe to host it.

5. Desktop preview + UI

  • Add an artifact tab to the existing PreviewHost; keep preview_open and ocode:open-preview as the entry points. Live refresh follows the session SSE bus as file previews do today.
  • The artifact iframe carries the sandbox allow-scripts CSP header and never gets the ocode app origin.
  • Author UI: code + preview side by side, publish, version picker, personal/shared data tab, sharing dialog.
  • kakiit UI: artifact list, versions, storage inspection, visibility, invite/revoke, audit.
  • Remote projects route via ?host=; hub-down shows the existing hub error, never a local copy.

6. Out of scope for v1

SSR, multi-route apps, per-app backends or containers, per-row author/permissions in the shared pool, public catalog, and build execution (buildCmd is stored but never run today).

7. Constraints

  • Mode B hub publish uploads blobs and finalises immutable, content-hashed versions; no build execution or SSR in that path.
  • Hub failure surfaces an error; no local fallback. Fresh-publish undo stays.
  • Append-only Drizzle migrations; secret scan before publish.

8. Blocks the spike

  1. postMessage bridge: how the kakiit wrapper authenticates a viewer to the opaque-origin page without cookies or bearer tokens.
  2. connect-src policy for generated code — bridge only, or an allowlist.
  3. Draft vs live: unpublished desktop preview needs its own dataset so it never pollutes live shared data.

9. Decisions for build

  • Anonymous viewers have no identity — what a "personal pool" means for a public link.
  • Rate limits and abuse controls on public shared writes; validate schema and size; state who may publish code that reads them.
  • Versioning of stored data: does a new app version carry records forward, and how?
  • Hub-down/offline behaviour for the desktop preview.
  • Public links when an organization disables external sharing.
  • Storage API contract: methods, pagination, conflict handling. Can the agent read/write data, and through which redaction path?
  • Identity and lifecycle: sync-token → kakiit user/org mapping; delete, member-leave, export, retention and quota owner.
  • Two public paths: keep or retire the Tailscale funnel /p; add a per-artifact kill switch and phased rollout.
