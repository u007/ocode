# ocode Web UI Field Guide

A dense map of the ocode React SPA so you don't re-discover it from scratch.

## 1. Build & Dev

| Command | What it does |
|---------|-------------|
| `cd web && npm run dev` | Vite dev server on `:5173`, proxying `/api` → `:4096` |
| `cd web && npm run build` | `tsgo && vite build` → `web/dist/` |
| `cd web && npm run test` | Vitest test suite |
| `cd web && npm run typecheck` | `tsgo --noEmit` |
| `make web-build` | `cd web && npm install && npm run build` |
| `make web-dev` | `cd web && npm run dev` (background) |
| `make dev` | Go backend + Vite together |
| `make production` | Full Go binary with embedded `web/dist/` |

**Vite config** (`web/vite.config.ts`): bare-bones. `base: "./"` + runtime `<base>` injection in `index.html` (so assets resolve behind tailscale path prefixes). Proxy `/api` → `localhost:4096` in dev. `@/` alias → `src/`.

**Production embed chain**: `web/embed.go` uses `//go:embed all:dist` to embed the built SPA. `web.FS()` returns the embedded filesystem (nil when `dist/` missing). Both the headless server (`main.go` → `server.Run(args, web.FS())`) and the desktop app (`cmd/ocode-desktop/main.go` → `desktop.StartServer(web.FS(), workDir)`) inject the same `web.FS()`.

## 4. State Management

Four stores — no Redux, no Zustand.

### chatStore.tsx
- **State**: `ChatState` — `messages[]`, `sessionId`, `model/smallModel/advisorModel`, `ocr*`, `isStreaming`, `live[]` buffer, `pendingPermission`, `pendingQuestion`, request-scoped `hiddenQuestionRequestId`, pagination cursor, `tuiStatus` snapshot, `spending`, `sessionContext`
- **Actions**: 24+ action types including `ADD_MESSAGE`, `SET_MESSAGES`, `LIVE_DELTA`, `LIVE_TOOL_START/RESULT`, `MERGE_SNAPSHOT` (from turn-done), `PREPEND_MESSAGES` (scroll-up lazy load), `SET_TUI_STATUS`, `SET_TRANSCRIPT_SCROLLED_UP`, `PERMISSION_REQUEST/RESOLVED`, `QUESTION_REQUEST/HIDE/SHOW/RESOLVED/ANSWERED/DISMISSED`, `RESET`
- **Pattern**: Separate `ChatStateContext` and `ChatDispatchContext` — read with `useChatState()`, dispatch with `useChatDispatch()`
- **RESET nuance**: preserves `advisorEnabled` and `tuiStatus` across `/new` so they don't blink out
- **Advisor is PER CHAT**: the root `advisorModel` is only the default NEW chats start with. A live chat's model/triggers/gate live in its `SessionSlice` (`advisorModel`, `advisorCheckpoints`, `advisorEnabled`) and arrive via a session-tagged `status` snapshot (`advisor_model` / `advisor_checkpoints`), which `sessionEvents` routes with `SET_SESSION_ADVISOR_CONFIG`. Only an UNTAGGED status may write the root field — a session-tagged one writing it is exactly the bug where one chat's advisor pick repainted every tab. `ModelDialog` and `/advisor` thread the active `sessionId`; Settings → Advisor edits the default. Same optimistic-then-reconcile shape as the main model.

### projectStore.tsx
- **State**: `ProjectState` — `projects[]`, `activeProject`, `projectSessions`, `tabsByProject{}`, `activeTabByProject{}`, `sessionPickerOpen`, `groups[]`, `sessionsByProject{}` (per-project cache)
- **Actions**: `SET_PROJECTS`, `ADD_PROJECT`, `REMOVE_PROJECT`, `ADD_TAB`, `REMOVE_TAB`, `SET_ACTIVE_TAB`, `SET_TAB_SUB_TAB`, `UPDATE_TAB_TITLE`, `RESTORE_TABS`, `SET_SESSION_PICKER`, `SET_GROUPS`, `REKEY_TABS`, etc.
- **Purpose**: Multi-project support, session tab management, sub-tab routing (`SessionSubTabId`: chat|agents|changes|logs|status|preview), session picker dialog state, project groups
- **`UPDATE_TAB_TITLE` semantics**: an auto title (no `manual`) never overwrites a manual rename; a title+manual-flag that already matches returns the SAME state object (no-op guard) — background title application (reconcile / cross-process revalidate) re-sends the authoritative title on every pass, and a fresh `tabsByProject` object would re-render the tab bar and re-trigger the debounced `PUT /api/tabs` write. Titles are applied for a tab in ANY project (`findProjectPathForTab` walks every project, not just the active one).
- **Pattern**: `useProjectState()` for reads, `useProjectDispatch()` for writes (dispatch identity is stable — use this in `React.memo`'d children to avoid re-renders)

### browserTabsStore.tsx
- **State**: `tabsByProject{}` → `BrowserTab[]`, `activeByProject{}` → `string|null`
- **Actions**: `OPEN`, `OPEN_BACKGROUND`, `OPEN_RESTORED`, `CLOSE`, `RENAME`, `CLEAR_MANUAL`, `ACTIVATE`, `RESTORE`
- **Purpose**: Embedded browser tabs per project (useReducer + Context). Tracks per-tab manual titles and active selection. Persisted via `browserPersistence.ts`

### terminalStore.tsx
- **State**: `TerminalInstance[]` per project (with `id`, `title`, `renamed`, `oscTitle`), active terminal per project, plus a `revision` counter. Keyed by `projectTerminalsKey(path, host)` = `<host>::<path>` for a remote project, the bare path for a local one.
- **Actions**: `SET_PROJECT_TERMINALS`, `CLOSE_TERMINAL`, `SET_ACTIVE_ID`, `RENAME_TERMINAL`, `SET_OSC_TITLE`, `MARK_ALERTED`, `CLEAR_ALERT`, `BUMP_REVISION`
- **Purpose**: Terminal tab instances per project (TanStack Store, not useReducer). `terminalDisplayTitle()` resolves manual rename → OSC title → default name
- **The tab LIST is SERVER state** (`GET/PUT /api/terminal-tabs` → `internal/termtabs`), because localStorage is per-origin and a terminal started in the desktop app was therefore invisible to a second browser even though the shell (a child of the remote host's `serve --remote`) was shared. Session tabs were already migrated server-side for the identical reason (`internal/tabs`). Converges on the unscoped `terminal_tabs_changed` bus event and on every bus reconnect. `activeId` is deliberately **not** shared — it is per-window focus state and can be `PROCESSES_TAB_ID`, which is not a terminal.
- **`terminalPersistence.ts` is now only a MIRROR** of the last server read, not a source of truth. It exists so `getProjectTerminals` can answer a synchronous *peek* before hydration and so `TopTabs`/`ProcessesPanel` can read a count without an await. Every server read overwrites it; the write-through is suppressed until the initial restore settles (`restoredRef`) so a mirror-derived list cannot clobber the server. Pre-server state is written through once, per project the server has never seen.
- **`state.revision` is load-bearing**: a peeked project reads the mirror out of localStorage, which is not reactive. Without the counter, a hydrating server read would write the mirror but change nothing the store exposes — nothing re-renders, and the second client keeps showing an empty strip. That was the original bug's last mile.
- **The shared list propagates closes and renames, but NOT the session itself.** An empty terminal list means DELETE server-side, so a project whose last tab closed is ABSENT from `GET /api/terminal-tabs` — a refetch must therefore also clear live projects missing from the response, not just walk the keys it got back. And `adoptServerList` must compare metadata (title/renamed/oscTitle), not just ids, or a rename never reaches another client's open project. Both were real bugs; regression tests in `terminalStore.shared.test.tsx`.
- **Keystrokes do NOT mirror.** The tab list is shared; the pty is not. Only the client holding the single attachment slot sees input and output — the other shows the tab and, if it tries to attach, takes the terminal over. Do not describe this feature as "the same terminal in two browsers".
- **One attachment slot per terminal.** A second client attaching the same `terminal_id` displaces the first; the server sends `{"type":"detached","reason":"superseded"}` before closing it, and `TerminalPanel` parks in a takeover state with a **Take over** button instead of auto-reconnecting. Do not "simplify" that guard away — both reconnect paths (backoff timer, `onWake`) would otherwise evict the other client on every wake, which is the 2026-09-19 two-sockets-per-terminal reconnect loop. Regression: `TerminalPanel.wake.test.tsx` ("TerminalPanel takeover"), `terminalStore.shared.test.tsx`.

## 5. Backend Communication

### REST API Client (`api/client.ts`)
- Single `api` object with 50+ typed methods: `api.getSessions()`, `api.sendMessage(id, text)`, `api.getSpending()`, `api.getTheme()`, `api.listProjects()`...
- `fetchJSON<T>()` wraps `fetch()` with auth headers, JSON parsing, error handling
- `authedFetch()` wraps `fetch()` with auth headers (used for non-JSON endpoints)
- **Base path**: `apiPath()` prepends `_basePath` to every path — derived from `location.pathname` matching `/session/<id>` for tailscale path-prefix support
- **Auth**: Bearer token from `?token=` URL param (embedded by `/rc` command), stored at load time. `authHeaders()` returns `{Authorization: Bearer <token>}`. `authToken()` returns the raw token for SSE URLs
- All `/api/*` calls proxied through Vite in dev (`localhost:5173` → `localhost:4096`)

### SSE Live Streaming — Unified Event Bus

A single long-lived fetch-based SSE stream on `GET /api/events` carries every event type: chat mirror frames, turn lifecycle, status, logs, agent runs, git status, spending. Consumers register per-event-type handlers via `lib/eventBus.ts`.

| Transport | Purpose |
|-----------|---------|
| `GET /api/events` | **Single persistent SSE stream** — all event types for all subscribed projects |
| `readSSEStream()` | Fetch-based SSE parser (used instead of EventSource for auth header support) |

**Why fetch, not EventSource**: `EventSource` cannot set custom headers. Remote-mode auth requires `Authorization: Bearer` header. The `readSSEStream()` helper in `api/client.ts` parses the SSE text protocol from a fetch Response body.

**EventBus** (`lib/eventBus.ts`):
- Singleton module-level instance, auto-starts on first `on()` call
- `eventBus.on(eventType, handler)` — register per-event handler, returns cleanup function
- `eventBus.onReconnect(handler)` — fires on stream re-establishment for state reconciliation
- `eventBus.setProjects(paths[])` — drives server's subscriber-aware emitters; changing it restarts the stream
- Reliability: exponential backoff reconnect, `seq` gap detection (warning + reconcile, no replay)
- Reconcile recovery: `reconcileOpenSessions` refetches `GET /api/sessions/:id/state` and hydrates a paused permission/question dialog from its `pending_asks` field (read from the live agent transcript). The `PERMISSION_ASK:` sentinel is normally in the persisted transcript, but a failed/conflicting save or a pause after the last write can leave it absent. Three client triggers hydrate the dialog: reconcile (reconnect/load/activation), a 409 send (`useChat`'s `hydratePendingAsks`), and the `turn_error`/`error` frame (`scheduleHydratePendingAsks` in `sessionEvents.ts`) — the last is required because the web client always sends `async:true`, so a refused send resolves 202 and the `ErrPermissionPending` refusal arrives later as an error frame rather than a 409. A repeated `QUESTION_REQUEST` for the same request id preserves `hiddenQuestionRequestId`, so recovery cannot reopen a dialog the user hid; a different request id clears the hide and opens normally.
- **Session tab titles are applied from every authoritative fetch, not just the active tab.** The live path is the `status` event's `session_title` (routed per open tab); the background paths are `reconcileOpenSessions` (page load / reconnect) and `revalidateSession` (cross-process poll) — both already fetch `detail.title`, and `applySessionTabTitle` dispatches `UPDATE_TAB_TITLE` so a tab that has never been visited (ChatPanel not mounted, so its own detail fetch never ran) still relabels. Placeholder titles (empty, the session id, `"New session"`) are skipped; the reducer protects a manual rename and treats an unchanged title as a no-op (so a background pass can't cause render/persist churn).
- Handlers receive full envelope with `session_id` and `project` for routing

**Key event types** (via `sessionEvents.ts`):
- `messages` — full session snapshot (replaces state via `MERGE_SNAPSHOT`)
- `user_message`, `thinking`, `text`, `tool_start`, `tool_result`, `turn_done`, `turn_error` — live streaming fragments
- `status` — TUI status snapshot
- `git_status` — working-tree change counts
- `spending` — token usage
- `permission` — permission approval needed (paired with `permission_resolved`)
- `question` — agent question prompt (paired with `question_resolved`)
- **Question close semantics:** X and Escape dispatch the synchronous local `QUESTION_HIDE` path only; they never call `POST /api/questions/cancel`. The footer `Don't answer` is the explicit async server-side dismissal. The transcript's `Open question` button dispatches `QUESTION_SHOW` for the same request id, while a new `QUESTION_REQUEST` clears the old hide.
- **Answered questions render as a Q&A card.** On a successful `POST /api/questions`, `useChat.submitQuestionAnswers` dispatches `QUESTION_ANSWERED`, which rewrites the local `QUESTION_PROMPT:` sentinel tool result in place with a shape-compatible payload parsed from the same answers the server sends the model — so the chat shows the questions + the selected answers the instant the dialog is submitted, without waiting for the continuation turn's `messages` snapshot. `TurnParts.parseQuestionAnswers` / `QuestionAnswerBlock` render that payload for any `question` tool call whose result is the answer array (grouped, loose, and live paths all go through `ToolBlock`). The raw `QUESTION_PROMPT:` sentinel is never rendered, including from the live stream.
- `permission_check` — auto-permission judge activity
- `compaction_started` / `compaction_done` — server-authoritative compaction
  lifecycle. `compaction_started` carries `started_at`; `compaction_done` is
  emitted once when the last overlapping pass finishes and carries `ok` plus an
  optional `error`. Both carry a monotonic `generation`; the client ignores a
  `done` older than its latest `started`. Routed into
  `lib/compactionState.ts`, so any open client (not only the one that submitted
  `/compact`) shows the composer indicator. `SessionTabSync` clears generation
  watermarks on SSE reconnect because a restarted server resets its counter.
- `/state` reconcile/revalidation carries `compacting`, `compaction_started_at`,
  `compaction_generation`, and `compaction_error`;
  `sessionEvents.ts` applies them with a per-session event-version guard so a
  slow `compacting:false` response cannot clear a start event that arrived
  mid-fetch. Older servers omit the fields, which preserves the client state.
- `log` — server log lines

**Auth for SSE**: `GET /api/events` is a fetch request (not EventSource), so it carries `Authorization: Bearer` headers natively. No `?token=` query param needed for the event bus stream.

### RC Bridge Architecture (TUI co-location mode)
When the web server runs alongside the TUI (`/rc` command):
1. `RCBridge` in `rc_bridge.go` is a channel-based proxy — `RcCh` receives requests, `StreamCh` sends SSE events back
2. The TUI's Update loop reads from `RcCh` and processes through its own agent
3. `RCBridge.Broadcast()` publishes events to the unified event bus (`/api/events`) for all SSE subscribers (fan-out pattern)
4. The event bus delivers events to all connected web clients

## 7. Streaming & Message Lifecycle

**Single source of truth**: The TUI/server holds the canonical message list. The `turn_done` SSE event carries a full snapshot (`messages` event) that replaces the current state via `MERGE_SNAPSHOT`. The live buffer (`live[]`) is cleared when the snapshot arrives. Dropped SSE events self-heal at the next snapshot.

**Failed turns keep their work**: when an LLM call fails part-way through a turn, `Agent.Step` returns the rounds that already completed alongside the error, and the server persists them and emits a `messages` snapshot *before* `turn_error`. So a failed turn ends the same way a successful one does — snapshot first, terminal frame second — and reopening the session shows everything that actually ran. The same applies to the permission/question continuations (`/api/permissions/resolve`, `/api/questions/answer`), which keep the resolved tool result instead of leaving the session on an unresolved sentinel.

**Lazy-loading chat history**: `ChatPanel` loads the last 50 messages (via `GET /api/sessions/{id}/messages` with `?after=` cursor), then prepends older messages on scroll-up via `PREPEND_MESSAGES`.

**Live rendering flow**:
1. User types message → `POST /api/chat` → returns session ID
2. The event bus (`eventBus.on(...)`) receives live events from the `GET /api/events` stream
3. SSE emits `user_message` → first live fragment
4. SSE emits `thinking`, `tool_start`, `tool_result`, `text` → appended to `live[]`
5. SSE emits `turn_done` with `messages` snapshot → `MERGE_SNAPSHOT` replaces state, clears `live[]`
6. SSE emits `status` → updates `tuiStatus`

**Key nuance**: The web UI is always a remote viewer/input. Every turn runs through the TUI's agent (in RC mode) or a headless server agent. The frontend sends a message via REST, then the response arrives via the event bus SSE stream — no WebSocket.

## 8. Theming

- **Dark-first**: `<html class="dark">` in `index.html`, `color-scheme: dark` in CSS, light mode via `html.light`
- **CSS variables** in `index.css`: `:root` carries HSL triplets for `--background`, `--foreground`, `--primary`, `--border`, etc. (shadcn pattern)
- **Dynamic theming**: `useTheme.ts` fetches `GET /api/theme` on mount, converts hex colors to HSL triplets, sets them on `:root` CSS vars via `document.documentElement.style.setProperty()`. Server-pushed colors override defaults
- **Contrast-safe mapping (gotcha)**: terminal palettes are designed for text-on-background only — mapping colors 1:1 onto shadcn surface roles makes vivid themes unreadable (e.g. `lcars` tan text on orange user bubbles, gray hint on brown muted cards, ~1.4:1). `computeThemeVars()` checks WCAG AA (4.5:1) per pair and only repairs what fails: foregrounds on colored surfaces (`--primary-foreground`, `--accent-foreground`, `--destructive-foreground`, `--secondary-foreground`) pick the best AA-passing theme color (black/white last resort); the `--muted`/`--muted-foreground` pair darkens the surface toward `--background` first (never toward `text` — that can flip surface polarity, see dracula in `useTheme.test.ts`), then brightens the foreground toward `text`→neutral. Consequence: any component painting text on `bg-accent`/`hover:bg-accent` MUST use `text-accent-foreground`/`hover:text-accent-foreground`, never inherit `text-foreground`. `web/src/hooks/useTheme.test.ts` asserts all pairs across every built-in palette (`themePalettes.fixture.ts`, snapshot of `internal/theme/theme.go` — regenerate when palettes change)
- **shadcn/ui** via `components.json` — New York style, zinc base color, CSS variables mode
- **Tailwind** classes reference CSS vars: `bg-background`, `text-foreground`, `border-border`
- The same theme engine powers both the web UI and the TUI — the Go theme system is the single source of truth

## 9. Slash Commands — Double-Routed

The canonical `COMMANDS` array in `web/src/components/Chat/commands.ts` is shared by `ChatInput` (autocomplete), `SlashCommandMenu` (popup), and `CommandPalette` (⌘K). Commands are **dynamically loaded** via `loadDynamicCommands()` (called by `useCommands()` hook), which merges additional commands from the server at runtime. The static array contains core commands (`/help`, `/clear`, `/export`, `/model`, etc.); server-provided commands (like `/computer`, `/sandbox`) are appended on first load.

`dispatchCommand(name, ...)` handles them asynchronously:
- **Frontend-only** (don't hit the agent): `/help`, `/commands`, `/clear`, `/export` (generates Markdown + triggers browser download), `/export-claude` (appends to Claude history)
- **API-call**: `/session`, `/ocr`, `/mask`, `/compact`, `/recap`, `/share`, `/btw`, `/sandbox` — call backend endpoints directly
- **Model/agent switches**: `/model`, `/small-model`, `/advisor`, `/explorer-model`, `/context-model` — dispatched via API (a bare `/x-model model` returns `openModelPicker` + `modelPickerPurpose`, which `App.tsx` turns into a `ModelDialog` open)
- **Config**: `/fake-agent`, `/editor`, `/editor-mode`, `/themes` — read/write the same REST endpoints as the Settings forms
- **In-chat find**: `/search`, `/find` — dispatch a `ocode:open-chat-search` window CustomEvent (`{query}`); `ChatPanel` listens and opens its find bar with the same tab-visibility guard as `Ctrl/Cmd+F`. The find bar searches the **whole transcript**, not just the loaded window: a debounced `api.searchSession(id, q, {}, host)` hits `GET /api/sessions/{id}/search` and returns matching **server indices**; `web/src/lib/sessionSearch.ts` translates them to render-entry positions via the store's `windowStartServerIndex`. Jumping to an off-window hit fetches the contiguous prefix (`{limit: windowStart - matchIndex, offset: messages.length}`) and `PREPEND_MESSAGES` is cap-exempt, so `MAX_SLICE_MESSAGES` (400) is never raised. A `"N total, M in view"` note appears only when hits sit outside the window; a draft tab (`new-*`) skips the server query and a failure falls back to the instant local matcher.
- **CLI utilities**: `/tools`, `/tool` — `GET /api/cli-tools` lists catalog tools with PATH-detected status; `/tools <name>` starts `POST /api/cli-tools/install` (202 + `job_id`) and polls `GET /api/cli-tools/install/{id}`. Install can take **minutes**, so the handler returns immediately and reports the outcome via `ctx.notify` (mapped in `App.tsx` to `ADD_MESSAGE`). Remote tabs route through `/api/remote/<host>/…`, so the probe runs on the remote host's PATH.
- **Computer-use**: `/computer` — show/enable/disable computer-use status
- **TUI-only** (no web equivalent): `/ide`, `/secret`, `/sidebar`, `/details`, `/sound`, `/rc`, `/exit` — these return an explanatory message naming the web alternative. They must NOT fall through to the LLM: a picker entry without a dispatch case silently becomes a chat message (this is how `/fake-agent` was reported "missing").
- **MCP OAuth**: `/mcp-auth <server>` — `POST /api/mcp/{name}/auth` starts the flow (202 + `job_id`), then polls `GET /api/mcp/auth/{id}` (`running`→`done`/`error`). The operation **refuses non-loopback callers with 403**: the flow launches a system browser and listens on the server's `127.0.0.1:8085`, so it only works when the browser and the server share a machine (desktop app / local web). A remote SSH session is refused **by the local server before it even connects** (the remote cannot tell: the `ssh -L` tunnel makes its peer loopback), so the fast 403 applies there too — WSL is exempt because its server shares the Windows machine. The command returns immediately and reports the outcome via `ctx.notify`. That is a real 403, not a "TUI-only" stub. **Never tell a web/desktop user to run a command "in the desktop shell"** — the desktop app renders this same SPA, so that advice loops.
- **Subcommands**: a command present in the picker can still silently ignore its arguments. `/recap`, `/agents`, `/compact`, `/init`, `/cron` all take subcommands/arguments in the TUI and must forward `args` in their dispatch case (a bare `return handleX(ctx)` dropped them). Tested by `commands.subcommands.test.tsx`.
- **Unknown commands**: displayed in UI but fall through to the next agent turn as plain messages

**Parity guard.** `web/src/components/Chat/commands.tuiParity.test.tsx` iterates the real `COMMANDS` array and asserts every entry dispatches (`handled: true`) except `/new` and `/clear`, which `App.tsx` intercepts before `dispatchCommand`. When adding a command, add both the `COMMANDS` entry and a `case` — the test fails otherwise. TUI-side reference list: `internal/tui/commands.go`'s `commandSpecs`.

## 11. Key Architectural Decisions & Gotchas

1. **No client-side agent** — The browser is always a remote viewer/input. Every turn runs server-side (TUI agent or headless agent). The frontend sends a message via REST, response arrives via SSE — no WebSocket.

2. **Unified event bus** — `GET /api/events` is a single long-lived fetch-based SSE stream carrying all event types. `lib/eventBus.ts` is the singleton transport; consumers register per-event-type handlers via `eventBus.on(event, handler)`. The old per-session EventSource connectors (`connectSessionMirror`, `connectAgentRunsSSE`) are deleted. `readSSEStream()` in `api/client.ts` parses the SSE text protocol from a fetch Response body — used because `EventSource` cannot set auth headers.

3. **Snapshot self-heals** — The `turn_done` event carries a `messages` snapshot that fully replaces state via `MERGE_SNAPSHOT`. If a few SSE events are dropped, the next snapshot fixes everything. Never treat the live buffer as authoritative.

4. **Lazy-loading** — `ChatPanel` loads 50 messages at a time. Scroll-up triggers `PREPEND_MESSAGES`. The pagination cursor is the `before` parameter (message ID before the oldest loaded).

5. **Runtime `<base>` injection** — A synchronous inline script in `<head>` parses the URL and injects `<base href>` before any asset tag loads. `_basePath` in `client.ts` mirrors this for API paths. Both must stay in sync.

6. **Monaco offline-first** — `monaco-setup.ts` bundles all workers via Vite `?worker` imports so the editor works fully offline in ocode-desktop's webview (no CDN). If you add a new worker type, bundle it the same way.

7. **shadcn/ui with CSS vars** — All components use Tailwind classes referencing CSS variables. The server theme engine swaps these at runtime by setting HSL values on `:root`. If you add a new color role, it must be a CSS var, not a hardcoded hex.

8. **Four stores, not one** — `chatStore` + `projectStore` + `browserTabsStore` + `terminalStore` as separate contexts. `SessionPage` reads from `chatStore` and `projectStore`; `App` wraps all four providers. If state needs to cross boundaries (e.g. "which project owns this session?"), wire it through `App`/`SessionPage`, not through a merged store.

9. **Auth for SSE** — The event bus (`GET /api/events`) is a fetch request, not EventSource, so it carries `Authorization: Bearer` headers natively. Legacy one-shot SSE endpoints (file search, exports) use `readSSEStream()` which also carries auth headers. If you add a new SSE endpoint, use `readSSEStream()` — never bare `EventSource` — so auth headers flow through.

10. **AdvisorEnabled preserved across `/new`** — The `RESET` action preserves `advisorEnabled` and `tuiStatus`. Any new state that should survive a session reset must be added to the RESET preservation list.

11. **Tests live in `web/src/` too** — the SPA has a vitest + testing-library suite (`npm run test`, ~150 files) alongside the Go-side tests (`web/embed_test.go`, `internal/server/handler_sse_test.go`). Add a component/store test next to the code you change; `npm run typecheck` and `npm run build` must both stay green.

12. **Session id routing** — The `/session/:id` route in react-router and the `sessionId` in `ChatState` must match. `SessionPage` reads `:id` from the URL params and dispatches `SET_SESSION_ID`. URL changes trigger a full session switch.

13. **SSE `status` event format** — The `status` event (via the unified event bus) carries a JSON blob that populates `tuiStatus` in chatStore. It mirrors the TUI's status rendering (model, agent, thinking state, spinner, spending). The web UI renders it in the StatusBar and CoworkSidebar. If the TUI adds a new status field, the web UI typing in `types.ts` needs updating. **Per-session token totals** (`input_tokens`/`output_tokens`/`cached_tokens`/`total_tokens`) are populated for headless web/desktop sessions by the server's `applySessionUsage` (`internal/server/handler_session_state.go`): live agent atomics → persisted session metadata (the same keys the TUI's `sidebarTelemetry` writes) → else absent. The CoworkSidebar Context section shows an Input/Cached/Output breakdown (independent of the context gauge, so a restored session with no provider reading still shows its totals); the Cached row carries the cache hit % (`cached ÷ (input+cached)`, mirroring the TUI's `Cache <n> (<pct>%)` line), and there is deliberately no billed Total row. The StatusBar row 2 shows `in … · cache … · out …`; both are hidden when all counts are 0 (never a fabricated 0). Tokens persist at turn end via `persistSessionTelemetry`; `agent.Message.Usage` is `json:"-"`, so the transcript cannot be used to reconstruct them — metadata is the only cross-restart source. **Live agent-loop activity arrives on a SEPARATE `agent_activity` event, not on `status`.** `status` is a whole-snapshot REPLACE (`SET_TUI_STATUS`), so it cannot carry an activity-only update; `agent_activity` carries just `llm_running` / `active_tools` / `active_agents` and the reducer MERGES them (`SET_AGENT_ACTIVITY`). The server publishes it per turn from `agent.Activity().Notify()` (`startAgentActivityBroadcast`), i.e. **headless web/desktop only** — with an RC bridge attached the TUI owns that single-consumer channel and publishes the same fields through complete `status` snapshots instead. Both sources write the same `TUIStatus` field names on purpose, so `StatusBar.runningStatusParts` renders either identically. Rules when touching this: (a) never add a new field to `agent_activity` without also adding it to `AgentActivityEvent` in `internal/server/tui_status.go` AND `AgentActivityEvent` in `api/types.ts`; (b) an event added to `SESSION_SCOPED_EVENTS` is automatically subscribed (`ROUTABLE_EVENTS` derives from it) and routed to a tracked session's slice, but it is NOT automatically replayed — `agent_activity` is deliberately excluded from the server's `liveFrameEvents` because replaying a momentary reading would show a stale `⟳ llm` for a tool that already finished; (c) the three fields are cleared on the turn boundary (`SET_TURN_STATE` → `turnActive:false`) so a late frame can't park a dead indicator that the next turn would inherit.

**Status-bar model semantics:** the bottom `StatusBar` reports the per-session `lastDispatchedModel`, captured from the backend's 202 `ChatResponse.model` (including new-session, retry, ask-continuation, and rewind dispatches) and the `turn_started.model` event fallback. Bridged RC 202s use the live TUI status model. It is intentionally independent of `tuiStatus.main_model`, which remains the CoworkSidebar's current configured/effective selection; the model segment is absent until this client has dispatched a turn. A failed submit does not change it, and a `turn_error` does not clear it.

14. **Permission flow** — When the server's agent needs a permission grant, it sends a `permission` SSE event. `PermissionDialog` shows the command and complete `args` in a formatted, wrapped, scrollable “Tool execution parameters” section (no truncation), captures user choice, and sends the result via `POST /api/permissions/resolve`. Full arguments are forwarded by both server-owned and TUI RC events and preserved through live-state and transcript recovery. Legacy requests without `args` retain the command-only display. The SSE then continues with the resolved tool call.

15. **Ask dialogs (`PermissionDialog`, `QuestionDialog`) must cap to the visible viewport** — both are Radix dialogs centred with `top-1/2 translate-y-[-50%]`, so without a height cap tall content paints off **both** edges with no scrollbar. They use the shared `.dialog-viewport-max` utility (`web/src/index.css`, inside `@layer utilities`) plus `overflow-y-auto`. The utility deliberately declares `100vh` in one rule and upgrades to `100dvh` in an `@supports (height:100dvh)` block — **do not** merge them into one rule with two `max-height` declarations: the CSS minifier drops the earlier one, leaving browsers without `dvh` support with no cap at all. `QuestionDialog` additionally lays out as `flex flex-col overflow-hidden` with the header/footer `shrink-0` and a `flex-1 min-h-0 overflow-y-auto` body, so the Don't answer/Submit row is pinned (never scrolls out of reach) on a long prompt — mirror `SessionDialog`/`PluginsPanel` for any new ask dialog rather than relying on whole-dialog scroll alone.

16. **Tabs are keep-alive — never unmount to "switch"** — every visited session tab (across **all** projects) stays mounted and is toggled with `hidden` CSS: the chat surfaces via `allChatTabs.map` + `visitedTabsRef`, the terminals via `terminalProjectPaths.map` in `App.tsx`. The `UnifiedTabBar` is a drag-and-drop sortable tab strip (`@dnd-kit`) with multi-row wrap overflow. That is what lets a background tab keep streaming and a pty/WebSocket survive a switch. Anything that unmounts on switch (e.g. rendering only the active project's surfaces, or a `key` that changes per tab) breaks streaming and terminal state — do not "simplify" it.

17. **Memo on the per-tab surfaces requires the *dispatch-only* project hook** — the hot per-tab children (`ChatPanel`, `ChatInput`, `ChangesPanel`, `LogPanel`, `AgentsPanel`, `PreviewTabPage`) are `React.memo`'d so a tab switch does not re-render every hidden tab. That only works if they do **not** call `useProjectState()`: the provider's context value is recreated on every dispatch, so any consumer of it re-renders on every tab/project switch and memo is defeated. Use `useProjectDispatch()` (stable identity) when a component only fires project actions, and pass per-project data (e.g. `projectPath`) as a prop. Passing an inline arrow/array prop to a memo'd child also defeats it — hoist with `useCallback`/`useMemo`, or use the trampoline pattern in `App.tsx` (`handleCommandRef` + `stableHandleCommand`) when the underlying closure must stay fresh.

18. **Heavy viewers must stay code-split (`React.lazy`)** — `PreviewSurface` lazily loads `PdfViewer`/`DocxViewer`/`PptxViewer`/`ExcelViewer`/`MmdViewer`/`MarkdownViewer`/`HtmlViewer`/`JsonViewer`/`TextViewer`, and `FileTabContent` lazily loads `FileEditor` (Monaco). Together these were ~4.8 MB of the old 6.7 MB entry chunk (Monaco, pdf.js, xlsx, docx-preview, mermaid). Never re-introduce a **static** import of those modules on the entry path (`App.tsx` → `FileTabContent`/`PreviewSurface`): a single static import puts the whole dependency back in the initial bundle. Type-only imports are fine (they erase). Tests that render a lazy surface must `await waitFor(...)` — the first paint is the Suspense fallback.

19. **Speech reads RENDERED text, never the markdown source** — the per-message `Speak` button (`AssistantText`), the `at-bottom` auto-speak (`ChatPanel`'s `ocode:assistant-complete` dispatch), and `Speak visible` all extract from the DOM via `renderedSpeechText` / `renderedSpeechTexts` / `lastRenderedSpeechText` in `web/src/components/Speech/speechUtils.ts`, not from `message.content`. 51. **The chat scroll surface has exactly one writer, and a clamped pin is not reader intent** — the transcript "bounced up" after every turn because several components wrote `scrollTop` and one of them lied. Four rules, all load-bearing:
    - **Key virtual items by global transcript position, never by object identity.** The turn-boundary `SET_MESSAGES` (from the `messages` SSE event, `sessionEvents.ts`) replaces the whole `messages` array with freshly parsed objects and clears `live` in the *same* reducer update; `MERGE_SNAPSHOT` does the same on initial load and from the turn watchdog. Either way object-identity keys change on every message at the end of every turn. That empties the virtualizer's `itemSizeCache`; because the list container's height **is** `getTotalSize()`, the container collapses from real measured heights to `count × estimateSize` and the tail pin's `el.scrollTop = el.scrollHeight` is clamped against the shrunken container — a real upward jump. `transcriptItemKey(windowStartServerIndex, originalIndex)` (`web/src/lib/chatItemKeys.ts`) is stable across both snapshots and across `PREPEND_MESSAGES` (the store walks the window start back by exactly the prepended count). It is also stable when a capped window (>400 msgs) slides forward: the store recomputes `windowStartServerIndex` from the trim, so head rows lose their keys while surviving rows keep both their key and their content. This is also what makes item 35(c)'s "keyed by stable message/tool identity" true for disclosure state.
    - **Seed the live→committed swap.** `live` is non-virtualized and fully rendered, so tearing it down while its replacements mount at `estimateSize` is a multi-thousand-pixel height hole even with stable keys. `ChatPanel` captures the live block's height with a `ResizeObserver` (not an effect — a per-delta `getBoundingClientRect` forces a reflow) and `estimateSize` hands it to the rows replacing it, spread proportionally. `ResizeObserver` rather than measurement also means no forced synchronous layout on every stream delta.
    - **`el.scrollTop = el.scrollHeight` is CLAMPED, so a decrease is not evidence of the reader.** Both the synchronous and the deferred at-bottom recompute used to treat any offset decrease as the user scrolling up and dropped `atBottomRef`, silently stranding the transcript above the bottom mid-turn. Unpinning now requires a real gesture (wheel with `deltaY < 0`, `touchmove`, a `pointerdown` in the scrollbar strip, or `ArrowUp`/`PageUp`/`Home`) within `USER_SCROLL_INTENT_MS`; **re-arming stays unconditional** or the follow can never resume when the reader scrolls back. A test that means "the reader scrolled up" must dispatch the gesture (`userScrollsUp(el)` in `ChatPanel.test.tsx`) — moving the offset and firing `scroll` alone is precisely the false positive.
    - **Suppress the other two writers while pinned.** The scroll surface carries `[overflow-anchor:none]` (native anchoring has to pick an anchor among absolutely positioned `translateY` rows), and `virtualizer.shouldAdjustScrollPositionOnItemSizeChange = () => !atBottomRef.current` disables virtual-core's estimate→measure compensation while following the tail. Note it is an **instance** field, not a `useVirtualizer` option, and `setOptions` never resets it. Regression: `web/src/lib/chatItemKeys.test.ts`, plus the disclosure-persistence and clamped-pin tests in `ChatPanel.test.tsx` (both mutation-verified against the old code).

52. **`alt+↑`/`alt+↓` walk your SENT messages, not your typed ones — and the count must come from the server** — the composer already owns bare `↑`/`↓` (the keydown lives in `ChatInput.tsx`'s handler, the state/derivation in `lib/tabInputHistory.ts`), so the transcript walk is bound to `alt+↑`/`alt+↓` and **must never** be moved onto the bare arrows. Three things that are not obvious:
    - **The index list is server-side, not client-derived.** The web client holds only a tail window (capped by `MAX_SLICE_MESSAGES`), so counting locally would make `msg 3/17` disagree with the TUI on the *same* session. `GET /api/sessions/{id}/user-messages` returns `{total, indices, truncated, scanned}` over the whole transcript; `userMessageNav.ts` keeps a client mirror of the counting predicate (`isCountableUserMessage`) used **only** as the fallback when that request is unavailable, so a failure degrades to the loaded window instead of the feature going dead. Keep the TS predicate and the Go one (`isCountableUserMessage` in the handler) in lockstep — divergence reintroduces exactly the cross-surface disagreement the endpoint exists to remove.
    - **Fetch the list LAZILY, on the first keypress.** Not on session mount: most sessions are read and never jumped in, and a request per session open is pure waste. `userJumpFetchRef` gates it; reset every jump ref on `sessionId` change, because the cursor is a position in the *previous* session's list.

The first press in *either* direction enters at the newest user message, which is both the nearest entry point (the reader is at the bottom) and keeps the two keys symmetric so neither is ever a silent no-op. `NO_USER_JUMP = -1` is the "no walk" sentinel; `userJumpLabel` returns `""` (not `msg 0/0`) so the caller can render nothing.

    - Off-window targets reuse the find bar's `olderPrefixFetch` + `PREPEND_MESSAGES` path. Two overlapping prepends would each subtract their own length from `windowStartServerIndex` and double-count the overlap, so the jump's prefix effect also bails while the find bar's fetch is in flight (it self-heals: the effect re-runs when `entryPosByServerIndex` changes identity). 53. **The Cron tab is three sub-views over TWO stores, and "pending" is the only re-armable state** — the tab's switcher (`CronSubTabs.tsx`) picks `Jobs | Reminders | Tasks`. Jobs is the pre-existing `scheduler.Job` list; reminders and tasks are `internal/reminders` items behind `/api/reminders` and `/api/tasks` (a separate store and engine, but they append to the SAME `deliveries.jsonl` and `runs.jsonl` cron uses — so a reminder shows up in the Outbox panel and gets the same history panel). Five things that are easy to get wrong, each of which was a real bug while building it:
    - **The two spellings differ, so map them in ONE place.** A list view knows its collection as the SINGULAR `"reminder"`/`"task"` (the route segment and the `Kind` type); the switcher knows its views as the PLURAL `"reminders"`/`"tasks"`. Deriving one from the other by string surgery silently broke `aria-controls` (pointing at ids that did not exist) and the sub-tab badges (never appeared). `CronPanel` holds the only mapping, `SUB_VIEW_FOR_KIND`, and `ReminderTaskView` takes `panelId` as a PROP rather than deriving it. If you add a fourth sub-view, extend that map — do not re-derive.
    - **All three panes stay MOUNTED; a pane loads LAZILY.** Keeping them mounted is what preserves each one's filter, dialog and scroll position across a switch (Radix `TabsContent` unmounts by default, which is why this is a `role="tablist"` of plain buttons instead). But mounting is not loading: `ReminderTaskView` gates its fetch behind `activated`, which flips the first time it is the front view. Without that gate, opening the Cron tab costs two extra requests for lists the user never looked at — and it also broke the two committed `CronPanel.*.test.tsx` suites, whose `api` mock lacks the new methods and crashed on `api.listReminderItems is not a function`. Only the front pane polls (`active && subView === <view>`).
    - **Every re-read trigger is an explicit input to ONE effect: `activated`, `statusFilter`, `reloadToken`, `refresh`.** Splitting "project changed" from "filter changed" into two effects is what let the status filter update local state and then quietly do nothing — the load effect did not depend on it. The `reloadToken` is a COUNTER, not a boolean, because resetting the filter to "all" when it is already "all" produces no state change, so a plain dependency would not fire at all.
    - **Status is the server's call; the client only hides what it knows is illegal.** `REMINDER_STATUS_TRANSITIONS` in `api/types.ts` mirrors `allowedTransitions` in `internal/reminders/transition.go` so `Start` is not rendered for a `completed` item.     - **A status change is a PATCH, so assert the ROUND TRIP, not the call.** The list is re-read after every mutation, so a mock that only counts calls lets the chip sit on "Pending" forever and still passes. `ReminderTaskView.test.tsx` therefore runs a tiny stateful fake server (a PATCH mutates, the next GET reflects it) — that is what makes "marks a task done and back to pending" able to fail.

Wrap the advance in `act()`. A Radix `Select` needs `fireEvent.click` on the trigger and its option queried with `within(document.body)` (it portals out).

56. **Terminal paste has exactly ONE owner: the native `paste` event — the keydown must not read the clipboard** — a `Cmd/Ctrl+V` pasted the clipboard text **twice** into the pty, in both the browser and the desktop shell. Verified against the installed `@xterm/xterm` 6.0.0 bundle, the mechanism is two facts: (a) xterm registers a native `paste` listener on **both** its hidden textarea and its element (`handlePasteEvent` → `paste(clipboardData.getData("text/plain"))` → `triggerDataEvent`), and a browser's `Cmd/Ctrl+V` **default action** is to dispatch that event on the focused editable element, which for a terminal is xterm's textarea; (b) xterm's `_keyDown` returns early **without `preventDefault`** as soon as a custom key handler answers `false`. So the old `pasteFromClipboard` (async `navigator.clipboard.readText()` → `term.paste`) fired **in addition to** xterm's own listener — two pastes, not a fallback. The rules:
    - **Never read the clipboard in the keydown.** `attachCustomKeyEventHandler` now returns `false` for `Cmd/Ctrl+V` and nothing else: `false` is what stops xterm's keyboard layer from turning a non-mac `Ctrl+V` into a literal `\x16` byte (that is the *only* reason the branch exists), and it must **not** call `preventDefault` — preventing the keydown default would suppress the `paste` event and with it the only paste.
    - **A container-level `paste` listener in CAPTURE phase owns the event.** `term.open(containerRef.current)`, so the panel root is an ancestor of the textarea: capture runs before xterm's target-phase listener, and `stopPropagation()` keeps that listener from ever running. It reads `clipboardData.getData("text/plain")`, returns early when empty (image-only clipboard), then `preventDefault()` + `stopPropagation()` and `term.paste(text)` (never a raw `sock.send`, so bracketed-paste is honored). This is the exact mirror of the sibling `copy` listener above it, and the paste-side dedupe exists for the same reason: one physical paste can arrive twice in the desktop shell (native `application.EditMenu` role **and** the keydown default action — `cmd/ocode-desktop/main.go` adds the Edit role), so `DUPLICATE_PASTE_WINDOW_MS` (**50ms**, far below the copy window's 250ms) drops a same-text repeat. Two numbers, both deliberate: the two deliveries of one paste land within a few ms, so a wide window buys nothing and would start swallowing a user's own rapid repeat — a dropped duplicate is the cheap mistake, a swallowed paste reads as "paste is broken" — and it reads `performance.now()`, not `Date.now()`, so a wall-clock jump cannot silently disable it. `stopPropagation()` in capture is also why a *deliberate* re-paste and a different-text paste are never lost: only identical text inside the window is dropped.
    - **Scope the listener to the TERMINAL, not the panel.** A capture-phase listener on the panel root also sees pastes aimed at the panel's other inputs — **`TerminalFindBar` renders its search `<input>` inside that same container** — so without a `term.element.contains(e.target)` guard, `Cmd+V` in the find box pastes into the shell *and* `preventDefault()` empties the field.     - **The right-click menu's Paste is the same path now.** `handlePaste` was `readText()` + a raw `sock.send(text)`, which skips bracketed-paste wrapping (a multiline payload would run line by line in `vim`) and bypasses the `attachedRef` + socket-state guard `term.onData` already applies.     - **xterm's `_inputEvent` is not a second paste.** It emits only for `inputType === "insertText"`, so the browser's own `insertFromPaste` into the textarea is ignored; this was checked rather than assumed.
    - **jsdom must model the DOM or the test is vacuous.** The regression tests build xterm's real nesting — panel root → `term.element` → a `<textarea>` carrying its own paste listener that calls the same `term.paste` mock — and dispatch a `paste` event with a stubbed `clipboardData`; that is the shape which produced the bug, and the stub `Terminal` needs an `element` field for the guard to be exercised at all. Regression: `web/src/components/Terminal/TerminalPanel.copyOnSelect.test.tsx` ("Cmd/Ctrl+V keydown blocks xterm (no \x16) and leaves the paste to the browser's paste event", "pastes a native paste event once and keeps xterm's own paste listener from seeing it", "drops a duplicate paste event for one physical paste", "still pastes the same text again 100ms later", "never drops a paste of different text inside the duplicate window", "leaves a paste aimed at another input inside the panel (the find bar) alone", "pastes the right-click menu Paste through term.paste, never a raw socket write").     - **The shortcut list lives on the textarea's `title`, NOT in its `placeholder`.** `CHAT_INPUT_PLACEHOLDER_HINT` holds "Enter to send · Shift+Enter for newline · ↑/↓ history · / for commands · ! for shell" and the placeholder is just `"Type a message…"`. The previous 110-character placeholder was the root cause of both narrow-width defects above (it dominated the box on desktop too), and no amount of CSS can stop placeholder text from owning the box's height. Regression: `ChatInput.rowAlign.test.tsx` pins the short placeholder AND that every hint still appears in `title`, because jsdom cannot observe wrapping.
    - **Verify narrow widths and font scales in a real browser, not jsdom.** Measured across 320/390/600/760/900/1100/1400/1600 CSS px and 16/20/24px root font: all three controls 47px, tops and bottoms aligned, no flex wrap, no page overflow, `scrollHeight == clientHeight`. A jsdom suite cannot see any of it (no stylesheet, no layout engine), so it pins the CSS *contract* only — the class names, `items-end`, the chrome term, and the placeholder/title split.
    - **A `className={\`h-[${CONST}px] …\`}` template literal produces NO CSS at all.** Tailwind's scanner reads the raw source text and cannot evaluate an interpolation, so the arbitrary value is simply never emitted — the element renders at its intrinsic size with no error and no warning. Verified in `dist/assets/*.css`: the interpolated form emits nothing, the `.composer-control` class emits its declared `height:calc(2.8125rem + 2px)`. This is the general trap for every Tailwind class in this codebase, not just heights. Use a real class, a plain literal, or an inline `style`.
    - **`items-end`, not `items-center`, is deliberate.** The textarea auto-grows to `max-h-40`; the controls must stay pinned to its BOTTOM edge, and they keep their base height rather than stretching. At one line all three edges coincide (measured live: top 808 / bottom 855 / h 47 for all three); at five lines the textarea is 131px and the controls sit at its bottom, which is correct.
    - **`scrollHeight` excludes the border but `height` is border-box — so a measured auto-fit must add the chrome back.** `fitTextarea` used `el.style.height = \`${el.scrollHeight}px\``, leaving the box 2px short of its content and **pinning a scrollbar track on an EMPTY composer** (visible in the screenshot that prompted this). The fix is `el.scrollHeight + (el.offsetHeight - el.clientHeight)`; both are 0 under jsdom, so the modelled tests still see the bare `scrollHeight`. Measured before/after on an empty box: old → `offset 45 / client 43 / scroll 45` (overflowing, scrollbar shown), new → `offset 47 / client 45 / scroll 45` (exact, no scrollbar). The `max-h-40` ceiling is unaffected — it caps the border-box at 160px either way.
    - **jsdom cannot verify any of this.** It loads no stylesheet and has no layout engine, so `ChatInput.rowAlign.test.tsx` can only pin the CSS *contract* (every row control carries `composer-control`, the row is `items-end` and not `items-center`, and the fit adds the chrome). The DECLARED height and the scrollbar behaviour must be checked against the BUILT stylesheet — `grep -o '\.composer-control{[^}]*}' dist/assets/*.css` — and then measured in a real browser. A mutation that only changes the CSS number survives the jsdom suite by construction; that is a limitation of the test, not a coverage gap to fix by weakening the assertion.
61. **The composer's quick-action strip is CONFIG, and several of its rules live in Go rather than in the component** — the pills below the chat input are no longer a hardcoded array; they are the user's chips from the shared `quick_actions` config (`{id,label,icon,message,mode,seed?}`) over authenticated `GET/PUT /api/config/ocode/quick-actions` (`api.getQuickActionsConfig`/`setQuickActionsConfig`, **no `host`** — the Settings panel is a global surface). Settings → **Quick actions** (`QuickActionsForm.tsx`, nav id `quick-actions`) edits them; `web/src/lib/quickActions.ts` holds the helpers, the icon map and the store; `ChatInput.tsx` builds ONE memo from `visibleChips(...)` and renders that list, so the ordering logic lives in a single place — do not split it into two memos. Rules that are easy to get wrong: (a) **`Chips == nil` means "no config yet" → seed the three starters; a non-nil EMPTY slice means the user deliberately deleted every chip → no strip.** Branching on `len(Chips) == 0` resurrects the starters for a user who removed them. Documented on the Go type, pinned by `TestSaveAndLoadOcodeQuickActionsPreservesEmptyStrip`. (b) **Go owns the starters and the allowlist; TS only degrades.** Go seeds and validates and returns resolved chips on GET; `SEED_CHIPS` in TS exists solely so a failed FIRST fetch renders the pre-feature strip instead of blanking, and it is pinned by a literal assertion. The 24-icon allowlist is duplicated in both languages on purpose — Go validates without a network round-trip, TS renders before its fetch lands. **The drift guard is PER-SIDE, not cross-language:** Go pins its key set against a transcription of the spec's list, TS pins its own length and distinct-component count, and `ICON_COMPONENTS` is typed `Record<(typeof QUICK_ACTION_ICONS)[number], LucideIcon>` so a key with no component is a typecheck error. Nothing reads the other language's file, so a key changed on one side only is still silent — if you touch the allowlist, change BOTH and update both transcriptions. (c) **Two states are DERIVED, never stored**, because a stored flag drifts the moment the message is edited: "dims while compacting" is `compacting && mode === "send" && chipDispatchesCompact(chip)`, and "requires history" is `seed != null` (seeded chips hide on an empty session, custom chips do not). This is why the visibility gate lives in the CHIP, not in a `{hasConversation && …}` wrapper — one always-visible custom chip would be suppressed by a wrapper written for the seeded three. (d) `mode: "fill"` puts the message in the composer and focuses it, replacing the draft, without sending or queueing; `"send"` goes through the existing `runQuickDispatch`, so a leading `/` still routes to the slash pipeline and busy-turn queueing is unchanged. The Continue preset's `seed` makes it resume an interrupted turn ahead of both modes. Its LABEL is left as the user configured it — it does **not** relabel itself to "Resume" the way the old hardcoded pill did; the tooltip gains `— resume the interrupted turn` instead, because the label is user-controlled. (e) **The queue holds resolved TEXT, not a chip id**, so editing or deleting a chip mid-queue cannot corrupt the pending dispatch — do not "improve" the queue to store the chip. (f) `NormalizeQuickActions` must NOT mutate its argument (`slices.Clone`): the struct copies by value but `Chips` is a slice header, so an in-place loop writes through to the caller and races a handler that snapshotted a cached config out from under its mutex. (g) `refreshQuickActions` is `async`, so a SYNCHRONOUS throw from an incomplete api surface becomes a rejected promise whose internal `.catch` never runs; refreshes go through `refreshQuietly()` and the `eventBus` subscriptions are guarded with a no-op fallback, or a partial `vi.mock("../../api/client")` becomes unhandled rejections that fail an all-green run. (h) The PUT needs a STRICT top-level decoder, not `readBodyJSON`: a plain `json.Decode` silently drops an unknown top-level key, so `{"chip":[…]}` would store as "the starters" with a 200. Load-time `Validate()` is deliberate, mirroring `chat_verbosity` — without it a hand-edited invalid strip loads silently and `writeOcodeConfigFile` writes the same block straight back, making the cap bypassable with a text editor. That is also why `writeOcodeConfigFile`'s payload always includes `quick_actions`: without it chip edits would never persist. (i) A new chip is minted with an empty `message`, so the first save after adding one always 400s until the user types one — server-as-authority is deliberate, but do not "fix" it by validating locally. Regression tests: `web/src/lib/quickActions.test.ts`, `api/client.quickActions.test.ts`, `Settings/QuickActionsForm.test.tsx`, `Chat/ChatInput.quickActions.test.tsx`; Go `internal/config/quick_actions_test.go`, `internal/server/handler_quick_actions_test.go`, and `handler_quick_actions_routes_test.go` (the real-mux test — a handler-only test cannot catch a missing route, which surfaces as a 404 from the SPA fallback). Design record: `docs/superpowers/specs/2026-10-01-quick-actions-config-design.md`.
58. **Settings → Browser's HTR section shows shared-daemon PROVENANCE, and the two shared keys are read-only on purpose** — ocode no longer runs a private `htrcli serve`; it ensures the one htrcli's own `~/.htrcli/config.json` describes, so the embedded browser and the user's installed HTR extension attach to the SAME daemon. `BrowserForm.tsx` is where that surfaces, and every rule below exists because the alternative reads as a broken Settings page:
    - **The field list.** Writable from this form: `chrome_path`, `idle_timeout_minutes`, `screencast_quality`, and `htr_port` / `htr_socket_path` **only when `htr_shared` is false**. Read-only, config-file-only (`config.SaveOcodeHTRConfig` has no parameter for either, so a control here would silently fail to persist): **`browser.htr_shared`** (bool, default `true`; `false` = the legacy private 3846 daemon, the rollback path) and **`browser.htr_token`** (escape hatch that substitutes the bearer *value* when htrcli's config is readable but tokenless). Never add an input for these — the existing copy ("set in ocodeconfig.json — this form cannot write them") is the honest answer.
    - **The two inputs are DISABLED, and omitted from the save payload, under shared mode** (`save()` spreads `...(browserCfg?.htr_shared ? {} : { htr_port, htr_socket_path })`). Sending them anyway would rewrite the legacy values on every Save; the inputs are disabled so their state is whatever loaded, not something the user typed.
    - **A leftover `htr_port: 3846` in a user's config is ignored under shared mode, and the panel must SAY so** rather than echo it. `GET /api/config/ocode/htr` returns the effective coordinates with provenance (`effective_port`, `effective_socket`, `config_path`, `token_source`, `adopt_only`, `mode`, `started_by_ocode`) and the `data-testid="htr-effective"` block renders *those*, with the input labels switching to "legacy private-daemon mode only". Rendering the configured value where the effective one belongs is what makes the page look broken.
    - **`token_source` is rendered on its own node** (`data-testid="htr-token-source"`) because `config_path` also contains the substring "htrcli" — a substring assertion over the whole row passes even if the label is dropped.
    - **Adopt-only renders an amber notice, and the notice is the resolver's own wording.** `SharedDaemon.Notice` names the actual problem (missing / unreadable / not-JSON / non-loopback `server` / no token) and the fix; the server only substitutes a generic sentence when the resolver produced none. A missing htrcli config must NOT be fixed by `browser.htr_token` and the notice must never offer it — ocode never passes `HTR_BEARER_TOKEN` to a shared daemon, so a spawned one would resolve no token at all.
    - **The Stop button is gated on `started_by_ocode`, not `running`.** ocode stops only a daemon this process spawned (`started_by_pid` in the owner marker, never `owner_pid`); a refused stop comes back as `stopped: false` with a reason, and disabling the button is what stops it from looking like it worked. The title explains the refusal rather than leaving a mysteriously dead button.
    - **Consequence to state, not hide:** closing ocode stops the daemon when ocode started it, so the user's extension drops. Intended — one daemon.
    - Regression: `BrowserForm.htrShared.test.tsx`, `BrowserForm.test.tsx`; server side `internal/server/handler_htr_shared_test.go` (provenance hidden for a stopped daemon, effective values from htrcli's config not the legacy fields) and `internal/config/ocodeconfig_htr_test.go`. Backend chain: `cdp.ResolveSharedDaemon` → `resolveManagedHTROptions` → `cdp.HTROptions.Shared` → `ManagerOptions.HTRSharedMode` → `filterSharedLaunchEnv`, which in shared mode withholds `HTR_SOCKET_PATH` from the headless Chrome so the preload's relay falls back to htrcli's own default socket.
