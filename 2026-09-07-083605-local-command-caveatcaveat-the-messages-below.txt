⏺ Found something important: there's already an approved architecture spec for
  this exact feature (docs/superpowers/specs/2026-08-29-remote-ssh/), and my
  first research pass pointed at a design that spec explicitly rejected.
  Correcting course before writing a plan.

  The approved architecture: the entire ocode backend runs on the remote host
  (SSH or WSL); the local browser/desktop is just a display client connected
  through an SSH tunnel (or, for WSL, plain localhost — Windows forwards it).
  Under this model, the Terminal panel needs zero changes — when you're
  connected remotely, HandleTerminalWS spawning a "local" shell is correct,
  because that server's local is the remote host. This was chosen specifically
  to avoid threading an SSH/WSL-aware runner through ~700 os.*/exec.Command call
  sites.

  Current implementation status:
  - Phase 1 (SSH connect, TUI passthrough via ssh -t) — done (git history
    confirms)
  - Phase 2 (web mode: remote server + SSH tunnel + token auth) — not 
    implemented (no --web/--remote flag exists yet)
  - Phase 3 (WSL transport swap) — not implemented, ParseTarget rejects wsl:
    targets outright, and Connect() hardcodes NewSSHTransport regardless of
    Target.Kind (so even Phase 3 needs a small dispatch fix, not just a new
    file)

  The spec also states Phase 3 reuses Phase 2's web-mode design verbatim and
  says to implement strictly in order — so "also implement WSL" commits us to 
  building Phase 2 first.

  Separately, there's a real small bug today: the web UI's "Add Remote Project"
  bookmarks a (host, path) but selecting it doesn't connect anywhere — it just
  silently runs a local shell in your home directory while the UI implies you're
  on that remote host.
